# Сравнение с эталоном: AI-Harness (наш) vs AIF Handoff (lee-to/aif-handoff)

Дата: 29.10.2026. Вопрос владельца: «переходы задач между статусами и взятие их
агентами у нас сделаны хуже, чем в референсе — переходы сейчас не работают,
задачи не берутся. В чём разница и как доработать, сохранив гибкость управления?»

---

## 1. Общее описание

Наш AI-Harness **не хуже по механике — он другой по замыслу**. AIF Handoff — это
жёсткий конвейер-транспортер: статусы зашиты в код (Backlog → Planning →
Implementing → Review → Done), система сама тащит каждую задачу от создания до
готовности, человек лишь иногда подписывает план или принимает работу. Наш
Harness — это конструктор конвейера: владелец рисует статусную модель сам,
сам назначает агентов на статусы, а демон лишь **реагирует** — берёт задачу
там, где стоит назначенный агент, и делает то, что разрешают рёбра.

Обратная сторона гибкости: **конвейер не стартует сам**. В референсе «создал
задачу — поехало». У нас задача лежит в «Бэклоге», пока человек не подтолкнёт
её в первый рабочий статус. Если владелец не настроил матрицу или не толкнул
задачу — она молча стоит, и выглядит это как «переходы не работают».

Плюс в момент анализа в работающем стеке был **реальный баг**: после
рефакторинга таймаутов (фикс-сессия 29.10) каждый запуск агента падал с
NameError ещё до старта SDK — задача уходила в ретраи и блокировалась
«требуется участие человека». Баг закрыт (коммит 80fc008 + e2e-тест раннера,
контейнер пересобран). Итого «не работает» = баг (исправлен) + интэйк
(особенность дизайна, см. §5).

## 2. Живой диагноз на стеке 29.10.2026

| Факт | Данные | Вывод |
|---|---|---|
| В очереди нет задач на рабочих статусах | 6 задач VITRINA в `backlog`, 2 истории в `blocked`, остальное терминальное | Демону нечего брать: подбор идёт только на статусах с назначением |
| Из `backlog` нет агентного пути | Единственное ребро `backlog→todo` — runner=`human`; назначений на `backlog` нет | Задачу в работу может ввести только человек |
| Прогон по живой задаче AH-130 упал мгновенно | `NameError: _iterate_sdk is not defined` (agent_runner, рефакторинг таймаутов 29.10) | Даже на назначенном статусе прогон умирал до SDK |
| После фикса задача AH-130 взята демоном на `todo` за один тик | reserve → запуск SDK → «сессия агента запущена», пульс свежий | Механика подбора и переходов работает |
| Первая послеправочная попытка погибла «heartbeat пропал» | SDK холодно стартовал >90 с; порог пульса (90 с) короче таймаута старта (300 с) | Легитимно медленный старт убивается свипом пульса — нужна фаза «старт» без свипа или watchdog первой активности с рестартом (см. §5.3) |

## 3. Как устроен AIF Handoff (референс)

- **Статусы захардкожены** (`packages/shared/src/types.ts`): 10 статусов, валидация
  enum'ом, пользователь добавить/переименовать не может.
- **Правила переходов — чистая функция** (`packages/shared/src/stateMachine.ts`):
  события `start_ai`, `request_changes`, `fail_verification`…; права зависят от
  флагов задачи (`autoMode`, `executionOwner` ai/human) и режима участников.
- **Координатор-демон** (`packages/agent/src/coordinator.ts`): опрос каждые 30 с
  + мгновенное пробуждение по WebSocket (`task:created`, `task:moved`,
  `agent:wake`). Конвейер — статический массив `PIPELINE`: на каждую стадию
  один фиксированный раннер (planner → implementer → reviewer+security sidecar).
- **Автозапуск**: `autoQueueMode` проекта сам докидывает задачи из backlog в
  planning (пул = 1 последовательно или N параллельно).
- **Двойной захват исключён** трёхслойно: семафор в памяти → CAS-claim в БД
  (`lockedBy`/`lockedUntil` + продление heartbeat'ом) → повторная валидация.
- **Самолечение**: таймаут стадии (1 ч) + abort процесса; классификатор ошибок
  (быстрый ретрай / `blocked_external` с бэкоффом 5–15 мин / ручной блок);
  watchdog «залипшей» стадии (90 мин без heartbeat → блок, после 3 попыток —
  карантин); watchdog первой активности (нет tool-call за 60 с → рестарт).
- **Rework с контролем сходимости**: ревью вернуло замечания → задача едет
  обратно в Implementing; лимит итераций (3); стратегия `closure_first` — если
  старые замечания закрыты, но появились новые, конвейер честно передаёт задачу
  человеку с флагом `manualReviewRequired`, а не крутит вечный цикл.

## 4. Сравнение по осям

| Ось | AIF Handoff | AI-Harness (наш) | Кто гибче |
|---|---|---|---|
| Статусная модель | захардкожена | редактируется графом, публикуется версиями, задачи живут по своей версии | **наш** |
| Кто двигает задачу | система (конвейер) всегда | определяется рёбрами: human/agent/auto/auto_or_agent на каждом ребре | **наш** (но нужна настройка) |
| Кто исполняет стадию | фиксированный субагент на стадию; меняется только модель (runtime-профиль plan/task/review на проекте) | матрица «тип × статус → агент», режимы «параллельно»/«замещение» | **наш** |
| Автозапуск задачи | есть: создание/auto-queue тянет из backlog | нет: intake-рёбра human, демон чисто реактивный | **референс** |
| Реакция на новое | мгновенно (WS-wake) | до тика (30 с) | референс |
| Двойной захват | семафор + CAS + revalidation | атомарный условный UPDATE (проверено тестом 1000 задач × 2 демона) | паритет |
| Ретраи/самолечение | классификация ошибок, бэкофф, карантин, watchdog первой активности 60 с | heartbeat 90 с, таймауты старт 300 с / работа 1800 с, лестница 1→5→15 мин, circuit breaker провайдера | паритет (разные акценты) |
| Rwork-петля | ревью → Implementing с лимитом итераций и передачей человеку при расходимости | зеркала M1–M6, цикл доработки M4 с лимитом 5 → blocked | паритет, у референса честнее сигнализация (`manualReviewRequired`) |
| Наблюдаемость | бейдж AI/Human owner, permittedActions с бэка | живая хроника, лента прогона, токены, «система ждёт человека» | **наш** |

## 5. Технические детали: почему у нас «не едет» и что делать

### 5.1 Корень 1 — нет автозапуска (главная разница с референсом)

> **Актуализация 29.10.2026 (коммит 852d65c):** по решению владельца статус
> backlog удалён из пресетов — intake теперь pending→todo (человек вводит задачу
> в работу одним переводом). В «В работе»/«К работе» сид назначает пресет-агентов
> по умолчанию (Планировщик на todo и т.д.), задачи VITRINA мигрированы. Ниже —
> исходный разбор; матрица «статус с назначением → демон берёт» не изменилась.

В нашей модели демон берёт задачу, только если сходятся три условия:
1. задача стоит на статусе X;
2. в матрице на (тип задачи, X) назначен живой агент;
3. из X есть ребро, которое агент имеет право пройти.

Сейчас для всех пресетов условия сходятся только начиная с `todo`
(«Готово к декомпозиции»): `backlog→todo` — human. Задачи скапливаются в
`backlog` и никогда не стартуют сами.

**Решение без новой техники** (в рамках существующей модели): в пресетах flow
перевести интэйк-ребро `backlog→todo` в `auto_or_agent`. Тогда на `backlog`
можно назначить агента (движок разрешает назначение только на статусы с
агентными рёбрами — условие выполнится), демон сам возьмёт задачу в backlog,
агент декомпозирует/подготовит чеклист и предложит переход в `todo`, где уже
работает существующая цепочка. Владелец, который хочет ручной отбор задач,
просто не назначает агента на `backlog` — поведение остаётся прежним.

### 5.2 Корень 2 — баг раннера (закрыт 29.10.2026)

Рефакторинг таймаутов превратил итератор SDK в метод `_iterate_sdk`, а вызов
остался модульным: `await _iterate_sdk(self, …)` → NameError на каждом прогоне.
Закрыт коммитом 80fc008 (+e2e-тест раннера на фейковом SDK); контейнер демона
пересобран, живой прогон AH-130 подтверждает взятие задачи и старт SDK-сессии.
Вторая находка того же прогона: попытка 1 после фикса умерла «heartbeat пропал» —
холодный старт SDK (нода + CLI + первый ход через прокси) занял больше порога
пульса 90 с. Свип пульса не различает фазу старта: таймаут старта 300 с
разрешает ждать, а свип убивает через 90 с. Минимальная правка — при
`heartbeat_at == started_at ± тик` (ещё нет ни одного события SDK) держать порог
пульса равным таймауту старта; целевая — watchdog первой активности с рестартом
(§5.3 п.3). Урок для
фикс-сессий: **путь `ClaudeCodeRunner.run()` целиком не покрыт тестами —
FakeRunner-путь демона эти ошибки не видит**; e2e-тест раннера теперь закрывает
класс «метод потерян / вызов модульный».

### 5.3 Чего стоит взять у референса (по ценности)

1. **Мгновенное пробуждение демона** (аналог WS-wake): сейчас человек подвинул
   задачу — агент стартует через ≤30 с. Достаточно события «kick» в существующий
   SSE-контур: бэкенд после мутаций статусов пишет в канал, демон слушает и
   делает внеочередной тик. Низкий риск, заметный UX-эффект.
2. **Честная передача человеку при несходимости** (аналог `manualReviewRequired`):
   при исчерпании лимита цикла доработки ставить не только `blocked`, но и
   структурированный флаг/причину для карточки («ревью не сходится N циклов —
   нужно решение человека»).
3. **Watchdog первой активности**: рестарт прогона, если агент не подал признаков
   жизни за 60–120 с (у нас сейчас только грубый таймаут старта 300 с).
4. **Диагностика застоя**: уведомление «в backlog лежит K задач, автозапуск не
   настроен» в warnbar `/pipeline-status` — чтобы «молчаливый простой» был виден
   сразу, а не находился по ощущению.

### 5.4 Чего брать НЕ стоит

- Захардкоженный конвейер и фиксированные субагенты — это потеря нашего
  главного преимущества (редактируемые flow + матрица).
- Отдельная таблица «история исполнителей» — у нас ту же роль играет хроника.

## 6. Итог

«Сильно хуже» — неверное ощущение: по гибкости (статусные модели, матрица
агентов, гейты, зеркала) наш решение **богаче референса**. Реально не хватало
двух вещей: работающего прогона агента (баг, исправлен) и **автозапуска
конвейера** (дизайн-решение; минимальная доработка — §5.1, четыре опции из
§5.3 — следующие шаги).
