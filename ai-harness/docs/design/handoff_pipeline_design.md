# Handoff-конвейер: от системных требований к автономной разработке (проект v3)

> **Статус:** проект на обсуждение. Не канон. После утверждения — дополнение к
> `harness_by_v2.md` (v2 остаётся базой: гейты, трассируемость, изоляция не пересматриваются).
> **Автор запроса:** «harness совсем не автономный, не управляемый, не интерактивный» —
> референс [aif-handoff](https://github.com/lee-to/aif-handoff); цель — конвейер
> «аналитика → разработка»: СТ sa-helper подаются в harness, дальше конвейер едет сам.
> **Родственные документы:** `harness_by_v2.md` (канон v2), `harness_by_v1.md` (архив).

---

## 0. Суть в двух словах (бизнес-слой)

Сегодня harness — это набор отличных инструментов, которые крутит человек. Каждая команда
(`/impl-plan`, `/impl-run T3`, `/impl-review T3`…) — отдельная сессия, которую аналитик
запускает вручную, читает результат и решает, что делать дальше. Сессия закончилась —
конвейер стоит. Пауза — только общий флаг на весь прогон. Комментарий к задаче агент
увидит, только когда сам дочитает до границы итерации в следующей сессии.

**Handoff-конвейер — это третий контур поверх harness: конвейер едет сам, человек управляет.**
Аналитик заканчивает свою работу там же, где и раньше, — утверждённым СТ. Дальше он
передаёт СТ конвейеру одной командой, утверждает план (тот же шлюз, что был), и конвейер
сам ведёт DAG задач: реализация → ревью → доработка по замечаниям → следующая задача.
Человек не запускает команды — он управляет из витрины: одобрить задачу, вернуть на
доработку с комментарием, поставить на паузу, спросить агента в чате. Как Jira, где
исполнитель — не человек, а агент, но с механическими воротами качества вместо доверия.

Что это меняет для аналитика:

- **Постановка задачи остаётся единственным ручным трудом.** Всё, что после утверждённого
  СТ и плана, конвейер доводит до PR без человека в цикле команд.
- **Управление становится адресным.** Не «остановить всё», а «остановить T5»; не
  «переписать правки руками», а «вернуть T4 на доработку с комментарием» — из окна витрины.
- **Конвейер честно сообщает, когда не справился.** Если ревью и доработка не сходятся,
  задача останавливается в состоянии «нужен человек», а не притворяется готовой.

Чем handoff-конвейер **не является**: это не автопилот без шлюзов. Оба ручных шлюза v2
(утверждение плана, приёмка PR) сохраняются; автономность — между ними, на уровне
конвейера, а не на уровне отмены контроля качества.

## 1. Анализ aif-handoff

### 1.1 Что это

Автономная канбан-доска: создаёшь задачу — ИИ сам планирует, реализует и ревьюит.
Монорепо TypeScript (7 пакетов): React UI, HTTP/WebSocket API, SQLite (drizzle),
координатор-демон (node-cron + WebSocket wake) и слой «runtime-адаптеров» — транспортов
к LLM (Claude CLI/SDK, Codex CLI/SDK, OpenRouter, OpenCode). Агентные роли — markdown-
определения из AI Factory (`plan-coordinator`, `implement-coordinator`, `review-sidecar`,
`security-sidecar`); для каждого проекта в его каталог кладётся каркас `.ai-factory/`
(DESCRIPTION, ARCHITECTURE, RULES, PLAN.md). Конвейер: Backlog → Planning → Plan Ready →
Implementing → (Verify) → Review → Done → Verified, с автоматической петлёй доработки
Review → request_changes → Implementing и честной передачей человеку, когда петля не
сходится («Done + manual review required»).

### 1.2 Ключевые механики (что именно стоит перенять)

1. **Демон-координатор вместо человека-диспетчера.** Фоновый процесс опрашивает очередь
   (30 с) и просыпается по событиям; атомарно «захватывает» задачу (lock + TTL),
   ведёт её по машине состояний. Человек не запускает команды — он создаёт события.
2. **Машина состояний как закон.** Статусы и переходы — чистая функция «(статус, событие,
   контекст) → патч», одна на API, демона и UI. Человеку доступны ровно те действия,
   которые разрешены в текущем статусе (`plan_ready`: начать реализацию / запросить
   перепланирование; `done`: approve / request_changes; `blocked`: retry). Нельзя «начать
   реализацию» задачи, которая не спланирована, — не потому что промпт вежливый, а потому
   что переход запрещён.
3. **Сходимость авто-ревью (главная жемчужина).** Вердикт ревьюера — структурированный
   документ (`## Blocking findings` / `## Advisories` / статус прежних находок), который
   парсится детерминированно, без LLM. Находка = текст + стабильный ID (hash). Петля
   доработки различает: прежние находки устранены / остались; есть ли новые. Стратегия
   `closure_first`: если прежние закрыты, а ревьюер нашёл новые — петля останавливается,
   задача уходит человеку (иначе можно итерировать до бесконечности). Лимит итераций тоже
   останавливает петлю с явным `manual_review_required`.
4. **Надёжность долгих автономных прогонов.** Heartbeat (агент регулярно отмечает
   живость), watchdog «зависшей стадии» (нет активности дольше таймаута → задача в
   `blocked_external` с повтором по backoff), first-activity watchdog (агент стартовал и
   молчит → убить и перезапустить), fencing (ID попытки: устаревший прогон не может
   записать результат поверх нового).
5. **Адресное управление задачей.** Флаги на задачу, а не на конвейер: `autoMode`
   (пропускать ли шлюзы автоматически), `skipReview`, `paused` (пауза не убивает текущий
   прогон — вступает на следующей стадии), `request_replanning`, `fast_fix`, отложенный
   запуск (`scheduledAt`), auto-queue (держать N задач в работе).
6. **Интерактивность.** Живой лог агента (stream-json), комментарии к задаче (человек и
   агент — в один журнал), чат с задачей, передача в работу как явная смена владельца
   (human ↔ AI) с историей исполнителей.
7. **Транспорт агентов — обычный CLI.** Внутри всё скучно и воспроизводимо:
   `claude --output-format stream-json --verbose -p [--resume <sid>] [--max-turns N]
   [--permission-mode acceptEdits | --dangerously-skip-permissions]`. Никакой магии SDK —
   значит, то же самое можно сделать из Python стандартной библиотекой.

### 1.3 Чего в aif-handoff нет (наши преимущества — сохранить)

| Наше | У них | Следствие |
|---|---|---|
| **Требования = контракт**: СТ с FR-ID → AC-ID, §2.5 «Затронутые системы и контракты» | title + description задачи | У нас вход конвейера богаче на порядок; их «планирование» изобретает требования из заголовка |
| Трассируемость FR → AC → тест → коммит `[FNR-N/Tk]` | чек-лист плана | Проверяемость покрытия требований у нас механическая |
| TDD RED-гейт (честно падающие тесты), impact-лестница (полный регресс), coverage-дельта | «run tests relevant to changes» | Защита смежного функционала у нас — механика, у них — просьба в промпте |
| **Мультирепо**: workspaces.yaml, DAG задач через репозитории, контракты К1–К3, фазы producer/consumer | один проект на задачу | Их конвейер не умеет задачу «переложить контракт между BI и TC» |
| Docker-first исполнение (build/test в контейнерах) | агент живёт в каталоге проекта | Совместимо: их демон ничего не знает о сборке — наш runner остаётся |
| Досье, build_info, пресеты стеков | `.ai-factory/` каркас | Аналог существует, наш предметно богаче |

### 1.4 Что сознательно НЕ копируем и почему

1. **Стек TS/React/SQLite/Hono/монорепо.** Универсальность (главная заповедь sa-helper):
   инструменты harness — stdlib Python, состояние — файлы в git-диффабельном формате,
   UI — текущая одностраничная витрина. SQLite не нужен при 10–50 задачах на FNR;
   блокировки и атомарность у нас уже решены (tmp + rename, один writer на поле).
2. **SDK-транспорт к Claude.** Прямое предупреждение в их README: использование Claude
   Max/Pro вне официального CLI запрещено условиями. Наш исполнитель — только CLI
   (`claude -p`), это и лицензионно чисто, и уже так работает sa-helper.
3. **Реестр runtime-профилей и провайдеров.** sa-helper — фреймворк Claude Code; слой
   адаптеров оставляем как *шов* (интерфейс «запусти промпт в каталоге, верни лог»), но
   реализуем один адаптер.
4. **GitHub Issue→PR, MCP-синк, участники/аккаунты.** Push — всегда вручную (правило
   пилота); MCP-синк — возможное продолжение, не база.

## 2. Диагноз текущего контура

| Жалоба | Корень в v2 | Что меняется |
|---|---|---|
| **Не автономный** | Оркестратор — человек: каждая `/impl-*` команда — отдельная интерактивная сессия; между командами конвейер не существует. DAG не движется сам; сессия завершилась — всё стоит | Демон-координатор ведёт DAG; сессии агента запускает он, по одной стадии |
| **Не управляемый** | Управление = 2 файла на весь прогон (APPROVE_PLAN, PAUSE). Нет действий по задаче: нельзя одобрить T5, вернуть T4 с комментарием, перезапустить зависшую T3, запросить перепланирование | Машина состояний + события по задаче из витрины; флаги остаются механикой, но адресные |
| **Не интерактивный** | Комментарии агент читает на границах итераций, если вспомнит; живого вывода агента нет; после завершения задачи диалог с её автором невозможен | Живой лог стадии в витрине; комментарии — первоклассные события (возврат на доработку); чат с задачей через resume сессии |

Важно признать: **внутри задачи v2 уже автономен** (RED→GREEN→гейты, circuit breaker,
PAUSE на границе итераций — проверено на T1/T2). Слабое место — не задача, а *конвейер
вокруг задач*: кто-то должен запускать следующую сессию, доставлять вердикт ревью
исполнителю и решать, что дальше. Этого «кого-то» в v2 нет — им был человек.

## 3. Целевая архитектура (v3)

### 3.1 Слои и поток

```
 СТ (утв.) ──► /impl-handoff ──► manifest v3 + tasks/ + dossier        (единоразово, как /impl-plan)
                    │
                    ▼
        orchestrator.py (демон, stdlib Python)          ← запуск: sa-helper daemon / вручную
          │  цикл: выбрать готовую задачу по DAG → провести стадию → применить переход
          │  состояние: manifest.json v3 + .flags/ + .run/ (heartbeats, логи стадий)
          │  надёжность: heartbeat + watchdog + retries с backoff + fencing
          ▼
        claude CLI (headless, одна сессия на стадию)
          • implementing: /impl-run T<k> (внутри — прежний цикл RED→GREEN→гейты, как в v2)
          • review: /impl-review T<k> (отдельная чистая сессия, структурированный вердикт)
          • rework: /impl-run T<k> + дельта ревью (fresh session)
          • verify: /impl-verify (после DONE всех задач DAG)
          ▼
        витрина v2 (kanban + действия + живой лог + чат)  ← человек управляет здесь
```

Принцип преемственности: **всё, что проверено в v2, не переписывается.** runner, хуки,
Docker-команды workspaces.yaml, пресеты, рубрика ревью, TDD-гейт, circuit breaker,
изоляция worktree — остаются. Добавляется слой *управления конвейером* (демон + машина
состояний + адресные события) и *канал обратной связи* (живой лог, чат).

### 3.2 Машина состояний задачи

Статус задачи разделяется на два поля (это ключ к совместимости с v2):

- `pipeline` — статус конвейера (кто и что должен делать дальше): `backlog` →
  `plan_ready` → `implementing` → `review` → `done` → `verified`; особые: `blocked`
  (внешняя помеха, ожидает retry), `needs_human` (петля не сошлась / эскалация).
- `phase` — внутренняя фаза исполнения (как в v2): TDD_RED / TDD_GREEN / GATES / … —
  её пишет сессия исполнителя, демон её только читает для витрины.

Таблица переходов (события человека — `A:`, агента — `X:`, автомата демона — `D:`):

| Из | Событие | В | Кто |
|---|---|---|---|
| backlog | `A: approve_plan` (= APPROVE_PLAN v2) | plan_ready→ Implementing первой готовой задачи | демон |
| backlog | `A: request_replanning` | перегенерация плана (/impl-plan) | демон |
| implementing | `X: все AC PASSED, gates passed` (manifest) | review | демон |
| implementing | watchdog: сессия молчит > таймаута | blocked (retry с backoff) | демон |
| implementing | `A: pause` (задача) | пауза на границе итерации (флаг v2) | сессия |
| review | `X: APPROVED` | done | демон |
| review | `X: CHANGES_REQUESTED` + находки | implementing (rework-дельта) | демон |
| review | петля не сошлась (closure-правило или лимит итераций) | needs_human (`manual_review_required`) | демон |
| review | `A: force_approve` | done (помечено «approved by human») | демон |
| done | все задачи DAG done → `D: verify` | verified (после /impl-verify) | демон |
| blocked | backoff истёк / `A: retry` | вернуть в статус до блокировки | демон |
| любой активный | `A: abort` | aborted | демон |

Правила:

1. **Переход — чистая функция** (`harness/state_machine.py`): `(pipeline, событие,
   контекст) → патч манифеста или отказ с кодом`. Одна реализация используется демоном,
   валидатором `manifest_check.py` и витриной (какие кнопки показывать).
2. **Владение полями манифеста.** `pipeline`, retries, heartbeat, session_id, verdict —
   пишет **только демон** (атомарно, как сейчас). `phase`, iteration_count, AC-статусы —
   **только сессия исполнителя** (как в v2). Коллизий нет по построению.
3. **Пауза не убивает прогон** (урок aif-handoff): флаг PAUSE вступает на ближайшей
   границе итерации — уже реализовано в v2, переиспользуется.

### 3.3 Демон-координатор (`harness/orchestrator.py`, stdlib)

Один демон обслуживает зарегистрированные воркспейсы (реестр `~/.sa-helper/workspaces.json`,
см. §3.6): для каждого — свой цикл и свой пул задач; задачи разных FNR одного воркспейса
идут в общем пуле (очередь DAG, последовательное исполнение).

Цикл (раз в N секунд + мгновенное пробуждение по mtime `.flags/` и `manifest.json`):

1. Прочитать манифест и флаги → вычислить события → применить переходы машины состояний
   (атомарная запись).
2. Если есть задача в статусе «нужна стадия X» и слот свободен (последовательное
   исполнение v2; параллель — позже через worktree-изоляцию, она уже есть) — запустить
   сессию стадии:
   `claude -p "<промпт стадии>" --output-format stream-json --verbose --permission-mode
   acceptEdits --max-turns <лимит>` в cwd целевого репо (worktree).
3. Стрим лога стадии в `.run/T<k>_<stage>.log` (+ last-event timestamp = heartbeat в
   `.run/T<k>.heartbeat`); финальный результат — в манифест/файлы артефактов.
4. Watchdog: heartbeat старше таймаута → убить дерево процессов (кроссплатформенный
   kill из runner.py уже есть) → задача в `blocked`, retry с backoff (лимит → `needs_human`).
5. Всё происходящее — append-only журнал `events.log` (`- [ts | daemon] событие`), он же
   feed витрины.

Сессии стадий — это **те же команды v2**, поданные в headless-режиме. Промпты стадий уже
написаны (файлы `.claude/commands/impl-*.md`); демон подставляет задачу и передаёт
`--resume <sid>` при повторных стадиях той же задачи, чтобы не потерять контекст.

### 3.4 Review-gate: структурированный вердикт и петля доработки

Ревьюер v2 уже пишет `reviews/T<k>.md` с вердиктом и находками `файл:строка`. Для
автоматизации вердикт дополняется машиночитаемым блоком в конце того же файла
(человек читает как раньше, демон парсит без LLM):

```markdown
## Verdict (machine-readable)
status: CHANGES_REQUESTED          # или APPROVED
blocking:
- id: b1 | file: src/.../DraftDbSchemaMigrationTest.java:42 | text: DROP SCHEMA без guard URL
- id: b2 | ...
advisory:
- id: a1 | ...
previous:
- b1: resolved                     # статус находок прошлой итерации (для closure_first)
- b2: still_blocking
```

Правила петли (переняты у aif-handoff, усилены нашим circuit breaker):

- находка = стабильный ID (hash текста) → видно, устранена ли именно она;
- стратегия **closure_first** (по умолчанию): доработка закрывает прежние находки; если
  после этого ревьюер нашёл *новые* блокирующие — петля останавливается, задача в
  `needs_human` (иначе ревьюер и исполнитель могут топтаться вечно);
- лимит итераций ревью — 3 (согласовано с circuit breaker v2) → `needs_human`;
- человек может в любой момент: вернуть сам (`A: request_changes` с комментарием —
  комментарий становится первичным заданием доработки) или дожать (`A: force_approve`).

### 3.5 Исполнитель: claude CLI headless

Один адаптер, интерфейс (шов на будущее):

```
run_stage(prompt, cwd, resume_sid=None, max_turns, timeout) -> StageResult(
    session_id, exit_code, transcript_path, result_text, usage)
```

- транспорт: `claude -p --output-format stream-json --verbose`; лог — JSONL в `.run/`;
- разрешения: `--permission-mode acceptEdits` + существующие allow/deny пилота
  (deny push и т.п.) в настройках воркспейса; опасные операции и так отрезаны хуками;
- лимиты: `--max-turns` и таймаут на стадию (аналог их `maxBudgetUsd`, но в токенах/времени);
- восстановление: после падения демона задача возобновляется `--resume <sid>`
  (или fresh session для rework — урок aif-handoff: доработка в старой сессии
  игнорирует новое задание, считая работу уже сделанной).

### 3.6 Витрина v2 (эволюция, не переписывание)

Существующий сервер (stdlib, SSE) дополняется:

- **Экран «Воркспейсы»** (входная точка, как «создать проект» в aif-handoff): добавляешь
  воркспейс — имя и путь к каталогу; реестр `~/.sa-helper/workspaces.json` общий для UI
  и демона. Из карточки воркспейса — список FNR и запуск демона; дальше конвейер едет сам.
- **Действия по задаче** (кнопки в карточке): Approve plan / Request changes (с окном
  комментария) / Retry / Pause–Resume / Force approve — каждая кнопка = файл события в
  `.flags/` (например `TASK_T4_REQUEST_CHANGES`), демон забирает. API уже умеет флаги —
  расширяется именование.
- **Живой лог стадии**: хвост `.run/T<k>_<stage>.log` по SSE — видно, что агент делает
  прямо сейчас (аналог их стрима, без React).
- **Чат задачи**: поле комментария уже есть; добавляется режим «спросить агента» —
  демон делает одноразовый `claude -p --resume <sid задачи>` с вопросом, ответ
  дописывается в `comments/T<k>.md` (журнал v2).
- Машина состояний подсказывает, какие кнопки активны (та же чистая функция).

### 3.7 Контракт команды `/impl-handoff` (вход → выход → дальше)

Формализует передачу «аналитика → конвейер» (сейчас это неявная часть `/impl-plan`):

- **Вход:** путь к СТ (`FNR_N/system_requirements_*.md`); опционально `--system` для
  одиночной системы.
- **Проверки входа (честный отказ):** FR-ID в метаданных задач; префиксы AC-ID;
  §2.5 «Затронутые системы и контракты»; системы есть в `workspaces.yaml`; критерии
  проверяемы тестом. Гэп-репорт и STOP при пробелах (как в пилоте FNR_8 — уже работает).
- **Выход:** `dossier.md`, `execution_plan.md` (DAG), `tasks/T*.md`, `manifest.json v3`
  (все задачи `pipeline=backlog`), первая задача — контрактная, если есть контракты.
- **Дальше:** человек читает план → `approve_plan` → демон ведёт сам. Выходной артефакт
  — PR-заготовки + verification_report (как в v2).

Отличие от текущего `/impl-plan`: (а) жёсткий машиночитаемый контракт входа —
«СТ подаётся в конвейер», а не «агент посмотрел и согласился»; (б) результат сразу
готов к автономному исполнению, без последующих ручных команд.

### 3.8 Что остаётся без изменений

runner.py (JSON-дайджесты), workspace_scan.py, хуки pre-commit/pre-push, Docker-команды
workspaces.yaml, пресеты стеков, рубрика ревью (rubric), примеры карточек/досье,
TDD-гейт и circuit breaker внутри `/impl-run`, изоляция worktree, правила трассируемости.
Манифест: схема расширяется (новые поля опциональны) — `manifest_check.py` принимает
и v2-, и v3-документы, чтобы пилотные артефакты не сломались.

### 4.1 Порция F — Story и бэклог (утверждена 2026-10-17)

Story = FNR (уже так устроено: СТ + harness-каталог). Добавляются функции входа и пополнения:

1. **Создание Story из витрины** (`POST /api/story`, режим `--workspace`): название + текст СТ
   (или путь) → каркас `FNR_<n>/` + флаг `HANDOFF` → демон запускает `/impl-handoff` headless.
   Gap-report по шлюзу готовности возвращается в витрину (`handoff_failed`).
2. **Ручной Task в Story**: payload-флаг `.flags/TASK_NEW_*.json` (title, system, description,
   depends_on, acceptance) → демон создаёт карточку + запись манифеста
   (`origin: manual`, `pipeline: BACKLOG`) и валидирует DAG. UI манифесты не пишет —
   только события (один писатель).
3. **Агентские предложения**: во время стадии агент добавляет задачу
   (`origin: agent`, `pipeline: PROPOSED`, честная пометка «внеплановая», если FR нет) →
   человек решает на витрине: **Принять в бэклог** (propose_accept → BACKLOG) или
   **Отклонить** (propose_reject → ABORTED). Объём работ расширяет только человек.
4. **Экран Stories (портфель)**: `--workspace`-режим витрины — список Stories с прогрессом,
   статусы handoff, переход к доске задачи.

Хранение (редакция v4, 2026-10-19): состояние — в SQLite `~/.sa-helper/harness.db`
(см. §5); файлы — только runtime-артефакты. python3 harness/db_migrate.py import —
переезд, export — снапшот.

### 4.2 Порция G — веб-приложение витрины (реализована 2026-10-17)

Витрина стала полноценным приложением: **бэкенд Python stdlib** (`harness/web/server.py`,
эволюция ui_server), **фронтенд React 18 + Vite + TypeScript** (`harness/web/frontend`,
собранный dist коммитится — Node нужен только для разработки). Хранение: с порции R2 —
БД (§5, редакция v4).

Реализовано (в порядке порций):
- G1: паритет текущих функций в React (портфель, канбан 8 колонок, список, панель задачи
  с вкладками, создание Story/Task); `/classic` — прежний UI как fallback.
- G2: usage — токены и стоимость сессий парсятся из result-событий stream-лога
  (accumulation по задаче, агрегат по Story); бейджи в портфеле и на карточках.
- G3: ⌘K-палитра (задачи/команды), фильтры доски, inline-создание Task в колонке
  бэклога, правка описания задачи (payload-флаг TASK_EDIT → манифест + карточка).
- G4: вкладка «История» (таймлайн событий из events.log), тосты «нужен человек»,

Развитие сверх G: журнал-канон comment-writing; чат задачи (--resume); живой лог
человекочитаемой хроникой. За кадром (осознанно): drag&drop, темы, участники,

## 5. Хранение: SQLite как источник истины (редакция v4, решение 2026-10-19;
ранее — «файлы, JSON и граница БД», решение 2026-10-17)

Решение 2026-10-17 («файлы — контракты агентов, БД только как проекция-аналитика»)
просуществовало до порции R миграции: конвейер вырос (мультипроект, steward, история),
файловый IO стал главным источником инцидентов (тень для защиты v3-полей, гонки
tmp+rename на Windows, рассинхрон карточка↔описание). Решение обращено:

- **Состояние машины и витрины** — SQLite `~/.sa-helper/harness.db` (WAL, stdlib):
  projects/stories/tasks (карточки — markdown-контент в БД), AC/зависимости/findings/
  вердикты — связанные таблицы; команды человека — очередь `commands` (бывшие `.flags/`);
  `events` — SSE-фид + таймлайн + аудит; sessions вместо pid/hb-файлов.
- **Markdown остаётся форматом контента**: карточки, СТ, досье, отчёты стадий —
  текст в колонках БД; снапшот в файлы — `db_migrate.py export` (бэкап/дифф/откат).
- **Файловые контракты агентов заменены адаптером** `harness/sahelper.py`: сессии
  читают контекст и пишут только свой домен (v2-поля, карточка по card_version,
  вердикты, документы); v3-домен и потребление команд — только демон.
- **Runtime остаётся файлами**: `.run/*.log` (stream-json стадий, путь в sessions),
  daemon.lock, ask.pending, вложения, git-worktree и хуки.
- Тень `pipeline_shadow.json` упразднена: колонка не может быть затёрта «чужим
  писателем» — UPDATE полевой. Роль аудита взял `events`.

Почему пересмотрено: тень и «один писатель файла» лечили симптомы документной модели
хранения; транзакционная модель снимает их целиком (Windows-гонки os.replace — в т.ч.),
а markdown сохранён как формат там, где он — контент.

## 6. Риски и ответы

| Риск | Ответ |
|---|---|
| Headless-сессии с широкими правами | Изоляция уже есть (worktree, ветки harness/*, хуки, deny push); разрешения — allow-лист пилота + `acceptEdits`; ничего вне `harness/*` не коммитится технически |
| Два писателя манифеста (демон + сессия) | Разделение владения полями (§3.2 п. 2); обе записи атомарны; `manifest_check` валидирует после каждой |
| Стоимость: конвейер жжёт токены без присмотра | Лимиты на стадию (`--max-turns`, таймаут), circuit breaker v2 внутри задачи, лимит ревью-петли, задачи `paused`/`scheduledAt`, журнал usage в events.log |
| Демон умер / машина перезагрузилась | Состояние целиком в файлах; восстановление — тот же цикл по манифесту + `--resume`; fencing по session_id |
| Windows (Git Bash) | stdlib Python + уже кроссплатформенный tree-kill; спавн CLI через shell-независимый запуск (паттерн aif-handoff для Windows учтён) |
| Возврат к v2 | Демон — надстройка: без запущенного демона контур v2 работает как раньше (команды те же); манифест обратно совместим |

## 7. Зафиксированные решения (2026-10-16…17)

1. **Имена статусов v3 — английские** (backlog, plan_ready, implementing, review, done,
   verified, blocked, needs_human, aborted); витрина показывает русские подписи, как
   сейчас.
2. **Один демон на воркспейс; воркспейсы регистрируются в UI.** Как в aif-handoff
   («создать проект» + путь к каталогу): в витрине есть экран «Воркспейсы» — добавляешь
   путь к воркспейсу, демон подхватывает его и ведёт все FNR этого воркспейса. Реестр —
   файл `~/.sa-helper/workspaces.json` (имя + путь, без проектной специфики), общий для
   UI-сервера и демона; UI и демон остаются универсальными, знание о системах — в
   `workspaces.yaml` самого воркспейса.
3. **Ревью — всегда отдельная чистая сессия** (как в пилоте); флаг `skip_review`
   существует на задачу, по умолчанию выключен.
