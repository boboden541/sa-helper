# AI-Harness. Task-tracker и конвейер

> **Версия:** 3 · **Статус:** в проектировании · **Обновлен:** 2026-10-24

Автоматизация реализации фичей: task-tracker (задачи, статусные модели, kanban) и автомат вокруг него — демон, ИИ-агенты, правила переходов. Компоненты системы: backend, frontend, база данных, демон.

## Оглавление

1. Типы задач и их устройство — концепция, общие поля, пять типов задач
2. Атрибуты задачи — название, приоритет, описание, теги, связи, даты, чеклисты
3. kanban-доска и список задач; переход по задачам
4. Процессы ревью и тестирования
5. Статусная модель по типам задач; правила зеркалирования истории
6. Работа с историей. ПСИ
7. Матрица прав переходов
8. Механика автомата
9. Код. Артефактный контракт разработки
10. Уведомления
11. Сущность "проект"
12. ИИ-чат помощник "Eve"
13. Настройки: status-flow, ИИ-провайдеры, пользователи-агенты; журнал настроек
14. Приложение. Исходный запрос

## Темы, которые хочу спроектировать

### Типы задач и их устройство

- Идейно я вижу, что неважно какая задача, это все должна быть одна таблица, разве что задача может иметь разный тип, от которого уже зависит логика. Например, могут быть обычные задачи на разработку, история, задача на тестирование, баг. И у каждой задачи со своим типом своя логика работы, свои ограничения, свои требования к ведению и пайплайну работы. Далее я попробую описать примерное видение того, как я это вижу. Ты можешь и должен дополнить описание, расширить функционал, предлагать свои идеи.

#### Главная концепция устройства сервиса

- Весь автомат построен на задачах. У каждой задачи в зависимости от ее типа свой status-flow. А весь автомат работает по заданным status-flow. То есть если нужно будет добавить новый тип задач, останется лишь "спроектировать" статусную модель и их переходы, дальше все заработает само по себе.

#### Общее для всех задач

- Есть идентификатор в базе данных
- Есть отображаемый код задачи (код проекта + порядковый номер задачи), отображается на UI, участвует в ссылках, в поиске и везде. Назовем это "Task-code". task-code должен быть уникальным
- Есть название
- Есть описание
- Есть статусная модель
- Есть возможность создать чеклист и вести его
- Есть теги (метки)
- Есть приоритет
- Есть возможность указать связь с другими задачами и задать тип связи
- Имеется дата создания задачи
- Имеется дата обновления задачи (последнее действие произведенное с любым параметром задачи)
- Декомпозиция. Обязательная концепция. Но способ декомпозиции у всех разный

#### Визуализация. Общие требования

Порядок полей следующий (полный набор; видимость блоков по типам — в таблице ниже):

1. Название (обязательно)
2. task-code отображается слева от названия (обязательно)
3. Приоритет задачи (обязательно)
4. Связанная история (опционально)
5. Теги (обязательно хотя бы один)
6. Дата создания (обязательно)
7. Дата обновления (обязательно)
8. Описание (обязательно)
9. Smart чек-лист разработчика (обязательно заполнен перед стартом разработки)
10. Связанные задачи (опционально, раскрывающийся блок)
11. Ревью (раскрывающийся блок)
11.1 Smart чек-лист (обязательно заполняется перед стартом процесса ревью)
11.2. Отчет о ревью (заполняется после процесса ревью, как отчет)
12. Тестирование (раскрывающийся блок)
12.1 Smart чек-лист (обязательно заполняется перед стартом процесса тестирование)
12.2 Отчет о тестировании (заполняется после процесса тестирования, как отчет)
13. Хроники (заполняется постепенно в процессе жизненного цикла задачи)
14. Комментарии (для дополнительной коммуникации между участниками процесса по работе над задачей)

#### Обычная задача (type = common_task)

- Самый стандартный и часто используемый объект. Обычно предназначен для реализации фичей по полному пайплайну: декомпозиция -> разработка -> ревью -> тестирование
- Данная задача может быть либо создана руками человека, либо появиться в рамках декомпозиции
- Имеется отдельное поле для заполнения (необязательное) для указания истории (type = story), в которую входит эта задача
- Эта задача по сути плановая деятельность команды, она должна пройти весь процесс разработки (декомпозиция по чеклисту, TDD-разработка, ревью, тестирование, конец)
- Возобновление процесса возможно несколькими способами: в случае возникновения замечания от ревьюера или тестировщика задача возвращается назад по статусу (разработка) и требует доработки
- Декомпозиция. До начала разработки создается чеклист с видимым планом работ. В процессе реализации в обязательном порядке ведется чеклист

#### История (type = story)

- Самый верхнеуровневый тип задач. Это по сути описание одной большой фичи, которую надо сделать
- Данная задача с типом story должна быть декомпозирована на обычные задачи (type = common_task) и у этих задач должно быть указано, в рамках какой истории они созданы в соответствующем поле
- Как только все задачи в рамках истории реализованы, история автоматически переходит на сквозное и полное тестирование функционала: правила M2–M3 перемещают саму историю (через qa ready), не создавая задачу на тестирование
- Если по итогам сквозного тестирования выявлены замечания (баги), тестировщик заводит их с привязкой к истории; баги попадают в бэклог, чтобы потом разработка планово взяла их в работу. Дальше история живет по правилам зеркалирования: блокировка по итогам тестирования (M4), автоматический возврат в in progress при возобновлении работы (M1), автоматическое повторное сквозное тестирование, когда все задачи/баги закрыты (M2–M3). Ручная разблокировка истории при этом не требуется: автоматика следует за дочерними задачами
- Декомпозиция. До начала разработки создается чеклист с видимым планом работ. В процессе реализации в обязательном порядке ведется чеклист. Цель декомпозиции истории – создание задач на разработку (type = common_task), понятных по объему работ. Идеально, чтобы каждая задача была понятна по объему и оценке. Задача должна быть тестируемой, иначе получим код "в воздухе", который тяжело проверить тестировщику.
- Статус истории отражает статусы всех дочерних задач и багов. Формально это правила зеркалирования ниже. Тестировать историю дальше невозможно, пока не закрыты найденные баги; процесс возобновляется сам, как только они завершены, и цикл может повториться (лимит числа циклов — "Механика автомата")

#### Правила зеркалирования истории

Автоматика истории — один источник правил, таблица ниже. "Дочерние" — задачи (common_task) и баги (bug), в которых указана эта история. Правила проверяются на каждом тике демона; каждое срабатывание пишется в хроники истории. Любое описание автоматики истории в других разделах — пересказ этой таблицы.

| # | Событие на дочерних задачах/багах | Переход истории | Кто запускает |
| --- | --- | --- | --- |
| M1 | Хотя бы одна дочерняя задача/баг взята в работу (in progress / in review / in testing) | → in progress (из to do или blocked) | Автомат |
| M2 | Все дочерние задачи/баги закрыты (done или canceled) | → qa ready (из in progress или blocked) | Автомат |
| M3 | История в qa ready | → in testing | Автомат |
| M4 | Тестирование или прогон ПСИ завершились замечаниями: все найденные баги заведены с привязкой к истории | → blocked (из in testing) | Автомат |
| M5 | Все дочерние задачи/баги заблокированы | → blocked (из in progress) | Автомат |
| M6 | Полный прогон ПСИ пройден, сквозное тестирование без замечаний | → done (из in testing) | Человек: подтверждает прогонявший |

- Пока история в to do, дочерних задач еще нет; в in progress история входит по M1
- M4 срабатывает по завершении тестирования, когда тестировщик завел все баги и составил отчет: сессия тестирования не обрывается на первом найденном баге
- Счетчик циклов доработки истории считается по срабатываниям M4; лимит и поведение при исчерпании — "Механика автомата"

#### Задача на тестирование (type = qa_task)

- Задача на тестирование функционала, она не подразумевает разработку или изменение кода. По сути это просто задача на ручное тестирование с прописанным чеклистом того, что будет делать тестировщик
- По окончании тестирования должен быть сформирован отчет по процессу тестирования (в формате ПСИ, чтобы любой человек даже без знания "техники" смог как по инструкции воспроизвести процесс).
- Если в рамках тестирования были зафиксированы баги (не соответствие требованиям), то тестировщик должен их завести и указать в рамках какой истории они созданы. Баги должны попадать в бэклог, чтобы потом разработка смогла планово взять их в работу. Сама задача переходит в статус done, на этом работа окончена.

#### Баг (type = bug)

- Это задача на фикс обнаруженного бага. Отдельный тип задачи.
- Декомпозиция. До начала разработки должен быть составлен чеклист по тому, как воспроизводить баг и как исправить. Как правило такие задачи делаются очень быстро.
- Разработка должна идти по чеклисту
- После разработки баг должен быть передан тестировщику для повторного тестирования. Код-ревью для таких задач не проводится.

#### Задача на анализ (type = analyse_task)

- Эта задача нацелена на проектирование технических решений и идей.
- Цель задачи аналитика: сформировать полную, понятную и непротиворечивую спецификацию, которая впоследствии будет передана в разработку
- Задача на анализ не живет в рамках истории, это просто задача на анализ. Скорее задача на анализ после завершения служит причиной для создания задачи с типом "история".
- pipeline задач на анализ примерно следующий: сбор требования, изыскания по текущему поведению, проектирование нескольких концептов решения, выбор одного самого лучшего, описание системных требований

### Указание названия, редактирование

- Каждая задача должна обладать названием, это обязательное поле.
- Название должно быть кратким и емким, понятным для быстрой идентификации задачи
- Чтобы изменить название задачи, нужно нажать на символ "карандаш", который отображается в конце текущего названия в карточке задачи
- Минимальная длина строки = 1; максимальная длина строки = 64 символа

### Приоритеты задач. Список, выбор, на что влияет

#### Общие требования

- Обязательное для заполнения поле

#### Список

- Возможные значения: low, medium, high, critical
- Визуальные отличия: low (тонкая голубая лычка вниз), medium (серый знак = ), high (красная лычка*вверх), critical (двойная красная лычка* вверх). *лычка = как у воинских погон в армии

#### Визуализация

- Отображается сразу после названия задачи (снизу)
- Отображение: в виде выпадающего списка
- по умолчанию значение приоритета не проставлено, нужно указать его самостоятельно
- отображение: в kanban-доске, в списке задач, в карточке задачи

#### на что влияет

- Отображение в порядке приоритета в kanban-доске (чем выше приоритет, тем выше задача и тем она важнее для реализации)
- баги имеют больший приоритет над задачами
- если имеется несколько задач с одинаковым приоритетом, то выше та, которая была создана раньше

### Описание задачи, отображение, редактирование (Два способа (визуальный с панелью, текстовый в формате markdown))

#### Общие требования

- Обязательное для заполнения поле
- Минимальная длина = 1; максимальная длина = 20 000 символов. Описание — первичный артефакт конвейера: им питаются декомпозиция, разработка, ревью и ПСИ. Если постановка не помещается — это сигнал декомпозировать, а не расширять поле
- Отображается под названием задачи, сразу после приоритета

#### Заполнение и редактирование описания

- Есть два способа для заполнения и редактирования описания.
- Выбрать режим можно при помощи кнопки-переключателя
**способ 1: визуальный режим**
- Имеется пространство для ввода текста
- Имеется панель инструментов (как в Word). Панель инструментов состоит из:
  - Форматирование текста (жирный, курсив, подчеркнутый, зачеркнутый)
  - Списки (маркированный, нумерованный)
  - Цитата
  - Ссылка
  - Изображение
  - Код
  - Таблица (добавить таблицу, добавить/удалить строку, добавить/удалить столбец, выделить колонку, выделить столбец)
- Саму панель для ввода можно менять по размеру, нужно просто потянуть курсором за правую нижнюю часть

**способ 2: текстовый режим**

- Имеется пространство для ввода текста
- Саму панель для ввода можно менять по размеру, нужно просто потянуть курсором за правую нижнюю часть
- Формат ввода текста это markdown. То есть в базе данных будет сохранен именно markdown формат.

#### Отображение

- Ранее сохраненный текст рендерится по канонам markdown
- При отображении можно также произвести редактирование описания, достаточно нажать на специальный значок (карандаш), который появляется при наведении курсора мыши на текст. При нажатии открывается режим редактирования, как бы вместо просмотра происходит плавный переход в режим редактирования. И уже там есть переключатель, чтобы сменить режим с визуального на текстовый.

### Указание тегов

#### Отображение

- Теги отображаются как хэштеги (с символом `#`)
- Теги отображаются под названием, сразу после приоритета, но выше описания
- Тегов может быть несколько: от 1 до 5
- Один из тегов обязательно должен быть: либо `by_human` (задачу создал человек), либо `by_ai` (задачу создал ИИ-агент)

#### Создание

- Для создания тега нужно нажать на поле ввода и начать вводить текст, а после нажать кнопку `enter`
- При вводе текста снизу появляется выпадающий список с уже имеющимися тегами, чтобы была возможность выбрать уже имеющийся тег, вместо создания дубля. Если подходящий тег не найден, то создается новый

#### Поиск

- Нечеткий поиск по имеющимся тегам, триграммный
- Пагинация не нужна, максимум можно показать 5 возможных подходящих тегов, чтобы уменьшить выборку, нужно указать больше символов, когда символы не введены, поиск не вызывается

#### Удаление тега из задачи, автоматическое общее удаление тега

- В конце строки, где указаны все теги должен быть символ "карандаш", нажатие на которые меняет стиль отображения на редактирование. В данном режиме около каждого тега в задаче есть крестик, нажатие на него удаляет у этой задачи конкретно этот тег. Если тег больше не привязан ни к одной из задач, то тогда тег в принципе удаляется из базы данных, чтобы её не захламлять

### Указание связи, типы связей, отображение связей, влияние связей на работу системы

#### Отображение

- Связи отображаются сразу под описанием
- Связи показываются в виде списка, в котором указывается: task-code, название этой задачи, тип связи

#### Типы связей

Возможны следующие типы связей

|Тип связи|Жесткость|Описание и влияние|
|---|---|---|
|do after|мягкая|Сделать после связанной задачи: связанную рекомендуется сделать первой. Взять задачу в работу можно; система показывает предупреждение и опускает её в сортировке очереди|
|do before|мягкая|Сделать до связанной задачи: рассматриваемую рекомендуется сделать первой. Для связанной задачи действует то же предупреждение|
|blocked by|жесткая|Заблокировано связанной задачей: взять задачу в работу нельзя, пока связанная не окажется в статусе done|
|blocks|жесткая|Данная задача блокирует связанную: связанную нельзя взять в работу, пока текущая не окажется в статусе done|

#### Указание связей

- Связи можно указать как при создании задачи, так и после ее создания в режиме редактирования
- При указании связи нужно заполнить два поля: сама задача, с которой нужна связь и тип связи
- При указании связанной задачи можно произвести поиск по названию, по task-code, ниже должен быть выпадающий поиск с результатами нечеткого поиска.
- Пример: если задача X связана с задачей Y с типом "do after", то у задачи Y автоматически должно отображаться "do before". Это можно и нужно сделать через одну запись в БД, просто на UI будет отображение нужного типа связи, чтобы не плодить записи в базе данных, которые тяжелее удалить в случае, если связь нужно будет удалить

#### Влияние связей

- Мягкие связи (do after / do before) влияют только на порядок и подсказки; жесткие (blocked by / blocks) — на саму возможность взятия в работу
- Правило едино для ручного взятия и для автомата: жесткая блокировка запрещает переход задачи в активный статус (in progress для разработки, in testing для тестирования)

### Дата создания и дата обновления задачи

#### Отображение

- Дата создания отображается сразу после тегов
- Дата обновления отображается сразу после даты создания
- формат дат: дата и время

#### Как заполняется

- Дата создания заполняется один раз при создании задачи и больше не меняется
- Дата обновления меняется каждый раз, когда меняется что-то в задаче: название, описание, статус, теги, перечень связанных задач, приоритет
- Каждое изменение пишется в хроники событием типа "поле" (см. "Хроники. Единый журнал задачи"): кто, когда, что менял. Само прошлое состояние (версию) хранить не надо

#### На что влияет

- Если у задач на доске одинаковый приоритет, то выше та, у которой старше дата создания, то есть она будет более приоритетной для взятия в работу

### Чеклисты

#### Общие требования

- Чеклист нужен для планирования своей работы над конкретной задачей или этапа работы над задачей (разработка, ревью, тестирование), чтобы декомпозировать свою работу на короткие и понятные шаги.
- Пока не закрыты пункты чеклиста соответствующего этапа перевести задачу дальше нельзя
- Взять задачу в работу на соответствующем этапе без созданного чеклиста нельзя
- Чеклист это отдельный объект в базе данных, но с разным типом (для разработчика, для ревьюера, для тестировщика).
- Чеклист это по сути именно сущность "строка" со своим типом. Есть два типа строк "заголовок", "пункт чеклиста".
- Строка "пункт чеклиста" обладает свойством статус.
- Строка "заголовок", это просто по своей сути заголовок для логического разделения пунктов чеклиста для реализации

#### Возможные статусы пунктов чеклиста

|Символ в текстовом режиме|Статус|Отображение|Описание|
|---|---|---|---|
|`-`|to do|серый|созданный пункт чеклиста, пункт еще не взят в работу|
|`~`|in progress|синий|данный пункт на данный момент находится в работе|
|`x`|closed|желтый|пункт чеклиста стал неактуальным|
|`+`|done|зеленый|пункт чеклиста реализован|
|`!`|failed|красный|пункт чеклиста не удается реализовать|

#### Создание и редактирование

Есть несколько способов для создания и редактирования пунктов чеклиста. Изначально в созданной задаче его нет. Но в блоке чеклиста есть два важных поля:

1. Строка для ввода
2. Карандаш для перехода в текстовый режим ввода

Два способа ведения чеклиста:

- Визуальный (об этом далее)
- Текстовый (об этом далее)

##### Визуальный

- Строка ввода и нажатие на клавишу "enter" это коммит одной строки в чеклист, далее таблицы:

| Вводимая строка | Описание вводимой сроки | Что должно быть | Пример |
| --- | --- | --- | --- |
| `#` | Если строка начинается с символа решетка и пробел | Заголовок первого уровня как в markdown | `# Heading 1` |
| `##` | Если строка начинается с двух решеток и пробела | Заголовок второго уровня как в markdown | `## Heading 2` |
| `###` | Если строка начинается с трех решеток и пробела | Заголовок третьего уровня как в markdown | `### Heading 3` |
| `####` | Если строка начинается с четырех решеток и пробела | Заголовок четвертого уровня как в markdown | `#### Heading 4` |
| `#####` | Если строка начинается с пяти решеток и пробела | Заголовок пятого уровня как в markdown | `##### Heading 5` |
| `пункт чеклиста` | Если строка не начинается с решеток | это пункт чеклиста (строка с типом пункт чеклиста, обладающая статусом) | `пункт чеклиста`; `пункт # чеклиста`; `пункт 123!@#` |

##### Текстовый

- Перейти в данный режим можно при помощи нажатия на символ карандаша. Нажатие на данный символ переключает режим создания/редактирования в текстовый, блок для визуализации работы с чеклистом переключается. Есть блок для ввода текста, видно нумерацию строк слева, как в IDE.
- Создание строк с типами "заголовок" и "пункт чеклиста" (в нужном статусе) регламентируется таблицами, описанными ранее

#### Просмотр чеклиста

- При визуализации выглядит, как: чекбокс, строковое значение (емкое описание этапа реализации), статус (одно из возможных значений)
- Заголовок может быть представлен разными уровнями — всего их пять.

#### Удаление пунктов чеклиста. Редактирование чеклиста

В визуальном режиме просмотра чеклиста должен быть реализован метод, который позволит удалить конкретную строку чеклиста.
Пример визуализации

| № Строки | Пример Строки чеклиста (заголовок/пункт чеклиста) | Статус | Крестик |
| --- | --- | --- | --- |
| 1 | `# Работа с базой данных` (в визуальном режиме это будет заголовок первого уровня, но в текстовом будет именно такая строка) | Статуса у заголовков нет | Имеется крестик для удаления данной строки |
| 2 | `Произвести миграцию базы данных` | Есть статус | Имеется крестик для удаления данной строки |
| 3 | `Накатить исторический массив данных` | Есть статус | Имеется крестик для удаления данной строки |

### kanban-доска и список задач

#### Визуализация и функционал

- На экране расположены колонки. Отдельный этап работы = один статус = одна отдельная колонка.
- Фильтры: по названию (нечеткий поиск), по типу задачи.
- Задача с типом "История" (type = story) визуализируется горизонтально сквозь всю kanban-доску. Задачи, которые входят в эту историю расположены по сути под этой истории и разложены по колонкам. Саму историю на доске можно "свернуть", сворачивая историю, видно историю в свернутом режиме, но задачи, входящие в эту историю, скрываются
- Есть переключатель "Доска | Список". При нажатии на режим "Доска" видно kanban-доску; при нажатии на режиме "Список" все-все задачи (всех типов) представлены в виде списка
- Имеется отдельно строка для поиска задач (нечеткий поиск по названию или task-code). Нашел задачу -> нажал на нее -> Перешел на новый экран просмотра конкретной задачи
- DnD для ручного перемещения задачи по статусу. В процессе перемещения заранее подсвечиваются колонки, куда система разрешает переместить задачу.

### Процесс ревью

- Задача поступает на ревью. Ревьюеру передается отчет по произведенной реализации и кодовая база (что логично)
- Ревьюер до старта работ (на статусе review ready) заполняет чеклист того, что он будет проверять и как будет проверять
- По завершению ревью формируется отчет. Если замечаний нет, то задача передается на ручное тестирование. Если замечания есть, то ревьюер в разделе "Smart чек-лист разработчика" дополняет чеклист новыми пунктами, которые нужно реализовать. У разработчика будет как фактура для работы: отчет ревьюера + декомпозиция в smart чек-лист.

### Процесс тестирования

- Задача поступает на тестирование. Тестировщику передаются как отчет от разработчика и его чеклист, отчет от ревьюера и его чеклист и верхнеуровневые абстракции проекта доступные человеку (API методы, таблицы, интерфейс).
- Тестировщик до старта работ заполняет чеклист того, что он будет проверять и как будет проверять
- По завершению тестирования формируется отчет. Если замечаний нет, то задача завершается – все реализован и работает правильно. Если замечания есть, что-то не работает или работает не по требованиям, то это также прописывается в отчете. Затем тестировщик в разделе "Smart чек-лист разработчика" дополняет чеклист новыми пунктами, которые нужно реализовать. У разработчика будет как фактура для работы: отчет тестировщика + декомпозиция в smart чек-лист.

### Переход по задачам

#### Визуализация

- Задачи могут существовать в рамках истории (опционально), могут быть связаны между собой и отображаются на доске, в списке, в поиске
- Везде, где фигурирует компонент задачи, отображается её task-code; нажатие открывает детальное представление задачи. Задача может открываться и в side-page — и там есть task-code и переход на детальный просмотр

### Работа с пользователями. Автор и Исполнитель задачи

#### Основы

- В функционал по указанию автора и исполнителя кроется одна база – это по сути работа с пользователями. Это по сути отношения пользователя к конкретной задаче.
- Пользователя нужно уметь создавать. Пользователи могут быть двух типов: человек и ИИ-агент. Базово пользователь-человек обязательно должен быть. И при создании пользователя нужно указать, что за ИИ-агента ты создаешь, как он должен работать, по какому навыку, за какой этап он отвечает (на каком статусе он вызывается).

#### Визуализация

##### Создание пользователей

- Об этом подробнее в разделе с описанием "Раздел настройки"

##### Автор и Исполнитель

- Если задача создается через интерфейс, то автор у задачи "человек". Исполнитель назначает автоматически в зависимости от типа задачи и ее жизненного цикла в рамках статусов
- Если задача создается ИИ-агентом, то автор соответствующий ИИ-агент. Пример: Я создаю историю (я автор), задача в статусе "предложено". Далее задачу берет на себя соответствующий ИИ-агент (он теперь исполнитель). Далее он декомпозирует ее и создает задачи (он теперь автор). Далее задачу берет разработчик (он теперь исполнитель), что-то делает и снимает с себя задачу, переводя ее в статус ревью. ИИ-агент берет задачу в статусе соответствующем ревью, назначает себя исполнителем. Аналогично с тестированием.

### Хроники. Единый журнал задачи

#### Назначение хроник

- Хроники — единственный журнал жизни задачи и единственный ответ на вопрос "что с ней происходило". Один вопрос — одно место
- Принцип: одно событие — одна запись. Отдельного "лога изменений" нет — изменения полей это тип события в хрониках
- Каждая запись: дата и время, автор (человек / ИИ-агент / Eve / автомат с указанием правила), тип события, человекочитаемая формулировка. У сложных записей — раскрывающийся технический блок (те же два слоя языка, что в ошибках провайдеров)

#### Типы событий

| Тип | Кто пишет | Примеры |
| --- | --- | --- |
| поле | человек, Eve | "описание изменено", "тег добавлен" |
| переход | человек / агент / автомат | "in review → qa ready"; у автомата — с номером правила (M4) |
| форс | человек | причина обязательна, пометка "ручное вмешательство" |
| агент | демон | "Ревьюер, попытка 2", "heartbeat пропал", "ошибка провайдера" |
| запрет | система | "агент попытался перейти из чужого статуса — отклонено" |
| ПСИ | составитель, тестировщик | "составлен ПСИ v2", "прогон: 18/20, 2 не пройдено" |
| баг | тестировщик / агент | "заведен SA-57 по пункту 12" |

- "Лог изменений" как отдельный журнал не существует: в интерфейсе хроник это предустановленный фильтр по типу "поле"
- Причина указывается только там, где было решение: форс-переход, возврат на доработку. Для остальных событий причина = сам тип: человек не пишет пояснение к смене тега
- Старое значение поля не хранится — фиксируется факт изменения

#### Два слоя хранения

- В хрониках всегда живет легкая строка-событие; тяжелое содержимое (промты, мысли агента) хранится отдельно со ссылкой из записи и смотрится по клику
- Тяжелое содержимое хранится с настраиваемым сроком (по умолчанию 90 дней), легкие записи — всегда
- Секреты (API-ключи и токены) не попадают в хроники никогда — только маски

### Статусная модель в зависимости от типа задачи

#### Типы задач и возможные статусы

**Общее поведение**

- Принцип модерации: pending — только для предложений, которые человек еще не проверял. Если человек уже подтвердил создание своим действием, задача минует pending
- Задача, созданная через интерфейс как предложение, попадает в статус pending. ИИ-агент и демон не берут такие задачи в работу: апрув переводит задачу в backlog, отклонение — в canceled. Выбрать другой статус при создании нельзя
- Минуют pending (человек уже высказался):
  - подзадачи истории, созданные ИИ-агентом в рамках декомпозиции, — модерация выполнена апрувом самой истории
  - баги, заведенные на статусе in testing истории или qa_task (тестировщиком — человеком или агентом), — модерация состоялась фактом тестирования. Механическое правило: тип bug + родитель в in testing в момент создания → сразу to do
  - задачи, подтвержденные "да" в чате Eve, — подтверждение и есть модерация, факт пишется в хроники
- Баг, созданный через интерфейс вне тестирования (человек заметил проблему), идет в pending — это полноценный триаж с подтверждением воспроизводимости

**История (type = story)**

| Статус | Описание статуса | Что происходит на этом статусе (этапе) | Возможные переходы | Как происходит переход |
| --- | --- | --- | --- | --- |
| pending | Предлагаемая задача | После создания истории она попадает на рассмотрения для ручной модерации и ожидает апрува, чтобы быть взятой в работу | backlog, canceled | Ручное вмешательство через интерфейс |
| backlog | Бэклог | Сюда попадает промодерированная задача. | to do, canceled | Автомат и ручное вмешательство для отмены задачи |
| to do | Готово к декомпозиции для дальнейшего взятия в работу | При попадании истории в этот статус, ИИ-агент должен декомпозировать эту задачу и создать задачи на разработку (type = common_task) | backlog, canceled, in progress, blocked | Автоматически или ручное вмешательство через интерфейс |
| in progress | Над задачами в рамках истории ведется работа | Статус истории зеркалит статус дочерних задач и багов: как только хотя бы одна задача/баг перешли в работу, история автоматически переходит в этот статус (M1) | qa ready, blocked, canceled | Автоматически: в qa ready — все дочерние задачи/баги закрыты (M2); в blocked — все дочерние заблокированы (M5); в canceled — ручное вмешательство |
| qa ready | Это своего рода бэклог для тестирования | На этом этапе история ждет автоперехода на сквозное тестирование | in testing, canceled, blocked | Автоматически: → in testing (M3); в canceled — ручное вмешательство |

### Работа с историей. ПСИ

#### Назначение и место процесса

- ПСИ (приёмо-сдаточные испытания) — финальная проверка истории: документ, по которому любой человек без знания "техники" воспроизводит действия и сверяет фактический результат с ожидаемым
- Процесс запускается, когда история попадает на тестирование (in testing) — то есть когда все плановые задачи истории закрыты
- На статусе in testing объединяются три работы: сквозное тестирование функционала, составление документа ПСИ и прогон ПСИ

#### Как история попадает в тестирование

- История находится в in progress, пока хотя бы одна её задача/баг в работе: разработка, ревью или тестирование (M1)
- Как только все плановые задачи истории закрыты, история автоматически переходит в qa ready, а оттуда — на сквозное тестирование (M2–M3)
- Эталон для проверки: постановка истории и требования её задач — с ними сверяется фактическая реализация

#### Сквозное тестирование

- Тестировщик проверяет весь функционал истории целиком, с учетом постановки и фактической реализации: соответствие требованиям, полнота реализации, работоспособность функционала, взаимодействие задач истории между собой (сквозные сценарии)
- Найденные несоответствия требованиям, недоработки и неработоспособность фиксируются как баги с привязкой к истории; баги попадают в бэклог

#### Документ ПСИ

- ПСИ — структурированный документ в карточке истории (раскрывающийся блок "ПСИ"). У документа есть версии: ПСИ v1, v2...
- Каждый пункт документа — пара "элементарное действие + ожидаемый результат":
  - элементарное действие — одно действие человека, которое можно воспроизвести руками (нажать, ввести, открыть)
  - ожидаемый результат — наблюдаемая реакция системы, сформулированная человекочитаемо
- Структура документа:

| Элемент | Описание |
| --- | --- |
| Шапка | история (task-code и название), версия документа, дата составления, автор |
| Разделы | функциональные блоки истории — заголовки (как в чеклисте) |
| Пункт | №, действие, ожидаемый результат, статус прогона (не прогонялся / пройден / не пройден), фактический результат |

- Пункт ПСИ — строка чеклиста особого типа: статусы чеклиста переиспользуются — "не прогонялся" = to do, "пройден" = done, "не пройден" = failed
- Требование к качеству: полное покрытие функционала истории; каждое действие элементарно; каждый ожидаемый результат проверяем человеком по инструкции

#### Скилл "ПСИ-составитель"

- Документ формирует отдельный агент со скиллом "ПСИ-составитель" (предустановленный; назначается на статус in testing истории)
- Скилл по рекомендуемой структуре (см. "Скилл. Из чего состоит"):
  - роль: составляет документ ПСИ по истории
  - процедура: прочитать постановку истории → собрать чеклисты и отчеты всех задач истории → декомпозировать функционал до элементарных действий → для каждого действия выписать ожидаемый результат из требований → собрать документ и присвоить версию
  - критерии качества: действие элементарно и воспроизводимо руками; ожидаемый результат наблюдаем и человекочитаем; покрытие функционала полное; ожидания не приукрашены против постановки
  - формат результата: новая версия документа ПСИ в карточке истории
  - ограничения: не менять требования и не улучшать ожидаемые результаты против постановки
- Составление ПСИ и сквозное тестирование идут на статусе in testing параллельно (режим "параллельно", см. матрицу назначений)

#### Прогон ПСИ

- Прогон — воспроизведение пунктов документа человеком (тестировщиком или принимающим): выполнить действие → сверить фактический результат с ожидаемым → отметить пройден/не пройден и вписать фактический результат
- Пункт не пройден (ожидаемый результат не совпал с фактическим) → по пункту заводится баг: в описании — пункт ПСИ (действие, ожидаемый результат, фактический результат) и история, к которой он относится
- Итог прогона — протокол: дата, кто прогонял, версия ПСИ, пункты со статусами. Прогонов может быть сколько угодно — каждый пишет свой протокол, предыдущие не затираются
- Разделение: документ ПСИ и протоколы живут в карточке истории как документы; события о них (составлен, начат прогон, пункт не пройден) пишутся в хроники типом "ПСИ"

#### Баги и цикл доработки

- Баги, найденные сквозным тестированием и прогоном ПСИ, обрабатываются одинаково: заводятся с привязкой к истории и попадают в бэклог
- Если найден хотя бы один баг, история не может быть закрыта: по завершении тестирования с замечаниями история переходит в blocked (M4), а как только по багам начинается работа — обратно в in progress (M1)
- После реализации и закрытия всех багов история снова автоматически попадает на тестирование (M2–M3), и цикл повторяется: сквозное тестирование затронутого функционала, при изменении функционала — новая версия ПСИ, затем полный повторный прогон. Число циклов ограничено (см. "Механика автомата")

#### Идемпотентность процесса

Процесс можно повторять; каждое повторение начинается из чистого состояния и завершается предсказуемым результатом — в том числе blocked "цикл не сходится", если исчерпан лимит циклов доработки (см. "Механика автомата"):

- новое вхождение истории в in testing всегда начинает цикл заново: статусы пунктов ПСИ сбрасываются в "не прогонялся", старые протоколы сохраняются в истории документа
- ПСИ перегенерируется в новую версию только если функционал изменился; если нет — документ переиспользуется как есть
- повторный цикл не плодит дублей: баг по пункту, который уже заведен и не закрыт, не создается заново — пункт ПСИ связывается с существующим багом
- зачет истории ровно один: последний полный прогон, в котором все пункты пройдены и сквозное тестирование без замечаний, переводит историю в done (M6: подтверждение прогонявшего — человека)

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Статусная модель (story) | Переходы in progress / qa ready / in testing / blocked — здесь их смысл для ПСИ, там — формальные правила |
| Пользователи-агенты | Агент "ПСИ-составитель" и режим "параллельно" на статусе in testing истории |
| Чеклисты | Пункт ПСИ — строка чеклиста особого типа со статусами to do / done / failed |
| Задача на тестирование (qa_task) | Отчет qa_task составляется в том же формате ПСИ, но по одной задаче, а не по истории |
| Хроники | Составление ПСИ, прогоны и заведение багов пишутся в хроники истории |

### Матрица прав переходов

#### Назначение

- Раздел отвечает на вопрос "кто может перевести задачу из статуса в статус". Субъектов перехода три: человек, ИИ-агент и автомат (система)
- Принцип разделения: человек принимает решения, агент делает работу на своем статусе, автомат исполняет детерминированные правила, не требующие интеллекта
- Матрица — правила по умолчанию для всех flow. В редакторе перехода поле "Кто запускает" наследует отсюда; в конкретном flow права можно сузить, расширить — нет

#### Три субъекта переходов

| Субъект | Кто это | Как действует |
| --- | --- | --- |
| Человек | Пользователь через интерфейс: DnD на доске, кнопки в карточке | Решение принимает сам; форс-переходы доступны только ему |
| ИИ-агент | Бот-пользователь, назначенный на статус (матрица назначений) | Действует строго в рамках процедуры своего скилла и переходов своего статуса |
| Автомат | Система: демон и правила конфигурации | Выполняет только детерминированные правила: агрегация статусов истории, авто-движение конвейера; ни одного решения "по разумению" |

#### Права субъектов

| Возможность | Человек | ИИ-агент | Автомат |
| --- | --- | --- | --- |
| Валидный переход по flow | Любой валидный переход | Только из своего статуса и только переходы с исполнителем-агентом | Только правила с пометкой "Автоматически" |
| Форс-переход: в любой статус, из любого (в том числе из done и canceled) | Да, с обязательной причиной | Нет | Нет |
| Обход чеклист-гейта | Только в составе форс-перехода | Нет: гейт для агента жесткий | Нет |
| Взятие задачи в работу | Да | Да, на своем статусе | Да: подбирает исполнителя по матрице назначений |
| Возврат на доработку (переход назад + пункты в чеклист разработчика) | Да | Да: ревьюер и тестировщик на своих статусах | Нет |
| Отмена задачи (canceled) | Да | Нет | Нет |
| Успешное завершение (→ done) | Да | Да: только валидным переходом из своего статуса — успешное закрытие своего этапа | Нет |
| Смена исполнителя | Да | Нет | Да: только при замещении (исполнитель не смог) |
| Редактирование матрицы и flow | Да | Нет | Нет |

#### Мостик к таблицам статусной модели

Формулировки колонки "Как происходит переход" в статусных таблицах отображаются на субъектов так:

| Формулировка | Кто выполняет |
| --- | --- |
| «Автоматически» | Автомат (детерминированное правило) |
| «Автоматом или ручное вмешательство» | Агент своего статуса или человек |
| «Ручное вмешательство через интерфейс», «Ручное вмешательство» | Только человек |
| «При ручном вмешательстве можно вернуть в любой статус» | Только человек, форс-переход с причиной |
| «автомат» (например, to do у common_task) | Инициатор — автомат (демон запускает агента), исполнитель перехода — агент своего статуса |

#### Форс-переход

- Форс-переход — единственный способ: вернуть задачу из done или canceled; перевести задачу в статус, не предусмотренный переходами; уйти дальше с незакрытым чеклистом
- Только человек, причина обязательна: без причины система переход не выполнит
- Каждый форс — одна запись в хроники задачи: тип "форс", пометка "ручное вмешательство", кто, откуда → куда, причина обязательна
- Агентам и автомату форс недоступен технически, а не "по договоренности"

#### Запреты агентов

Агент не может — система отклоняет попытку и пишет об этом в хроники задачи:

- выполнять переходы со статусов, на которые он не назначен
- переводить задачи в canceled и возвращать из терминальных статусов (done, canceled)
- переводить в done иначе, чем успешным завершением своего этапа: разрешено только валидное ребро "свой статус → done" его flow
- обходить гейты чеклистов и переходить вне разрешенных переходов
- назначать и снимать других исполнителей
- работать с задачами, на чьих статусах он не назначен (в том числе других типов)

Повторные нарушения прав — перевод задачи в blocked по правилам механики автомата.

#### Гарантии автомата

- Каждое правило автомата конфигурируемо: по записи в хрониках всегда можно сказать, какое правило сработало
- Автомат не выполняет ни одного перехода вне своих правил — у него нет "инициативы"
- Каждое срабатывание правила пишется в хроники задачи с указанием правила

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Статусная модель | Колонка "Как происходит переход" отображается на субъектов через мостик |
| Пользователи-агенты | Какие статусы закреплены за агентом — из матрицы назначений |
| Создание и редактирование kanban-status-flow | Поле перехода "Кто запускает" наследует из матрицы; сузить можно, расширить нет |
| Механика автомата | Как технически запускаются агенты и правила автомата; поведение при ошибках |
| Хроники | Все переходы, форсы и отклоненные попытки пишутся в хроники |

### Механика автомата

#### Назначение

- Раздел отвечает на вопросы "когда запускается работа" и "что происходит, когда работа не получается". Матрица прав сказала "кто", статусная модель — "куда", здесь — "когда и как технически"
- Сердце автомата — демон: фоновый процесс, который циклически обходит базу задач и в зависимости от статуса задачи запускает нужного агента
- Триггер запуска — наличие статуса: задача попала в статус с назначенным ИИ-агентом — демон её подхватывает. Никаких скрытых событий: состояние конвейера всегда можно объяснить статусами задач

#### Демон. Цикл работы

- Шаг 1. Сканирование: демон каждые N секунд (тик) ищет задачи "готовые к работе": статус, на котором работает ИИ-агент; исполнитель не назначен (или резерв снят); задача не в blocked
- Шаг 2. Выбор по приоритету: из готовых задач демон берет по правилам раздела "Приоритеты" (critical выше high, баги выше задач, при равенстве — старше по дате создания)
- Шаг 3. Резервирование и запуск: демон атомарно помечает задачу "в работе у агента X (начато ...)" и запускает агента со скиллом и контекстом задачи
- Шаг 4. Завершение: агент отчитывается, демон применяет переход (проверяет права по матрице и гейты) и снимает резерв. Правила автомата (агрегация статусов историй) пересчитываются на каждом тике
- Человек не ждет демона: он может работать с задачей параллельно

#### Защита от двойного взятия

- Резервирование атомарно: две копии демона или два агента физически не могут пометить одну задачу — пометка одна
- Heartbeat: работающий агент отмечается каждые M секунд. Heartbeat пропал (процесс умер, контейнер упал) → резерв снимается, задача возвращается в очередь, попытка считается неудачной
- Пометка "в работе у агента" видна в интерфейсе: человек видит, кто и сколько уже работает

#### Ручное действие старше работы агента

- Если человек вмешивается, пока агент работает (переводит задачу, форсит, отменяет), работа агента немедленно прекращается: резерв снимается, агент получает сигнал "задача больше не твоя"
- Незавершенный результат агента не применяется; факт прерванной работы пишется в хроники

#### Таймауты и повторы (ретраи)

Все лимиты настраиваемые. По умолчанию:

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| Тик демона | 30 сек | как часто сканируется база |
| Таймаут старта | 5 мин | агент не подал признаков жизни после запуска |
| Таймаут работы | 30 мин | максимальная длительность одной попытки (переопределяется на статусе: тяжелые статусы — дольше) |
| Попыток на статус | 3 | сколько раз демон перезапускает агента на той же задаче в том же статусе |
| Пауза между попытками | 1 → 5 → 15 мин | растущая пауза, чтобы не долбить упавшего провайдера |
| Heartbeat | 30 сек | интервал маркера живости агента |

- Счетчик попыток привязан к статусу и сбрасывается, когда задача заново входит в этот статус: каждый новый цикл — с чистого состояния
- Неудачная попытка — запись в хроники: причина, номер попытки, когда будет следующая

#### Поведение при ошибке

- Попытка не удалась (ошибка провайдера, таймаут, сбой) → ретрай по расписанию пауз
- Попытки исчерпаны → задача автоматически переходит в blocked "требуется участие человека". В хроники пишется: причина последней ошибки, число попыток, что проверит человек
- Возврат из blocked: человек устраняет причину и переводит задачу назад в статус — счетчик попыток чист, демон снова берет задачу
- Режим замещения: если на статусе несколько агентов, при неудаче задача передается следующему по списку — и только после исчерпания списка идут ретраи и blocked
- Массовый отказ (несколько задач подряд падают на одном подключении к ИИ) → демон приостанавливает конвейер по этому подключению и показывает в интерфейсе предупреждение "провайдер недоступен"; задачи ждут, а не блокируются по одной

#### Защита от бесконечных циклов

- Ретраи ограничены (см. таблицу) — бесконечного перезапуска нет
- Возвраты на доработку (ревью → разработка, тестирование → разработка) считаются на задаче; циклы доработки истории — по срабатываниям правила M4 ("Правила зеркалирования истории"). Превышен лимит (по умолчанию 5) → автоматический blocked с формулировкой "цикл не сходится, нужно участие человека"
- Любой автоматический blocked — вход в статус, где решения принимает только человек: демон не пытается сам распутать цикл

#### Наблюдаемость

- В хроники задачи пишется всё: запуск агента, сбои heartbeat, ошибки с номером попытки, примененные переходы, автоматические blocked
- Экран "очередь автомата" в настройках — снимок "сейчас", а не журнал: какие задачи в работе у агентов, сколько попыток, что ждет ретрая, что заблокировано. Строится из состояний задач, собственного журнала не ведет — его история это и есть хроники

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Матрица прав переходов | Демон применяет переходы агентов только с правами агента; человек может перехватить задачу в любой момент |
| Пользователи-агенты | Порядок замещения берется из матрицы назначений |
| Подключение ИИ-провайдеров и моделей | Ошибки соединения — самая частая причина ретраев; массовый отказ приостанавливает конвейер по подключению |
| Работа с историей. ПСИ | Счетчик возвратов ограничивает и циклы доработки истории |
| Хроники | Полная запись работы автомата по каждой задаче |
| Код. Артефактный контракт разработки | Результат работы агента на статусе — изменения в ветке задачи и отчеты |
| Уведомления | Состояния "система ждет человека" порождают уведомления |

### Код. Артефактный контракт разработки

#### Назначение контракта

- Раздел отвечает на вопрос "что агент оставляет после себя в репозитории проекта и как результаты этапов передаются дальше"
- Принцип: одна задача — одна ветка. Все правки изолированы в ветке задачи; параллельные задачи проекта не мешают друг другу ни на диске, ни в истории

#### Ветка и worktree задачи

- Ветка `task/<task-code>` создается при первом входе задачи в in progress от базовой ветки проекта (по умолчанию main, задается в настройках проекта) и живет до done или canceled
- Работа агента ведется в отдельном worktree — изолированной рабочей копии ветки задачи; основная рабочая копия проекта агентам не принадлежит
- Базовые ветки защищены от агентов технически: агент пишет только в свою ветку `task/<task-code>`
- Правило одного писателя: коммитить в ветку задачи может только один активный агент. Параллельные исполнители допустимы на читающих статусах (ревью, тестирование) — они читают диф и код, но не пишут
- Возвраты на доработку продолжаются в той же ветке задачи
- Слияние: переход задачи в done выполняется после того, как автомат слил ветку задачи в базовую ветку. Конфликт слияния → задача уходит в blocked с формулировкой "конфликт слияния"; человек распутывает ветки и переводит задачу дальше — автомат повторяет слияние
- Для задач без кода (qa_task, analyse_task) ветка не создается: результат — документы в карточке задачи

#### Артефакты этапов

| Этап | Артефакт | Что в нем |
| --- | --- | --- |
| in progress | коммиты в ветке задачи + отчет разработчика | что сделано; как проверялось (тесты, TDD-цикл) |
| review ready → in review | диф ветки + чеклист ревьюера | изменения относительно базовой ветки; план проверки |
| in review | отчет о ревью | см. "Отчет о ревью" |
| qa ready → in testing | чеклист тестирования | что и как проверяет тестировщик |
| in testing | отчет о тестировании | см. "Отчет о тестировании" |

#### Отчет о ревью

- Структура как у документа ПСИ — шапка, разделы, пункты:
  - шапка: task-code, дата, ревьюер
  - раздел: функциональный блок изменений (заголовок)
  - пункт: проверка из чеклиста ревьюера + вердикт (пройдено / замечание) + описание замечания человекочитаемым языком
- Каждое замечание из отчета дублируется новым пунктом в smart чек-листе разработчика: отчет объясняет, чеклист декомпозирует

#### Отчет о тестировании

- Структура та же: шапка (task-code, дата, тестировщик), разделы, пункт — шаг из чеклиста тестирования + статус (пройден / не пройден) + фактический результат
- Пункт "не пройден" → заводится баг: действие, ожидаемый результат, фактический результат, привязка к задаче/истории
- Для qa_task отчет составляется в формате ПСИ (см. "Работа с историей. ПСИ")

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Сущность "проект" | Путь и базовая ветка проекта — основа веток задач |
| Механика автомата | Слияние ветки после done — правило автомата; конфликт слияния — blocked |
| Процесс ревью | Ревьюеру передается диф ветки и отчет разработчика |
| Процесс тестирования | Тестировщику передаются диф, отчеты разработки и ревью |
| Правила зеркалирования истории | done дочерней задачи — часть условий M2 |

### Уведомления

#### Назначение уведомлений

- Система не имеет права молчать, когда ждет человека. Уведомление — это "система ждет тебя": событие конвейера, требующее человеческого действия или решения
- Контракт событий отделен от каналов доставки: сначала "что и кому", каналы подключаются поверх без изменения контракта

#### Контракт событий

| Событие | Кому | Суть формулировки |
| --- | --- | --- |
| Задача создана через интерфейс (pending) | людям проекта | задача ждет модерации: апрув или отклонение |
| Задача в blocked (любая причина) | автору задачи | что случилось и что проверит человек |
| "Цикл не сходится", "конфликт слияния" | автору задачи | автомат перестал справляться, нужно решение |
| "Провайдер недоступен", "путь проекта недоступен" | людям проекта | конвейер приостановлен, причина и что сделать |
| На статусе нет назначенного агента | людям проекта | задачи статуса автоматически встанут в blocked |
| Задача ждет ревью (review ready) | ревьюеру статуса, если назначен человек | работа готова к проверке |
| Задача ждет тестирования (qa ready, in testing) | тестировщику статуса, если назначен человек | работа готова к проверке |
| История на сквозном тестировании | тестировщику статуса | история готова к ПСИ |
| Задача закрыта (done) | автору задачи | результат готов |

- Правило полноты: любое состояние "система ждет человека" обязано быть в этой таблице. Новый статус или новая причина blocked без события — ошибка дизайна, а не "просто нет уведомления"
- Уведомление исчезает, когда состояние разрешилось (задача вышла из blocked, дождалась ревью): список показывает только актуальное

#### Канал

- В этой версии канал один: колокольчик в интерфейсе со счетчиком; клик открывает список уведомлений, клик по уведомлению — переход к задаче
- Формулировки человекочитаемы без знания "техники" (те же два слоя языка, что в ошибках провайдеров): формулировка + раскрывающийся технический блок
- Внешние каналы (почта, мессенджеры) и доставка через Eve — перспектива; контракт событий от них не зависит

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Матрица прав переходов | События — про состояния, где решение за человеком |
| Механика автомата | Источник автоматических событий: blocked, лимиты, недоступность |
| Хроники | Событие всегда дублируется записью в хроники: уведомление — указатель, хроника — журнал |
| ИИ-чат помощник "Eve" | Перспектива: Eve доставляет уведомления в чат |

### Сущность "проект"

#### Назначение

- Проект — рабочее пространство, в рамках которого живут задачи: репозиторий или папка мультирепозитория на диске, где производятся доработки
- Проект дает задачам человекочитаемые адреса: task-code = мнемоника проекта + дефис + порядковый номер (например, FNR-11, SA-1). task-code — абстракция для взаимодействия человека с задачей вместо идентификатора базы данных
- На kanban-доске можно управлять несколькими проектами сразу

#### Проект. Поля

| Поле | Описание | Ограничения |
| --- | --- | --- |
| Название | Отображаемое имя проекта | 1–64 символа; меняется свободно (переименование) |
| Мнемоника | Краткий код для task-code: латинские буквы верхнего регистра и цифры | 2–10 символов; уникальна среди всех проектов; после создания не меняется |
| Путь на диске | Полный абсолютный путь до директории: одиночный репозиторий или папка мультирепозитория | путь должен существовать и быть доступен на запись; проверяется при создании и изменении |
| Базовая ветка | Ветка репозитория, от которой создаются ветки задач и в которую сливается результат | по умолчанию main; меняется свободно, влияет только на новые ветки задач |
| Описание | Для чего проект | опционально |

#### Task-code

- Формат: МНЕМОНИКА-НОМЕР — мнемоника сервиса, дефис, число: FNR-11, SA-1
- Порядковый номер выделяется автоматически из счетчика проекта, вручную не задается; номера только растут — даже после удаления задачи номер не переиспользуется
- task-code уникален глобально (уникальность мнемоники + номера в рамках проекта) и не меняется никогда: переименование проекта меняет название, но не коды задач
- task-code участвует везде, где человек встречается с задачей: URL страницы задачи, kanban-доска, список, поиск, связи, комментарии, хроники
- Поиск: по task-code — точный и по префиксу, по названию — нечеткий

#### Проекты и kanban-доска

- На доске — переключатель проектов: один / несколько / все. Задачи выбранных проектов показываются вместе; истории разворачиваются со своими задачами как обычно
- Фильтр по проекту добавляется к фильтрам доски (название, тип задачи)
- Проект всегда различим по task-code на карточке: мнемоника сразу видна
- Задача создается в рамках выбранного проекта и живет в нем весь жизненный цикл; перенос задач между проектами не предусмотрен — он менял бы мнемонику в task-code и ломал ссылки

#### Создание, редактирование, удаление

- Создание: кнопка "+ проект"; мнемоника на уникальность и путь на доступность проверяются сразу
- Редактирование: название, описание, путь (со повторной проверкой доступности)
- Переименование: только название; task-code всех задач остаются прежними
- Архивирование: проект убирается с доски и из создания задач, задачи остаются доступны для просмотра — безопасный способ спрятать завершенный проект
- Жесткое удаление: только для проектов без задач. Мнемоника удаленного проекта не переиспользуется автоматически — защита от коллизий task-code со старыми ссылками
- Управлять проектами может только человек (матрица прав переходов)

#### Путь на диске. Работа конвейера

- Путь — репозиторий проекта: автомат создает в нем worktree веток задач (см. "Код. Артефактный контракт разработки"); ревью и тестирование читают код по этому пути
- Перед запуском агента демон проверяет доступность пути. Путь недоступен (диск отмонтирован, директория переехала) → агенты проекта не запускаются, задачи ждут — как при массовом отказе провайдера; на карточке проекта горит предупреждение
- Восстановление: исправить путь в настройках проекта или вернуть директорию на место — конвейер продолжается сам

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Общее для всех задач | task-code заявлен как обязательное поле задачи — здесь его устройство |
| kanban-доска и список задач | Мультипроектность: переключатель и фильтр проектов |
| Переход по задачам | Навигация по task-code: код в URL и во всех списках |
| Механика автомата | Недоступный путь — пауза запуска агентов проекта |
| Код. Артефактный контракт разработки | Путь и базовая ветка проекта — основа веток задач |
| Матрица прав переходов | Проекты создают, меняют и удаляют только люди |

### ИИ-чат помощник "Eve"

#### Назначение

- Eve — универсальный ИИ-помощник: чат в нижнем левом углу, доступный с любого экрана системы
- Конвейерные агенты работают на своих статусах и ограничены матрицей прав. Eve — другая: это "руки и глаза" человека в системе, с максимальными правами на все действия
- К Eve можно прийти с чем угодно: вопросом, заданием, проблемой ("почему задача встала?") — она сама разберется, что нужно сделать

#### Кто такая Eve

- Пользователь типа ИИ-агент со специальной ролью "чат-помощник": не привязана к статусам, не участвует в матрице назначений и в очереди демона — Eve запускается сообщением человека, а не статусом задачи
- Предустановленный агент: создается при первом запуске системы; по тому же образцу можно завести и других чат-помощников
- Подключение к ИИ — свое или активное из раздела провайдеров; Eve разумно ставить самую сильную модель

#### Интерфейс

- Чат сворачивается и разворачивается, история диалогов сохраняется
- Eve видит контекст экрана: если вы находитесь на задаче и пишете "переведи на ревью" — она понимает, о какой задаче речь
- Задачу можно указать и явно — по task-code

#### Что умеет

| Действие | Примеры |
| --- | --- |
| Задачи | создать задачу любого типа в проекте; отредактировать название, описание, теги, связи, приоритет; завести чеклист |
| Статусы | перевести задачу по статусам, включая форс-переходы — как человек; вернуть из done; отменить |
| Консультации | объяснить, почему задача в blocked, что происходило с историей, какие задачи зависли; сводные отчеты по проекту |
| Инфраструктура | залезть в docker: вытащить логи контейнеров, посмотреть состояние сервисов; просмотреть кодовую базу проекта по пути из настроек |
| Код | изучить реализацию, найти место в коде, внести правки — правки фиксируются от имени Eve и упоминаются в задаче |

#### Права. Максимальные — но не безнаказанные

- Действия Eve приравнены к человеческим: в матрице прав она может все, что может человек, включая форс-переходы (причину формулирует и указывает сама)
- Автор всех действий — "Eve (через чат)": каждое действие — запись в хроники задачи
- Подтверждения: чтение (статусы, логи, код, консультации) — без вопросов. Изменяющие действия — показывает, что собирается сделать, и ждет "да". Необратимые (удаления, docker-команды с эффектом) — всегда с подтверждением
- Создание задач: подтверждение "да" в чате и есть модерация — задача создается сразу в to do, факт подтверждения пишется в хроники
- Свободный режим: в настройках можно отключить подтверждения целиком — осознанный выбор; аудит при этом не отключается никогда
- Границы: секреты (API-ключи) Eve не показывает никогда — только маски; историю, логи и хроники не стирает

#### Docker и кодовая база

- Docker: просмотр логов и состояния контейнеров — свободно; команды с эффектом (перезапуск, остановка) — после подтверждения
- Кодовая база: чтение — свободно; правки кода — фиксируются от имени Eve и упоминаются в задаче, на которой идет работа

#### Чем Eve отличается от конвейерного агента

| | Конвейерный агент | Eve |
| --- | --- | --- |
| Где работает | на своем статусе | чат, любой экран |
| Триггер | демон: наличие статуса | сообщение человека |
| Права | строго по матрице, без форс-переходов | как у человека + docker и код |
| Результат | переход статуса и отчет | ответ в чате + действия в системе с аудитом |

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Пользователи-агенты | Eve — предустановленный агент роли "чат-помощник", вне матрицы назначений |
| Матрица прав переходов | Действия Eve приравнены к человеческим; форс-переходы — с авто-причиной |
| Подключение ИИ-провайдеров и моделей | Своё или активное подключение |
| Механика автомата | Eve не в очереди демона: запускается сообщением, а не статусом |
| Сущность "проект" | Доступ к кодовой базе — через путь проекта |
| Хроники | Каждое действие Eve в задаче — запись в хроники |

### Раздел настроек. Создание и редактирование kanban-status-flow

#### Назначение раздела

- Все правила из раздела "Статусная модель" — это не код, а конфигурация. Данный раздел — инструмент, на котором эти правила создаются, просматриваются и меняются
- Бизнес-цель: добавить новый тип задач = собрать новый status-flow (с нуля или из пресета) и привязать его к типу. Программирование не требуется, автомат подхватывает новый тип сам — ровно как обещает главная концепция устройства сервиса
- Редактировать flow может только человек-администратор. ИИ-агенты и автомат — исполнители правил, но не их редакторы

#### Основные понятия

| Понятие | Что это |
| --- | --- |
| Статус (узел) | Один этап работы в рамках flow. Описывается набором полей (см. ниже) |
| Переход (ребро) | Направленное правило "из статуса А в статус Б": кто запускает и при каком условии |
| Flow | Набор статусов + переходов + alias-колонок, привязанный к типу задачи. У flow есть версия |
| Пресет | Тот же flow, но не привязанный к типу задачи. Хранится в библиотеке пресетов |
| Alias-колонка | Колонка на kanban-доске, в которую сводится один или несколько статусов |

#### Статус flow. Поля

| Поле | Описание | Ограничения |
| --- | --- | --- |
| Ключ (машинное имя) | Идентификатор статуса, по нему задачи связаны с flow в базе данных | строчные латинские буквы, цифры, `_`; уникален в рамках flow; после создания не меняется |
| Название на интерфейсе | Отображаемое имя, как в таблицах раздела "Статусная модель" | 1–64 символа; можно менять в любой момент |
| Описание этапа | "Что происходит на этом статусе" — тот самый столбец из таблиц статусной модели | до 2000 символов |
| Кто работает на статусе | человек / ИИ-агент / автомат; для ИИ-агента — ссылка на пользователя-агента | сама привязка агентов редактируется в разделе "Один статус = один ИИ-агент" |
| Чеклист-гейт | Какой чеклист обязателен на этом этапе: разработчика / ревьюера / тестировщика / без гейта | без закрытого чеклиста задачу нельзя взять в работу и нельзя перевести дальше |
| Признаки | точка входа (обычно pending) / терминальный (done, canceled) / блокирующий (blocked) | точка входа одна; у терминальных статусов нет исходящих переходов |

#### Переход. Поля

| Поле | Описание |
| --- | --- |
| Откуда → куда | Пара статусов внутри одного flow |
| Кто запускает | автомат / человек через интерфейс / ИИ-агент. Детальные права — в разделе "Матрица прав переходов" |
| Условие | Чеклист этапа: все пункты в конечных статусах (done или closed), ни одного failed. Жесткие связи: нет неснятых блокеров "blocked by". Артефакты этапа: например, отчет о ревью заполнен |
| Как отображается | "Автоматически" / "Автоматом или ручное вмешательство" / "Ручное вмешательство" — те же формулировки, что в таблицах статусной модели |

#### Редактор flow. Два режима

Как и везде в системе, редактирование доступно в двух режимах с переключателем.

**способ 1: визуальный (граф)**

- Статусы — карточки на холсте, переходы — стрелки между ними
- Клик по карточке открывает панель редактирования статуса (поля из таблицы выше), клик по стрелке — панель редактирования перехода
- Новый статус — кнопкой "+ статус"; новый переход — протягиванием стрелки от карточки к карточке
- Удаление статуса — крестиком на карточке. Если в статусе есть задачи, удаление блокируется до миграции (см. "Версионирование")
- Раскладку карточек можно таскать мышью, она сохраняется — это рабочее место, а не разовая картинка

**способ 2: табличный**

- Редактор выглядит ровно как таблицы раздела "Статусная модель": Статус | Описание статуса | Что происходит на этом статусе | Возможные переходы | Как происходит переход
- Новая строка = новый статус; ячейка "Возможные переходы" редактирует список переходов из статуса
- Табличный режим удобен для массовых правок и для переноса описания из документа в систему и обратно

#### Валидация перед сохранением

Перед публикацией flow проверяется автоматически. Ошибки блокируют сохранение, предупреждения — нет.

| Проверка | Ошибка / предупреждение |
| --- | --- |
| Ровно одна точка входа | ошибка |
| Есть хотя бы один терминальный статус (done) | ошибка |
| Нет тупиков: у каждого нетерминального статуса есть исходящий переход | ошибка |
| Нет недостижимых статусов: каждый статус достижим из точки входа | ошибка |
| Из любого статуса есть путь хотя бы до одного терминального статуса | ошибка |
| Есть статусы canceled и blocked | предупреждение: без них автомату некуда девать отмены и блокеры |
| Каждый статус замаплен на alias-колонку | предупреждение: статус без колонки не виден на доске |
| Условия переходов ссылаются на существующие чеклисты и поля | ошибка |
| Ключи статусов уникальны и соответствуют формату | ошибка |

#### Версионирование и задачи "в полёте"

- Каждая публикация изменений создает новую версию flow: v1, v2, v3... Запись о публикации идет в журнал настроек: дата, кто изменил, что изменилось
- Задача хранит версию flow, в которой она создана. Переходы задачи всегда проверяются по её версии, а не по актуальной — изменение правил никогда не ломает задачи посреди работы
- Переименование отображаемого названия статуса применяется сразу ко всем версиям (это не меняет правил, только подписи)
- При удалении или замене статуса, в котором есть задачи, публикация требует миграции: для каждого удаляемого статуса назначается статус-приёмник "старый статус → новый статус", задачи переводятся автоматически
- Откат к предыдущей версии возможен: при откате создается новая версия с содержимым старой, история не переписывается
- Сброс к пресету: если flow собран из пресета, можно вернуться к его исходному состоянию (тоже через новую версию)

#### Пресеты и новые типы задач

- Пресет = flow, не привязанный к типу задачи. Раздел хранит библиотеку пресетов: название, описание, количество статусов, дата изменения
- Источники нового пресета: собрать с нуля / клонировать существующий пресет или flow любого типа / взять встроенный шаблон
- Встроенные пресеты: по одному на пять текущих типов задач (story, common_task, qa_task, bug, analyse_task). Создаются при первом запуске системы, их можно править и сбрасывать к исходному состоянию
- Сценарий добавления нового типа задач: 1) собрать пресет; 2) создать тип задачи и привязать к нему пресет; 3) задачи нового типа появляются на доске в alias-колонках пресета. На этом подключение типа закончено — автомат работает по тем же правилам
- Импорт/экспорт пресета в текстовом формате (YAML): пресет можно перенести между инсталляциями и править текстом

#### Alias-колонки. Редактирование

- В рамках flow ведется таблица маппинга, как в разделе "Общий alias для статусов на kanban-доске": статус flow → колонка на интерфейсе
- Правила: колонка должна содержать хотя бы один статус; колонка без статусов удаляется автоматически; порядок колонок на доске меняется перетаскиванием
- Колонка может объединять несколько статусов одного flow (как "На ревью" объединяет review ready и in review)

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Статусная модель | Источник правил по умолчанию: встроенные пресеты собраны из её таблиц |
| Один статус = один ИИ-агент | Поле статуса "кто работает на статусе" ссылается на агентов из того раздела |
| kanban-доска | Доска строится из alias-колонок той версии flow, по которой живет задача |
| Матрица прав переходов | Детализирует поле перехода "кто запускает" |

### Раздел настроек. Подключение ИИ-провайдеров и моделей

#### Назначение раздела

- Здесь настраивается связь с ИИ-провайдерами: по какому протоколу, какому адресу, с какой моделью и каким токеном работают агенты конвейера
- Никаких зашитых провайдеров: подключается любой провайдер, говорящий на одном из поддерживаемых протоколов, без доработки системы
- Кто из агентов какую модель использует — решается в разделе "Один статус = один ИИ-агент"; этот раздел про само соединение

#### Протоколы взаимодействия

- Пользователь сам выбирает, по какому протоколу система общается с провайдером:

| Протокол | Что это | Через него обычно работают |
| --- | --- | --- |
| OpenAI-совместимый | Протокол OpenAI (chat completions), фактический стандарт: его поддерживают или эмулируют большинство провайдеров и локальные движки | OpenAI, OpenRouter, Groq, локальные vLLM / Ollama и др. |
| Anthropic | Нативный протокол Anthropic (messages API) | Anthropic Claude |

- От выбора протокола зависит список доступных пресетов и формат проверки соединения
- Смена протокола сбрасывает выбранный пресет и модель

#### Пресеты провайдеров

- Пресет провайдера — не путать с пресетом flow из предыдущего раздела — это готовая карточка соединения под конкретного провайдера: название, протокол, базовый URL
- Выбор пресета автоматически заполняет поле URL; поле остается редактируемым (можно поправить под свой шлюз или прокси)
- Встроенные пресеты поставляются вместе с системой и пополняются её обновлениями; пользователь может создать свой пресет (например, для внутреннего корпоративного шлюза)
- Примеры встроенных пресетов (список не ограничен):
  - OpenAI-совместимый: OpenAI, OpenRouter, Groq, локальный vLLM, Ollama
  - Anthropic: Anthropic

#### Форма подключения. Поля

| Поле | Описание | Ограничения |
| --- | --- | --- |
| Название подключения | Произвольное имя в списке подключений | 1–64 символа; уникально |
| Протокол | Переключатель: OpenAI-совместимый / Anthropic | смена протокола сбрасывает пресет и модель |
| Пресет провайдера | Выпадающий список; автозаполняет URL | опционально: URL можно вписать вручную и без пресета |
| URL адрес | Базовый адрес API провайдера | валидный http/https адрес |
| Модель | Выпадающий список моделей, которые отдает провайдер, + кнопка "Обновить список". Если провайдер не отдает список моделей — ввод имени вручную | модель должна быть выбрана или указана |
| API-ключ (токен) | Уникальный токен пользователя для этого провайдера | поле с маской; хранится зашифрованным; в интерфейсе виден только хвост токена (последние 4 символа) |

#### Кнопки "Проверить" и "Сохранить"

В самом низу формы две кнопки.

- **Проверить** — проверяет соединение, ничего не сохраняя: 1) доступность URL; 2) валидность токена; 3) доступность выбранной модели (пробный минимальный запрос). По итогам — баннер "Подключение успешно" или ошибка (см. "Ошибки. Два слоя")
- **Сохранить** — сохраняет конфигурацию в список подключений; по ней в дальнейшем работают агенты
- Кнопки независимы: можно сначала проверить и потом сохранить, а можно сохранить без проверки — такое подключение помечается "не проверено" с предупреждением. Проверить сохраненное можно позже из списка
- Сохранение без заполненных обязательных полей (название, URL, модель, токен) блокируется с подсказкой, какое поле пустое

#### Список подключений. Активное подключение

- Сохранять можно сколько угодно подключений — разные провайдеры, разные токены, разные модели
- Ровно одно подключение в системе является активным: его по умолчанию используют все агенты конвейера. Активное подключение всегда видно в интерфейсе (отдельная пометка)
- В списке по каждому подключению видно: название, протокол, провайдер/URL, модель, статус проверки (активное / проверено / не проверено / ошибка последней проверки), маску токена, дату последней проверки
- Переключение активного подключения — одно действие из списка, без повторного ввода; смена активного пишется в журнал настроек
- Удаление подключения — с подтверждением; активное подключение нельзя удалить, пока не выбрано другое

#### Ошибки. Два слоя

- Любая ошибка при проверке или сохранении показывается в двух слоях:
  - человекочитаемая формулировка — что случилось и что делать;
  - раскрывающийся блок "Техническая информация": HTTP-статус, код ошибки провайдера, тело ответа; копируется одной кнопкой
- Типовые ситуации:

| Ситуация | Человекочитаемое сообщение |
| --- | --- |
| URL недоступен / таймаут | Не удалось связаться с провайдером. Проверьте адрес и сеть |
| 401 / 403 | Провайдер отклонил токен. Проверьте API-ключ и его права |
| 404 | Метод API не найден. Проверьте URL и выбранный протокол |
| Модель не найдена | Провайдер не знает такую модель. Обновите список или выберите модель из списка |
| 429 | Лимит запросов исчерпан. Подождите или проверьте квоту токена |
| 5xx | Провайдер временно недоступен. Повторите проверку позже |

#### Безопасность токенов

- Токены хранятся только в зашифрованном виде; полный токен не показывается нигде — ни в форме, ни в списке
- В хроники задач и журнал настроек попадают только маски токенов

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Один статус = один ИИ-агент | Выбирает подключение и модель из списка этого раздела; по умолчанию — активное подключение |
| Хроники | Вызовы провайдера и ошибки соединения пишутся в хроники задачи |
| Механика автомата | Поведение при недоступности провайдера во время работы: ретраи, перевод задачи в blocked |

### Раздел настроек. Пользователи-агенты и назначение агентов на статусы

#### Назначение раздела

- Здесь живут две связанные вещи: 1) карточки пользователей-агентов (ботов) с их скиллами и 2) матрица назначений: какой агент на каком статусе работает с задачами каждого типа
- Агент — это пользователь-бот: у него есть имя, роль и скилл — подробная инструкция, как он работает. Один агент = один скилл, поэтому агентов иначе можно называть скиллами
- Конечная картина, которую дает раздел: открыв тип задачи, я вижу все статусы этого типа и вижу, какие агенты работают на каждом статусе. Одна задача может иметь несколько исполнителей одновременно — если на её статус назначено несколько агентов

#### Основные понятия

| Понятие | Что это |
| --- | --- |
| Агент | Пользователь-бот (тип "ИИ-агент" из раздела "Работа с пользователями"). Берет задачи на своем статусе и становится их исполнителем |
| Скилл | Инструкция агента: роль, процедура работы, критерии качества, формат результата. Хранится внутри агента как markdown-документ |
| Матрица назначений | Таблица "тип задачи → статусы → агенты" — главный экран раздела |
| Режим совместной работы | Как ведут себя несколько агентов на одном статусе: параллельно или в режиме замещения |

#### Агент. Поля

| Поле | Описание | Ограничения |
| --- | --- | --- |
| Название | Имя агента в списке и в матрице: "Планировщик", "Ревьюер-критик" | 1–64 символа; уникально |
| Роль | Короткое описание, за что агент отвечает: "проводит код-ревью и фиксирует замечания" | обязательное поле |
| Скилл (инструкция) | Подробное описание того, как агент работает (см. "Скилл. Из чего состоит") | markdown; два режима редактирования |
| Подключение к ИИ | Ссылка на подключение и модель из раздела "Подключение ИИ-провайдеров и моделей" | по умолчанию — активное подключение; опционально свое: простые статусы можно посадить на дешевую модель, сложные — на сильную |
| Теги | Метки для поиска: #ревью, #backend | от 0 до 5 |

#### Скилл. Из чего состоит

- Скилл — это "мозг" агента. Рекомендуемая структура (свободная, не жесткая):
  - Роль и цель: за что агент отвечает, одним абзацем
  - Процедура: пошагово, что агент делает, попав на статус (например: прочитать постановку и изменения кода → составить чеклист проверки → пройти по пунктам → написать отчет)
  - Критерии качества: как агент отличает "хорошо" от "плохо"
  - Формат результата: что агент обязан оставить после себя (отчет о ревью, новые пункты чеклиста разработчика, документ ПСИ)
  - Ограничения: что агенту делать нельзя (ревьюеру — править код; тестировщику — менять требования)
- Скилл редактируется как описание задачи: визуальный режим с панелью или текстовый markdown
- При выполнении задачи скилл передается агенту как основная инструкция вместе с контекстом задачи (постановка, чеклисты, отчеты предыдущих этапов)

#### Создание, редактирование, удаление агентов

- Создание: кнопка "+ агент". После создания агент появляется в общем списке пользователей (тип "ИИ-агент") и становится доступен для назначения в матрице
- Быстрый старт: клонирование существующего агента — копия скилла, чтобы править под свою роль, а не писать с нуля
- Предустановленные агенты: при первом запуске система создает базовый набор под текущие типы задач (Планировщик, Разработчик, Ревьюер, Тестировщик, Аналитик, ПСИ-составитель). Их можно править и сбрасывать к исходному состоянию — как встроенные пресеты flow
- Редактирование: карандаш в карточке агента (как у задач). Правки скилла вступают в силу для следующих запусков; уже запущенное выполнение заканчивает работу по старой инструкции
- Удаление: крестик. Агент, назначенный хотя бы на один статус, не удаляется — сначала снимаются назначения; система показывает список статусов, где агент используется
- Список агентов: нечеткий поиск по названию, фильтр по типам задач (на какие назначен) и по тегам

#### Матрица назначений. Тип задачи → статус → агенты

- Главный экран раздела. Сверху — выбор типа задачи (вкладки: story, common_task, qa_task, bug, analyse_task и все добавленные вами новые типы)
- Под выбранным типом — таблица статусов из актуальной версии flow этого типа. Пример для common_task:

| Статус | Что происходит на статусе | Агенты | Режим |
| --- | --- | --- | --- |
| to do | декомпозиция, чеклист разработки, контекст | Планировщик | — |
| in progress | разработка по TDD, ведение чеклиста | Разработчик | — |
| review ready | подготовка чеклиста ревьюера | Ревьюер | — |
| in review | проверка кода, отчет о ревью | Ревьюер + Ревьюер-критик | параллельно |
| qa ready | формирование чеклиста тестирования | Тестировщик | — |
| in testing | тестирование по чеклисту, отчет | Тестировщик | — |

(назначения в примере меняются в один клик)

- Назначение: в строке статуса нажать на ячейку "Агенты" → выпадающий поиск по агентам → выбрать одного или нескольких
- Матрица и редактор status-flow — одна конфигурация в двух видах: здесь сгруппировано по типам задач, там — то же поле "кто работает на статусе" у каждой карточки статуса. Правка в одном месте видна в другом
- На статус можно назначить и человека: в ячейку ставится любой пользователь (например, in review у analyse_task ревьюит человек)
- Статусам с автоматическими переходами (например, pending → backlog) агенты не назначаются

#### Несколько агентов на одном статусе

- На статус можно назначить сколько угодно агентов. Режим совместной работы выбирается тут же:
  - параллельно — все назначенные агенты работают над задачей одновременно и независимо; результаты собираются вместе (пример: два независимых ревью, расхождения разбирает человек). Исполнителей у задачи в этом режиме несколько
  - замещение — работает один агент; если он не смог (ошибка, недоступность), задача автоматически передается следующему по списку. Исполнитель у задачи один
- Режим по умолчанию — замещение
- Кто именно работает с задачей, видно в поле "Исполнитель" (см. "Автор и Исполнитель"): при параллельной работе поле показывает список исполнителей
- Правка назначений не создает новую версию flow и не трогает задачи в полёте: следующий запуск агента на статусе уже пойдет по новому назначению

#### Контроль назначений

- Если на статусе, где должен работать ИИ-агент, не назначено ни одного агента, в матрице горит предупреждение: задачи, попавшие на такой статус, автоматически перейдут в blocked с записью в хрониках "нет назначенного агента"
- Проверка выполняется при сохранении матрицы

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Подключение ИИ-провайдеров и моделей | У агента свое или активное подключение; смена активного переключает всех агентов с настройкой "по умолчанию" |
| Создание и редактирование kanban-status-flow | Поле статуса "кто работает на статусе" — та же конфигурация, другой вид |
| Автор и Исполнитель | Назначенный агент становится исполнителем задачи, взяв её на своем статусе; при параллельной работе исполнителей несколько |
| Матрица прав переходов | Что агент может делать с задачей на своем статусе |
| Механика автомата | Когда и как агент запускается при попадании задачи на статус; ретраи и поведение при ошибке |

### Журнал настроек

#### Назначение журнала

- Единый журнал конфигурации: кто и когда менял правила системы — flow и их версии, подключения к ИИ, агенты и матрицу назначений, проекты
- Отвечает на вопрос "кто менял правила" — в отличие от хроник задач ("что происходило с задачей") и очереди автомата ("что происходит сейчас")

#### Как ведется

- Запись при каждом изменении настроек: дата и время, кто, что изменил. Здесь, в отличие от хроник задач, хранится полный диф: старое и новое значение правила — цена испорченного правила выше
- Лог версий flow — часть этого журнала: каждая публикация версии пишется здесь
- Журнал доступен в разделе настроек; записи вносятся автоматически при любом изменении конфигурации; секреты — только масками

#### Связь с другими разделами

| Раздел | Связь |
| --- | --- |
| Создание и редактирование kanban-status-flow | Публикация версий flow пишется в журнал |
| Подключение ИИ-провайдеров и моделей | Смена активного подключения и правки подключений пишутся в журнал |
| Пользователи-агенты и назначение агентов на статусы | Создание и правки агентов, изменения матрицы назначений |
| Сущность "проект" | Создание, правки и архивирование проектов |
