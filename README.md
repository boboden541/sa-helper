### 🔧 Продвинутая настройка (Алиас `init_sa`)

#### macOS / Linux

1. Определите шелл: `echo $SHELL`
   - `/bin/zsh` → `~/.zshrc`
   - `/bin/bash` → `~/.bashrc`
2. Запишите алиас:

```bash
echo "alias init_sa='curl -sSL https://raw.githubusercontent.com/boboden541/sa-helper/main/install.sh -o /tmp/sa-install.sh && bash /tmp/sa-install.sh && rm -f /tmp/sa-install.sh'" >> ~/.zshrc
```

1. Примените: `source ~/.zshrc`
2. Проверьте: введите `init_sa` в любой папке проекта.

#### Windows

> Требуется Git Bash (ставится вместе с Git for Windows).

Откройте профиль PowerShell:

```powershell
notepad $PROFILE
```

Добавьте функцию:

```powershell
function init_sa {
    $tempDir = Join-Path $env:TEMP "sa-helper-$(Get-Random)"
    git clone --depth 1 https://github.com/boboden541/sa-helper.git $tempDir
    bash "$tempDir\install.sh"
    Remove-Item -Recurse -Force $tempDir -ErrorAction SilentlyContinue
}
```

### Процесс 2: Системные требования (FNR Pipeline)

У процесса **два входа**:

- **Задача понятна** → постановка через анализ проблемы: `/fnr-new-task` формирует `task.md`.
- **Задача от руководства размыта, требований нет** → discovery‑этапы (`/discovery` → цикл вопросов‑ответов `/discovery-answer` / `/discovery-brief`), которые закрывают развилки и готовят тот же `task.md` (детали — Процесс 4).

# Часть II — Разработка (AI-Harness)

Вторая половина инструмента: утверждённые системные требования превращаются в работающий код.
**AI-Harness — task-tracker плюс автомат вокруг него.** Канбан-доска и статусные модели для пяти типов задач, а поверх — фоновый демон и ИИ-агенты: они сами ведут задачу от декомпозиции до приёмо-сдаточных испытаний. Человек управляет из веб-интерфейса и словами через чат Eve; форс-переходы и приёмка работы — только человек.

## Как работать: пошагово

| Шаг | Что делать | Где |
|---|---|---|
| 1 | **Поднять стек** и демо-данные (см. [Подъём в Docker](#-подъём-в-docker)) | http://localhost:8088 |
| 2 | **Подключить ИИ-провайдера** и **папку инструментов** — `.claude` установленного SA-Helper, один путь на все проекты | Настройки → ИИ-провайдеры / Инструменты |
| 3 | **Создать историю** и вставить текст СТ: Планировщик декомпозирует её на задачи; если СТ неполные — агент вернёт вопросы, а не додумает | «+ Задача» → история |
| 4 | **Наблюдать**: канбан двигается сам; на доске, в списке и в карточке видно, какой агент работает прямо сейчас, сколько минут и токенов, и что он делает — хроника обновляется живьём | витрина |
| 5 | **Управлять**: кнопки переходов и форс (с обязательной причиной), перехват задачи у агента, чат Eve: «почему SA-13 не двигается?», «переведи SA-11 на ревью», «создай задачу: …» | карточка / 💬 Eve |
| 6 | **Проверить и принять**: ПСИ-составитель готовит документ ПСИ по истории (сохраняется файлом в папку FNR, например `…/FNR/FNR_8/psi.md`); человек выполняет прогон «действие → ожидаемый результат» и принимает работу | карточка истории |

## Задачи и автомат

Автомат построен на задачах: у каждого типа — своя статусная модель, и добавить новый тип задач значит «спроектировать» статусную модель в настройках, без программирования. Задачи в полёте живут по своей версии правил — публикация новой версии не ломает идущие работы.

| Тип | Для чего | Путь |
|:----|:---------|:-----|
| **История** | большая фича | декомпозируется на задачи → когда все закрыты — сквозное тестирование с ПСИ |
| **Задача** | разработка | декомпозиция → разработка → ревью → тестирование; замечания возвращают на доработку |
| **QA-задача** | проверка без кода | чеклист и отчёт в формате ПСИ: любой человек воспроизводит проверку как по инструкции |
| **Баг** | исправление | чеклист «как воспроизвести и как исправить», без код-ревью, с повторным тестом |
| **Анализ** | проектирование решения | требования → изыскания → концепты → выбор → системные требования |

**История движется сама** (зеркалирование): дочернюю задачу взяли в работу — история «в работе»; всё закрыто — на тестирование; найдены баги — заблокирована; ПСИ пройден без замечаний — «готово», и это подтверждает человек. Каждое срабатывание правила — запись в хрониках истории.

**Право на переход.** Человек — любые переходы и форс (даже из «готово», только с причиной). Агент — работа на своём статусе. Автомат — только детерминированные правила, без «инициативы». Чеклист-гейт: без созданного чеклиста этапа задача не берётся в работу, с незакрытыми пунктами — не передаётся дальше. Если агенту не удалось (провайдер, таймаут, исчерпаны попытки) — задача уходит в «заблокировано» с формулировкой «требуется участие человека».

## 🤖 Агенты и конвейер

Демон сам находит задачи на статусах с назначенным агентом, атомарно резервирует их (двойное взятие исключено) и запускает прогоны. На один статус можно назначить несколько агентов: «параллельно» — работают одновременно, «замещение» (по умолчанию) — работает один, при сбое подхватывает следующий.

| Пресет-агент | Что делает |
|:-------------|:-----------|
| **Планировщик** | декомпозирует истории и задачи, готовит чеклист разработчика и контекст прогона |
| **Разработчик** | TDD-разработка в ветке `task/<код>`: чеклист, осмысленные коммиты, отчёт |
| **Ревьюер** | независимое ревью диффа и отчёта по чеклисту ревьюера |
| **Ревьюер-критик** | второе независимое ревью — строгость к краевым случаям |
| **Тестировщик** | чеклист тестирования и отчёт; для qa_task — в формате ПСИ |
| **Аналитик** | требования, концепты, спецификация |
| **ПСИ-составитель** | документ ПСИ по истории: версии, прогон, файл в папке FNR |

**Как устроен прогон.** Агент запускается headless (Claude Agent SDK) в git-worktree задачи — ветка `task/<код>` от базовой ветки проекта. Слияние в базовую ветку делает демон перед «готово»; конфликт — задача заблокирована, распутывает человек. Промт = персона «Имя — роль» + контекст задачи + назначенные скиллы + контракт отчёта: свободного текста у агента нет, методологии живут в скиллах. Отчёт — строгий JSON: статус, сводка, обновления чеклиста, артефакт, предложенный переход, вопросы и комментарии человеку (они попадают в карточку от имени агента).

**SA-Helper внутри конвейера.** Инструментарий задаётся одним глобальным путём на все проекты (папка `.claude` установленного SA-Helper) и подключается к worktree живой ссылкой — симлинк (Windows — junction): правки на диске агент видит сразу, копии по задачам не плодятся. Вкладка «Инструменты» ведёт реестр команд и скиллов с версиями по sha256 и живым синком (актуален / изменился / пропал); карточку инструмента можно править прямо из браузера — запись идёт в файл с защитой от затирания. Скиллы назначаются агенту чипами из реестра (до 8), команды запускаются кнопкой **⚡ Команда** — выбор команды открывает диалог создания задачи с её текстом.

**Надёжность.** Heartbeat: потеря пульса — возврат в очередь. Ретраи с паузами 1 → 5 → 15 минут; после исчерпания попыток — честное «требуется участие человека». Перехват задачи человеком останавливает процесс агента, незавершённый отчёт не применяется. Рубильник конвейера запрещает запуск новых агентов — ручная работа продолжается. Массовый отказ провайдера: задачи ждут паузы, не блокируясь.

**Живой контур.** На доске, в списке и в карточке — признак «агент работает» с минутами и растущим счётчиком токенов (формат «1300К»); хроника задачи и лента прогона обновляются в реальном времени; после завершения прогона расход токенов остаётся на карточке.

**💬 Eve** — универсальный помощник в чате с любого экрана: создаёт и правит задачи, переводит статусы (форс — с причиной), объясняет, почему задача встала. Понимает свободные фразы и контекст открытой задачи; изменяющие действия — только после «да» человека, аудит не отключается.

**Принятые риски (решения владельца, 29.10.2026).** У Eve есть прямой SQL-доступ к базе: прямые переводы статусов идут мимо рёбер flow без подтверждения «да» (аудит остаётся в chat_message). Анонимный dev-режим при auth.required=false действует от имени первого человека в БД. Оба решения зафиксированы сознательно.

## 🗂 Структура sa_documentation

Документация реверс‑инжиниринга раскладывается **по сервисам** (один анализируемый репозиторий = один сервис), внутри сервиса — **по назначению**:

```text
sa_documentation/
├── tasks.md                        # ЕДИНЫЙ план задач на весь workspace (корень; формируется /reverse-plan-tasks)
├── <сервис>-docs/                  # один репозиторий = один сервис (имя из папки репо, kebab-case)
│   ├── repomix-output.xml          # контекст-снапшот этого репозитория
│   ├── api_map.md                  # карта публичного API: внешний URL → контроллер/метод
│   ├── naming_conventions.md       # словарь «код ↔ бизнес» этого репозитория
│   ├── api/                        # api_<нормализованный_роут>.md (+ openapi/<domain>.yaml)
│   ├── integrations/               # integration_<партнёр>_<назначение>.md
│   ├── screens/                    # screen_<название_экрана>.md
│   ├── architecture/               # architecture_<название>.md (+ .puml)
│   ├── erd/                        # erd_<домен|схема>.md
│   ├── data_trace/                 # data_trace_<название>.md
│   ├── processes/                  # process_<название>.md
│   └── mindmaps/                   # mindmap_<ось>_<область>.md (+ _partN.md) — карты погружения
├── FNR/                            # кросс-сервисный задачный уровень (корень, не трогаем)
├── prd/  bft/                      # кросс-сервисный задачный уровень (корень, не трогаем)
```

**Правила:**

- **Владелец документа — сервис, о котором документ.** API сервиса Y → `y-docs/api/`; ERD репозитория БД → `data-base-docs/erd/`; интеграция X→Y → `x-docs/integrations/` (владелец — инициатор/клиент).
- Категории создаются по мере появления документов, пустые папки не создаются.
- Отдельный репозиторий БД — такой же «сервис» (`data-base-docs/`), его документы живут в `erd/` (и опционально `data_trace/`).
- **Карта типов документации** (тип ↔ папка ↔ признаки ↔ команда) — редактируемая таблица в `skills/doc-type-router/resources/type_map.md`. Хотите добавить свой тип или изменить признаки — правьте этот файл: команды сверяются с ним, а не с локальными копиями.

> **Legacy.** Документы, созданные до переезда и лежащие в плоских путях (`sa_documentation/api/…`, `sa_documentation/screens/…`), остаются рабочими: `/validate-doc` распознаёт тип по категории пути. Автоматической миграции нет — при желании перенесите файлы в `<сервис>-docs/` вручную.

# Применение на практике

> **Несколько репозиториев (workspace).** Откройте агента в корневой папке, где склонированы все нужные репозитории: `/context-gen` сам найдёт их, покажет план сервисов (`sa_documentation/<сервис>-docs/` по каждому) на утверждение и соберёт контекст по каждому сервису (repomix-снапшот, карту API, словарь). Затем `/reverse-plan-tasks` сформирует единый корневой `tasks.md` — по одному сервису (полное покрытие 8 типов) или по взаимосвязи сервисов. Дальше команды определяют сервис по задаче из `tasks.md`.

### Я хочу быстро понять суть сервиса

```text
1. /context-gen <цель реверса> — контекст по сервису (repomix, api_map, словарь)
2. /reverse-plan-tasks <та же цель> — план задач, включая задачу Mindmap (карта погружения)
3. /mindmap [T<N>] — PlantUML mindmap «от общего к частному»: ось (экраны / объекты / интеграции),
   действия Чтение/ЗАПИСЬ, каналы, трассируемые атомы (SP / таблицы / эндпоинты)
4. /validate-doc sa_documentation/<сервис>-docs/mindmaps/mindmap_<ось>_<область>.md
```

> Если документы по сервису уже есть, `/mindmap <сервис>` работает ad hoc: карта собирается из готовых
> ✅-документов (screen / api / integration / erd / data_trace), а не из повторной разведки по коду.
