## Использование

```
/impl-verify <путь к каталогу harness>
```

**Параметры:**

- `<путь к каталогу harness>` — например, `sa_documentation/FNR/FNR_1/harness`.

## Примеры

```
/impl-verify sa_documentation/FNR/FNR_1/harness
```

## Важно

**Приоритет:** верификация только когда **все задачи плана** в `DONE` (частичный скоуп —
явно перечислить задачи и пометить отчёт как частичный). Ничего не «дотягиваем» до зелёного:
красный гейт — красный вердикт.

**Ожидаемый результат:** документ `verification_report` (doc-set) (прогоны всех систем, контрактные
проверки, метрики пилота, PR-заготовка) + манифест `status: "COMPLETED"` при полном успехе.

**Универсальность:** команды прогонов — из `workspaces.yaml`; контрактные проверки — по
разделу контрактов досье; data-only системы — проверки отсутствия обращений. `python3`
(Windows Git Bash: `python`).

## Инструкция для LLM

### Этап 0: Готовность

1. Манифест: все задачи `DONE`? Нет → перечисли неготовые; продолжай только с явно
   подтверждённым частичным скоупом (человек сказал — отметь в отчёте).
2. `bootstrap`-статусы систем не хуже `ready_with_notes`; иначе — сначала `/impl-bootstrap`.

### Этап 1: Полные прогоны систем

Для каждой системы плана: гейты build/test из `workspaces.yaml` на **основном** дереве
(не worktree — ветки уже слиты локально в ветки задач; если изменения ещё только в ветках
`harness/*`, прогон делай в их worktree и пометь в отчёте). `runner.py` `--mode build` и
`--mode test` (junit-glob, где задан) с логами в `harness/logs/verify_<система>.log`.

### Этап 2: Контрактные проверки

По разделу контрактов досье (для каждого контракта К*):

1. Спецификация существует и валидна (валидатор, если инструмент есть; иначе структурная
   проверка агентом с пометкой).
2. Реализация каждой стороны соответствует спецификации: в коде стороны есть использование
   схемы/метода контракта (ссылки `файл:строка` в отчёт).
3. Стороны согласованы: имена полей/коды ответов в коде потребителя = спецификации.

### Этап 3: Проверки data-only и выводимых систем

Для систем с `data_only: true` и для систем, выводимых из контура по СТ:

1. В диффах задач нет обращений к их объектам, если СТ требует обратного (для выводимой
   системы — наоборот: новых обращений появиться не должно). Проверка: ripgrep по диффам
   (имена таблиц/процедур/репозиториев).
2. Результат — в отчёт с перечнем проверенных паттернов.

### Этап 4: Метрики пилота и PR-заготовка

1. Из манифеста: доля задач без эскалаций, среднее `iteration_count`, находки ревью по
   существенности, число `skipped`-гейтов и почему.
2. документ `verification_report` (doc-set): прогоны (числа), контракты (проверено/не проверено),
   data-only проверки, метрики, границы верификации (что не проверялось).
3. PR-заготовка: документ `pr_draft` (doc-set) — заголовок `[FNR-<N>] <название>`, сводка изменений
   по системам, перечень веток `harness/*` с коммитами, чек-лист проверок с результатами.
   **Никаких push** — создание PR и push делает человек.

### Этап 5: Итог

1. Все зелёные → манифест `status: "COMPLETED"`, `updated_at`. Любой красный → отчёт с
   вердиктом `NOT_VERIFIED` и перечнем что чинить (манифест не трогаем).
2. Завершение: выведи вердикт, путь отчёта и подсказку: «Дифф готов к ревью человеком.
   Ветки: <перечень>. PR-заготовка: <путь> (push — вручную)».


**Фиксация отчётов:** `sahelper doc-set FNR --kind verification_report --file <файл>`
и `sahelper doc-set FNR --kind pr_draft --file <файл>`.
