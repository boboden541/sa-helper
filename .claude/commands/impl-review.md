**ХРАНИЛИЩЕ:** состояние — в БД; доступ только через `python3 harness/sahelper.py`
(task/docs/comments для чтения; doc-set/verdict-set/comment-add для записи). Файлы
harness/ (reviews/, comments/, manifest.json) не читать и не писать.
---

## Использование

```
/impl-review <путь к каталогу harness> [T<k>]
```

**Параметры:**

- `<путь к каталогу harness>` — например, `sa_documentation/FNR/FNR_1/harness`.
- `[T<k>]` — id задачи; если не указан — задача в статусе `AGENT_REVIEW`.

## Примеры

```
/impl-review sa_documentation/FNR/FNR_1/harness T2
```

## Важно

**Приоритет:** ревьюер — **независимый контекст** (v2 §9): новая сессия/подагент, не видящий
диалог кодера. Материалы ревью — только дифф ветки, карточка, досье, фрагменты СТ. Каждая
находка — с `файл:строка` (рубрика: `resources/review_rubric.md`).

**Ожидаемый результат:** `reviews/T<k>_review.md` + вердикт в `manifest.json`
(`review_verdict`), задача `DONE` (APPROVED, worktree удалён) или возврат в `/impl-run`.

**Универсальность:** ревьюер не знает стек и домен заранее — всё в материалах; рубрика одна
для любых систем. `python3` (Windows Git Bash: `python`).

## Инструкция для LLM

### Этап 0: Предусловия

1. Задача в статусе `AGENT_REVIEW` (или `GATES` — тогда сначала дозакрой гейты `/impl-run`-ом).
2. Worktree задачи существует; дифф не пуст. Иначе — STOP с пояснением.

### Этап 1: Материалы ревьюера

Собери в временный комплект (не добавляй в него ничего из диалога кодера):

- дифф: `git -C <worktree> diff <base>...HEAD` плюс список файлов;
- карточка `tasks/T<k>.md`, `dossier.md`, соответствующие задачи СТ (только разделы задачи и
  общие системы/контракты);
- логи гейтов из `harness/logs/` (сводки, не сырые стены).

### Этап 2: Независимое ревью

Запусти ревью в **отдельном контексте** (подагент/новая сессия — не продолжение этого диалога).
Передай только комплект из Этапа 1 и рубрику `resources/review_rubric.md`. Ревьюер:

1. Проверяет все 6 осей рубрики; каждая находка — `файл:строка` + существенность
   (критично/существенно/nit) + как чинить.
2. Для data-only задач (DDL) — оси 3 (расширительность миграций) и 1 (трассируемость) главные,
   гейты build/test = `skipped (data-only)`.
3. Возвращает вердикт `APPROVED | CHANGES_REQUESTED | BLOCKED` и текст отчёта.

### Этап 3: Фиксация вердикта

1. Отчёт ревьюера (дословно, структурированный markdown: находки с
   `файл:строка`, существенность, «как чинить») — в БД:
   `sahelper doc-set FNR --kind review --tid T<k> --file <отчёт.md>`.
   Он виден человеку в блоке «Ревью» витрины.
2. **Свой чек-лист ревью** — декомпозиция проверки (человек видит его в блоке
   «Ревью» и следит за ходом):
   `sahelper checklist-section-add FNR T<k> --title "Ревью (чек-лист)" --kind review`,
   затем по каждому направлению проверки:
   `sahelper checklist-add FNR T<k> --section "Ревью (чек-лист)" --text "Проверена
   обработка 409-конфликта карточки" --kind review --depth 1`
   (подпункты — `--depth 2`; существенные направления помечай `--mandatory`).
   Проверил направление — `sahelper checklist-state FNR T<k> <текст-или-id> --state done`.
   ПЕРЕД вердиктом APPROVED закрой все обязательные пункты — иначе гейт чек-листа
   заблокирует approve (незакрытые mandatory план- и review-секций).
3. **Машиночитаемый вердикт** — адаптеру (демон ведёт петлю доработки без LLM):
   `sahelper verdict-set FNR T<k> --status APPROVED|CHANGES_REQUESTED --iteration <n>
   --blocking '[{"file": "файл:строка", "text": "суть"}, ...]'
   --advisory '[{"file": "...", "text": "..."}]'` (id находок адаптер вычислит сам;
   `<n>` — из `sahelper state FNR` → review_iterations + 1).
4. **Комментарий от ревьюера** — понятный указатель исполнителю:
   `sahelper comment-add FNR T<k> --author reviewer --text ...` по канону
   comment-writing; при CHANGES_REQUESTED обязательно: сколько blocking/advisory,
   что замечания описаны в отчёте («Ревью» витрины) и чек-листе ревью, шаги чинить
   по порядку blocking.
5. `CHANGES_REQUESTED` → **в чек-лист исполнителя не пиши**: раздел
   «Доработка по ревью (чек-лист)» упразднён — шаги доработки вносит сам исполнитель
   подзаголовком в СВОЙ план (канон /impl-run, «Режим доработки после ревью»).
   nit-замечания — только в advisory вердикта, без отдельных пунктов.
   `APPROVED` → удали worktree задачи (`git worktree remove .worktrees/FNR-<N>-t<k>`;
   ветку с коммитами оставить).
6. `sahelper validate FNR`.
