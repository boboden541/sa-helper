## Использование

```
/reverse-plan-tasks <промт>
```

**Параметры:**

- `<промт>` — отправная точка: название сервиса (сервисов) и/или цель изучения.

**Два режима:**

- **Режим А «Один сервис».** В промте назван один сервис (или цель внутри одного сервиса). `tasks.md` получает задачи по ВСЕМ 8 реверс-типам `type_map.md` — полное покрытие аспектов сервиса.
- **Режим Б «Взаимосвязь сервисов».** В промте названы два и более сервисов и связь между ними. `tasks.md` получает задачи всех 8 типов, нацеленные на определение и документирование СВЯЗЕЙ между сервисами.

## Примеры

**Режим А (один сервис):**

```
/reverse-plan-tasks Изучи сервис svc-a полностью: экраны, API, интеграции, архитектуру, БД, трассы данных и процессы
```

```
/reverse-plan-tasks svc-a
```

**Режим Б (взаимосвязь):**

```
/reverse-plan-tasks Изучи сервисы svc-a и svc-b и их взаимосвязь: как svc-a оформляет заказ, а svc-b его оплачивает
```

**Дополнение существующего плана:**

```
/reverse-plan-tasks Добавь в план задачи по сервису svc-c
```

**Пересоздание:**

```
/reverse-plan-tasks Пересоздай план полностью по сервису svc-a
```

## Важно

**Прекондишены (жёсткие):**

1. Для **каждого** сервиса из промта существует `sa_documentation/<сервис>-docs/repomix-output.xml`. Если нет — СТОП: «Контекст сервиса <X> не собран. Сначала запусти /context-gen». Не планируй по живому коду: план разойдётся со снапшотом, по которому потом работают `/create-doc` и `/arch-gen`.
2. Карта API: если есть `sa_documentation/<сервис>-docs/api_map.md` — это источник истины для нарезки API-задач. Если нет (legacy-прогон) — выведи таблицу картирования сам из `repomix-output.xml` (конфиги роутинга / GraphQL-схемы / proto) и работай по ней; файл на диск НЕ пиши — контекст-артефакты принадлежат `/context-gen`.
3. Загрузи `.claude/skills/doc-type-router/resources/type_map.md` — единственный источник истины «тип ↔ папка ↔ признаки ↔ префикс».

**Поведение при существующем tasks.md:**

- По умолчанию — ДОПОЛНЕНИЕ: новые `[ID]` продолжают глобальную нумерацию от максимального существующего; существующие задачи, их `[ID]` и строки статусов не изменяются; дубликат (совпадает «Шаблон результата») не создаётся — факт зафиксируй в отчёте.
- ПЕРЕСОЗДАНИЕ — только если пользователь явно попросил («пересоздай», «заново», «с нуля»). Задачи со статусом ✅ переносятся в новый план с сохранением `[ID]`, остальные отбрасываются. Перед выполнением выведи предупреждение: «Часть [ID] исчезнет — ссылки вида /create-doc [ID] на старые задачи перестанут работать».

**На выходе ожидается:**

- Файл `sa_documentation/tasks.md` — единый план задач workspace (создан или дополнен), включая раздел «Покрытие типов (Coverage Gate)».
- **Иные файлы не создавать и не править** (`repomix-output.xml`, `api_map.md`, `naming_conventions.md` — артефакты `/context-gen`). Подпапки категорий не создавать — их создают команды генерации по мере появления документов.

**Универсальность:** команда не привязана к конкретному стеку, БД или бизнес-домену.

## Инструкция для LLM

### Графовый контекст (complement-модель)

Граф дополняет repomix-output.xml, а не заменяет его. Связи `confidence='low'` — только гипотеза, не факт (см. `/create-doc`).

- **Режим А:** `graph_schema` / `graph_arch_summary` (слои, контроллеры, DAO), `graph_db_schema` (наличие БД-объектов для ERD).
- **Режим Б:** `graph_export` / `graph_impact` (рёбра между сервисами), `graph_db_lineage` (пересечение моделей на стыке).

Если MCP-инструменты недоступны — продолжай с repomix-output.xml.

### Этап 0: Режим, сервисы и план на утверждение

1. Извлеки из промта имена сервисов и сопоставь их с существующими папками `sa_documentation/*-docs/` (при необходимости — с папками репозиториев workspace: kebab-case от имени папки, суффиксы НЕ отрезать).
2. Определи режим: ровно один сервис → Режим А; два и более сервисов И цель про связь между ними (маркеры: «связь», «взаимосвязь», «интеграция между», «как X ходит в Y», «сквозной») → Режим Б; два и более сервисов без маркеров связи (цель «изучить/задокументировать полностью») → спроси одним сообщением: (А) полное покрытие каждого сервиса независимо или (Б) взаимосвязи.
3. Неоднозначность — спроси (одним сообщением, с вариантами):
   - ни один сервис не найден → перечисли доступные `sa_documentation/*-docs/`;
   - найден один, но промт подразумевает партнёра без собранного контекста → спроси: ограничиться одним сервисом или сначала собрать контекст партнёра (`/context-gen`).
4. Проверь прекондишены (см. «Важно»). При нарушении — стоп.
5. Если tasks.md существует — прочитай его: максимальный `[ID]`, задачи со статусом ✅, список существующих «Шаблон результата» (отсечение дублей). Определи: дополнение или пересоздание (маркеры пересоздания — из «Важно»).
6. Выведи план на утверждение ДО записи:

   ```
   Режим: (А) один сервис / (Б) взаимосвязь
   Сервисы: svc-a, svc-b
   Контекст: repomix-output.xml — есть/нет; api_map.md — есть (N строк) / будет выведен из repomix
   tasks.md: будет создан / дополнен (текущих задач: M, нумерация продолжится с [T...])
   Ожидаемо задач по типам: Screen ~..., API ~..., Integration ~..., DataTrace ~..., Architecture ~..., ERD ~..., Process ~..., Mindmap ~1–2
   Подтверди.
   ```

### Этап 1: Сбор исходников планирования

1. Прочитай `repomix-output.xml` каждого сервиса промта — основной контекст.
2. Прочитай `api_map.md` каждого сервиса (или выведи картирование сам — см. прекондишены).
3. Прочитай `naming_conventions.md` каждого сервиса — бизнес-имена для названий задач.
4. Примени графовую надстройку (см. выше).
5. Для Режима Б составь **реестр связей X→Y**: конфиги базовых адресов партнёров, HTTP/gRPC-клиенты, топики и очереди, общие БД, вызовы эндпоинтов партнёра (по api_map партнёра + клиентскому коду X). Оба направления — отдельные записи.

### Этап 2: Правила нарезки задач (общие для обоих режимов)

1. Используя универсальные паттерны из `.claude/skills/architecture/resources/architecture_patterns.md`, определи ключевые слои (Controllers, Services, DAO).
2. tasks.md — **единый файл** с шапкой:

   ```
   # План документирования workspace

   | Сервис | Папка документации |
   |---|---|
   | svc-a | sa_documentation/svc-a-docs/ |
   ```

   Задачи всех сервисов живут в этом одном файле. **[ID] задач глобально уникальны по всему workspace** (продолжай нумерацию между сервисами, не начинай с начала для каждого сервиса). Распредели задачи так, чтобы файлы в одной задаче суммарно не превышали $100,000$ токенов.

> **Правило атомарности задач типа API (приоритетнее лимита токенов):**
> Для задач типа **API** действует принцип «один API = одна задача = один документ». Каждая строка `api_map.md` (одна атомарная единица API) порождает ровно ОДНУ задачу типа API. **Лимит токенов (100 000) НЕ может служить причиной объединения нескольких эндпоинтов в одну задачу.** Лимит токенов применяется к API-задачам только как критерий ДРОБЛЕНИЯ контекста: если контекст одного эндпоинта сам по себе превышает лимит — раздроби список файлов контекста, но не объединяй эндпоинты.
>
> **Атомарная единица API** определяется по типу контракта:
> - **REST** — отдельный эндпоинт (HTTP-метод + путь).
> - **GraphQL** — отдельный query или mutation (единый транспортный эндпоинт `/graphql` НЕ является атомарной единицей).
> - **gRPC** — отдельный метод сервиса.
>
> Для задач типа **Integration** действует тот же принцип атомарности: «одна интеграция = одна задача = один документ».
> Для задач типа **DataTrace**, **Architecture**, **ERD** и **Process** правило атомарности НЕ применяется — допустима группировка по смыслу/лимиту токенов (но ERD группируется по схемам/доменам БД, а не «всё в одном»).

#### Правило классификации задач по типу документа

**Загрузи карту типов** `.claude/skills/doc-type-router/resources/type_map.md` — это единственный источник истины «тип ↔ папка ↔ признаки ↔ префикс». Классифицируй каждую задачу по признакам из карты. Сводка соответствий:

| Тип задачи | Признаки | Гранулярность | Подпапка (в `<сервис>-docs/`) | Префикс файла |
|---|---|---|---|---|
| **Screen** | Описание ОДНОГО экрана (страницы) UI и всех вызываемых на нём API-методов | **1 экран = 1 задача = 1 обзорный документ** (зонтичная задача) | `screens` | `screen_` |
| **API** | Описание ОДНОГО REST/GraphQL/gRPC эндпоинта (атомарной единицы API) | **1 эндпоинт = 1 задача** | `api` | `api_` |
| **Integration** | Взаимодействие с ОДНИМ внешним сервисом/партнёром (исходящее или входящее): протокол, эндпоинт, передаваемые данные, маппинг | **1 интеграция = 1 задача = 1 документ** | `integrations` | `integration_` |
| **DataTrace** | Трассировка данных от входа до хранилища, lineage полей, анализ трансформаций | По смыслу / лимиту токенов | `data_trace` | `data_trace_` |
| **Architecture** | C4-диаграммы, описание компонентов, слои сервиса | По смыслу / лимиту токенов | `architecture` | `architecture_` |
| **ERD** | Структура БД/схемы: таблицы, колонки, связи, ограничения (DDL/миграции) | По схеме / бизнес-домену БД | `erd` | `erd_` |
| **Process** | Сквозной бизнес-процесс через компоненты/сервисы: участники, шаги, ветвления | По смыслу / лимиту токенов | `processes` | `process_` |
| **Mindmap** | Карта погружения «от общего к частному» (PlantUML `@startmindmap`): одна ось группировки, действия Чтение/ЗАПИСЬ, каналы, трассируемые атомы | **1 сервис = 1–2 карты по разным осям** (не на каждую сущность) | `mindmaps` | `mindmap_` |

> ⛔ **Интеграционные взаимодействия больше НЕ классифицируются как Architecture.** Каждая интеграция сервиса с внешним партнёром — отдельная задача типа **Integration**. Владелец документа — анализируемый сервис (инициатор/клиент): документ живёт в `integrations/` папки ЭТОГО сервиса.

> **Правило для задач типа Screen (экран = зонтичная задача):**
> Когда цель пользователя — «описать экран и все вызываемые на нём API-методы», заведи задачу типа **Screen**. Такая задача:
> 1. **Зонтичная.** Она порождает ОДИН обзорный документ-индекс экрана (папка `screens/`) и набор подзадач типа **API** — по одной на каждый атомарный эндпоинт, вызываемый на экране (правило «1 эндпоинт = 1 задача» сохраняется).
> 2. **Обзорный документ НЕ дублирует методы.** В документе `screens/screen_*.md` — только сводная карта методов со ссылками на их документы в `api/`, маршруты экрана, сквозной флоу и общие пруфы. Детальные параметры/маппинг полей живут в API-документах подзадач.
> 3. **Переиспользование (reuse).** Если метод экрана уже документируется на другом экране — не дублируй API-задачу: в карте методов укажи ссылку на документ-владелец (колонка «Владелец»).
> 4. **Экран без собственных методов.** Если все методы экрана — reuse, задача Screen остаётся (порождает только обзорный документ), новых API-подзадач не создаётся.

**Формат имени файла:**

- Для **Screen**: `screen_<человекочитаемое_название_экрана>.md` — имя по типу/назначению экрана, НЕ по роуту и НЕ с префиксом `api_` (например: `screen_main_page.md`, `screen_search.md`). Имя описывает экран, а не отдельный эндпоинт.
- Для **Integration**: `integration_<партнёр>_<назначение>.md`, где `<партнёр>` — имя внешней системы из конфигурации/`System_Ext` C4, нормализованное (kebab → snake). Если у партнёра одна интеграция — допустимо `integration_<партнёр>.md`. При коллизии (два направления с одним партнёром) — добавь суффикс направления: `_in` (входящая) / `_out` (исходящая).
- Для **ERD**: `erd_<домен_или_схема>.md`; при полном покрытии БД — `erd_<имя_бд>.md`.
- Для **Process**: `process_<человекочитаемое_название>.md` — по типу Screen: имя описывает процесс, а не эндпоинт.
- Для **Mindmap**: `mindmap_<ось>_<область>.md` (например: `mindmap_ui_gates.md`, `mindmap_objects.md`, `mindmap_integrations.md`); карта связи сервисов — `mindmap_link_<svc-x>_<svc-y>.md`; части декомпозиции большой карты — `mindmap_<название>_partN.md` (та же задача, отдельные задачи на части не заводятся).
- Для **DataTrace** и **Architecture**: `<префикс>_<человекочитаемое_название>.md` (например: `data_trace_order_status.md`, `architecture_c4_overview.md`).
- Для **API**: `api_<нормализованный_роут>.md`. Имя файла детерминированно выводится из роута эндпоинта по алгоритму нормализации:
  a. Отбрось ведущий `/`.
  b. Замени остальные `/` на `_`; отбрось завершающий `/`.
  c. Параметры пути вида `{id}` заменяй на `by_<param>` (например, `{id}` → `by_id`).
  d. При коллизии путей с разными HTTP-методами — добавь метод суффиксом (`_get`, `_post`).
  e. Добавь префикс `api_` и расширение `.md`.

  **Примеры преобразования роут → имя файла:**
  - `GET /api/shows/search/` → `api_shows_search.md`
  - `POST /search/autocompleteMore/` → `api_search_autocomplete_more.md`
  - `GET /api/shows/{id}` → `api_shows_by_id.md`
  - Коллизия `GET /api/show/filter/` и `POST /api/show/filter/` → `api_show_filter_get.md` и `api_show_filter_post.md`

  **Для не-REST контрактов:** GraphQL — `api_<query_name>.md` (по имени query/mutation); gRPC — `api_<service>_<method>.md`.

**Формат задачи:**

```
[ID] Название задачи (например: "Чтение данных по Show")

Бизнес-цель: (Описать понятным языком, что делает этот узел).

Сервис: <сервис> (папка sa_documentation/<сервис>-docs/)

Тип задачи: (Screen | API | Integration | DataTrace | Architecture | ERD | Process | Mindmap)

Необходимый контекст (Файлы):
**Global Context:** Какие архитектурные принципы или общие файлы (конфиги, интерфейсы) должны быть в памяти.

**Local Context:** Список конкретных путей к файлам, которые содержат логику этой задачи.
[ ] path/to/config (Global)
[ ] path/to/service (Local)
[ ] path/to/entity (Data)

**Связи для проверки:** (На что обратить внимание, чтобы не соврать, например: "Проверить маппинг поля status_id в коде vs status_name в БД").

**Шаблон результата:** sa_documentation/<сервис>-docs/<подпапка>/<префикс>_<название>.md
```

#### Навигационная группировка задач типа API

При атомарной нарезке API-задач (1 эндпоинт = 1 задача) их число растёт. Чтобы сохранить обзорность `tasks.md` и не дублировать контекст, применяй навигационную группировку:

1. **Заголовки-секции (функциональные блоки).** Логически связанные атомарные API-задачи (эндпоинты одного экрана, контроллера или домена) объединяй под общим Markdown-заголовком-секцией.
   a. Заголовок-секция НЕ имеет собственного `[ID]` задачи.
   b. Заголовок-секция НЕ порождает документ и НЕ передаётся в `/create-doc` — он служит только для навигации по плану.
2. **Общий Global Context на уровне секции.** Чтобы не дублировать одинаковый Global Context в каждой атомарной задаче:
   a. Опиши Global Context (конфиги роутинга, базовый контроллер, общие интерфейсы) ОДИН раз на уровне секции-блока.
   b. Внутри атомарных задач секции в поле `Global Context` ставь ссылку «см. Global Context секции», а перечисляй только `Local Context` — файлы конкретного эндпоинта.
   c. Внутри секции `## Сервис: <сервис>` поле `Сервис` задачи можно опустить — сервис задаётся заголовком секции. Поля `Бизнес-цель` и `Связи для проверки` обязательны в каждой задаче.
3. **Группировка не отменяет атомарность.** Каждая атомарная задача внутри секции сохраняет свой `[ID]`, `Тип задачи: API` и `Шаблон результата` → `/create-doc` по-прежнему генерирует ОДИН документ на один эндпоинт.
4. **Секция-экран = задача типа Screen.** Если секция группирует методы одного экрана и пользователь хочет получить обзорный документ экрана, оформи заголовок секции как полноценную зонтичную задачу `[ID]` с `Тип задачи: Screen` и `Шаблон результата` → `sa_documentation/<сервис>-docs/screens/screen_<название>.md`. В этом случае секция-экран И группирует API-подзадачи (навигация + общий Global Context), И сама порождает обзорный документ-индекс экрана. Атомарные API-подзадачи внутри сохраняют свои `[ID]` и `Тип задачи: API`.
5. **Группировка по сервисам.** В едином `tasks.md` группируй задачи по сервисам заголовками верхнего уровня (`## Сервис: <сервис>`); ID остаются глобально уникальными.

**Пример навигационной группировки:**

```
## Сервис: svc-a

### Блок: Экраны «Поиск» (контроллеры SearchController, ShowsController)

**Global Context секции:**
[ ] path/to/router/search (Global)
[ ] path/to/base/Controller (Global)

#### [T7.1] GET /api/shows/search/ — поиск мероприятий
Бизнес-цель: пользователь находит мероприятия по поисковому запросу.
Тип задачи: API
Global Context: см. Global Context секции
**Local Context:**
[ ] path/to/ShowsController (Local)
**Связи для проверки:** маппинг полей ответа (title, city) на колонки таблицы shows.
**Шаблон результата:** sa_documentation/svc-a-docs/api/api_shows_search.md

#### [T7.2] POST /search/autocompleteMore/ — подсказки поиска
Бизнес-цель: пользователь получает подсказки при вводе поискового запроса.
Тип задачи: API
Global Context: см. Global Context секции
**Local Context:**
[ ] path/to/SearchController (Local)
**Связи для проверки:** источник подсказок — поисковый индекс или БД.
**Шаблон результата:** sa_documentation/svc-a-docs/api/api_search_autocomplete_more.md
```

### Этап 3: Генерация задач — Режим А «Один сервис»

1. **API:** каждая строка `api_map.md` = ровно одна задача типа API.
2. **Screen:** зоны UI из роутов фронтенда/шаблонов; экран-зонтик + API-подзадачи (reuse — ссылкой).
3. **Integration:** каждый внешний партнёр/направление = одна задача.
4. **DataTrace:** ключевые трассы полей (вход → хранилище).
5. **Architecture:** C4-обзор + при необходимости по компонентным блокам.
6. **ERD:** по схеме/домену БД.
7. **Process:** основные сквозные бизнес-процессы.
8. **Mindmap:** карта погружения сервиса «от общего к частному»; ось — из цели промта (правила выбора оси — скилл `mindmap-cartographer`); при большом сервисе или явном запросе — вторая задача по другой оси.
9. Закрой Coverage Gate (Этап 5): по каждому типу — задачи ИЛИ запись «не применимо + причина».

### Этап 4: Генерация задач — Режим Б «Взаимосвязь сервисов»

Задачи всех 8 типов, но нацелены на **определение и документирование связей** из реестра (Этап 1 п.5). Внутренние аспекты, не относящиеся к связи, НЕ планируются.

| Тип | Задача на связь X↔Y | Владелец (папка) | Имя файла |
|---|---|---|---|
| **Integration** | Каждое направленное взаимодействие X→Y = одна задача: партнёр, протокол, физический эндпоинт, маппинг «наш ↔ партнёр», ошибки. Обратные вызовы Y→X — отдельные задачи | Инициатор вызова | `integration_<партнёр>_<назначение>.md` (два направления → `_in`/`_out`) |
| **API** | Точки контакта: эндпоинты Y, вызываемые X (по api_map Y + клиентский код X) — **только для сервисов workspace**; точки контакта с внешними системами — это Integration, не API | Провайдер эндпоинта (где контроллер) | `api_<нормализованный_роут>.md` по общему алгоритму |
| **Screen** | Экраны, где взаимодействие инициируется или его данные отображаются | Сервис фронтенда | `screen_<название>.md` + обычные зонтичные правила |
| **DataTrace** | Трасса поля через границу — по одному плечу на сервис: «вход X → исходящий вызов» в X и «входящий эндпоинт Y → таблица» в Y, перекрёстные ссылки в «Связи для проверки» | Каждое плечо — свой сервис | `data_trace_<сущность>_<плечо>.md` |
| **Architecture** | Контекстная диаграмма взаимодействия (C4 C1/C2): X, Y, контракт между ними, внешние системы вокруг пары | Инициатор связи / «главный» сервис из промта (неоднозначно → спроси) | `architecture_context_<svc-x>_<svc-y>.md` |
| **ERD** | Сопоставление моделей сущности на стыке (заказ в x_db ↔ проекция в y_db): маппинг полей, расхождения, дубли | Сервис-источник сущности (мастер-данные); при неопределённости — инициатор | `erd_<сущность>_cross_<svc-x>_<svc-y>.md` |
| **Process** | Сквозной процесс через X и Y: участники, шаги с привязкой к коду обоих сервисов, ветвления | Сервис первого шага процесса | `process_<название>.md` |
| **Mindmap** | Карта погружения связи X↔Y: ось = точки контакта/направления обмена; элементы = обмены с атомами обеих сторон (метод/SQL у X и Y) | Инициатор связи; симметричная/неясная связь — «главный» сервис из промта (неоднозначно → спроси) | `mindmap_link_<svc-x>_<svc-y>.md` |

**Разграничение дублей:** Integration описывает **контракт** (что и как передаётся); DataTrace-плечи — **путь полей внутри каждого сервиса**; Process — **порядок шагов**. Один и тот же обмен данными правомерно порождает все три документа без дублирования содержания.

Если реестр связей пуст — выведи предупреждение: проверь имена сервисов, собери контекст партнёра (`/context-gen`) или перейди в Режим А.

### Этап 5: Coverage Gate — полнота покрытия типов

После генерации заполни раздел `## Покрытие типов (Coverage Gate)` в tasks.md (сразу после шапки):

> Правило: каждый из 8 реверс-типов `type_map.md` в рамках области покрыт задачами ИЛИ явно помечен «не применимо» с причиной. Молчаливое отсутствие типа запрещено. Gate относится к задачам плана, НЕ к папкам: категории в `<сервис>-docs/` создаются командами генерации по мере появления документов.

| Область | Тип | Статус | Задачи / причина неприменимости |
|---|---|---|---|
| svc-a | Screen | ✅ | [T2.1]–[T2.9] (9 экранов по роутам фронтенда) |
| svc-a | API | ✅ | [T1.1]–[T1.24] — сверено с api_map.md (24 строки) |
| svc-a | Mindmap | ✅ | [T8.1] — карта погружения по UI-экранам |
| svc-a | ERD | ⛔ не применимо | фронтенд-репозиторий без собственной БД: нет DDL/миграций/ORM; данные через API svc-a |

- **Область** = сервис (Режим А) или `svc-x ↔ svc-y` (Режим Б).
- Причина неприменимости — проверяемая по коду (что искали и не нашли: «нет UI-роутов и шаблонов», «нет DDL/миграций/ORM — сервис stateless», «нет исходящих вызовов и внешних входящих»), а не «показалось ненужным». В Режиме Б неприменимость = «нет точки контакта этого типа».
- В Режиме Б в плане обязательна ≥1 задача, чей предмет — сама связь (Integration или Architecture-контекст), иначе запуск режима бессмысленен.
- При дополнении таблица пересчитывается целиком по всем областям; ранее записанные «не применимо» сохраняются, если причина всё ещё валидна.

### Этап 6: Сверка полноты

1. **Режим А:** число задач типа API = числу строк `api_map.md` каждого сервиса прогона (минус строки, охваченные reuse-ссылками, и задачи, уже существующие с тем же «Шаблоном результата»). При расхождении — найди пропущенные эндпоинты и добавь задачи. **Режим Б:** сверяй по реестру связей (Этап 1 п.5) — каждая связь породила Integration-задачу, каждая точка контакта между сервисами workspace — API-задачу; полнота по всей `api_map.md` НЕ требуется.
2. Coverage Gate заполнен по всем 8 типам каждой области без пропусков.
3. `[ID]` глобально уникальны, нумерация продолжена; заголовки-секций `[ID]` не имеют.

### Этап 7: Запись tasks.md

1. Шапка: `# План документирования workspace` + таблица «Сервис | Папка документации» (при дополнении — сверь и дополни таблицу новыми сервисами).
2. Раздел `## Покрытие типов (Coverage Gate)`.
3. Секции `## Сервис: <сервис>`, внутри — навигационные секции и задачи в формате Этапа 2.
4. При дополнении: не изменяй существующие задачи и их статусы; новые задачи добавляй в конец секции соответствующего сервиса или новыми секциями сервиса.
