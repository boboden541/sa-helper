## Использование

```
/mindmap <аргумент>
```

**Параметры** (свободная форма, из которой извлекаются):

- **Сервис или задача:** `[T<N>]` — ID задачи из единого корневого `sa_documentation/tasks.md`, либо имя сервиса.
- **Тема/область** (опц.): «раздел Шлюзы», «загрузка данных через BI».
- **Ось** (опц.): «по экранам», «по объектам», «по интеграциям» — иначе выбирается по правилам методологии.
- **Режим** (опц.): As-Is (по умолчанию) / To-Be (только при наличии источника требований).
- **Цветовое измерение** (опц.): «риск касания uat_db» — иначе по правилам `mindmap_colors.md`.

## Примеры

**Пример №1 — по задаче из плана, ось задана:**

```
/mindmap [T9] карта погружения по экранам раздела «Шлюзы», As-Is
```

**Пример №2 — ad hoc, объектный разрез:**

```
/mindmap building-integrations по объектам: какие типы проходят через сервис и как грузятся в uat_db
```

**Пример №3 — ось не задана, «понять суть сервиса»:**

```
/mindmap ZION быстро понять, что это за сервис и куда он ходит за данными
```

## Важно

**Приоритет:** СТРОГОЕ следование навыку `.../skills/mindmap-cartographer/SKILL.md`, его эталонам (`examples/ideal_mindmap_ui_axis.md`, `examples/ideal_mindmap_object_axis.md`) и ресурсам (`resources/mindmap_methodology.md`, `resources/mindmap_colors.md`, `resources/mindmap_checklist.md`).

**Ожидаемый результат:** карта сохраняется в `sa_documentation/<сервис>-docs/mindmaps/mindmap_<название>.md` (части декомпозиции — `mindmap_<название>_partN.md`). Если папки `mindmaps` нет — создай её. Формат — ТОЛЬКО PlantUML `@startmindmap`; Mermaid запрещён. Соответствие «тип ↔ папка ↔ префикс» сверяется с картой типов `.../skills/doc-type-router/resources/type_map.md`.

**Прекондишены (мягкие):**

1. `sa_documentation/<сервис>-docs/repomix-output.xml` желателен; если его нет — предупреди в отчёте. Живой код как замена repomix допустим только при наличии хотя бы одного готового документа сервиса (см. п.2).
2. Если нет НИ repomix, НИ одного готового документа сервиса (`screens/`, `api/`, `integrations/`, `erd/`, `data_trace/`, `processes/`, `architecture/`, `api_map.md`) — СТОП: «Карте не из чего собираться. Сначала запусти /context-gen, затем /reverse-plan-tasks».
3. Если есть `api_map.md` — это реестр для проверки полноты оси.

## Инструкция для LLM

### Графовый контекст (complement-модель)

Граф дополняет repomix-output.xml и готовые документы, а не заменяет их. Используй источники одновременно:

- **Готовые документы** — главный источник подтверждённых фактов (см. Этап 3).
- **repomix-output.xml** — полный текст кода (SQL, SP-вызовы, конфиги) для пробелов.
- **MCP-инструменты** (если sa-helper-graph подключён) — структура и связи.

**Графовые запросы для данной команды:**

- `graph_schema` / `graph_arch_summary` — структура проекта (ось «домены/модули», реестр контроллеров)
- `graph_db_schema` — БД-объекты для атомов (таблицы, view, SP)
- `graph_query` — точечная проверка существования атома: `MATCH (n) WHERE n.name = $name RETURN labels(n), n.file`
- `graph_export` — подграф вокруг сервиса

> **Достоверность связей (`confidence`):** рёбра код→БД с `confidence='low'` или `source='inventory_resolver'` — выведенные (предположительные). Атом из такого ребра не попадает в карту как факт без подтверждения по фактическому SQL в `repomix-output.xml`; точными считай связи без `confidence` или с `confidence='high'`.

Если MCP-инструменты недоступны — пропусти графовые запросы, работай по документам и repomix.

### Этап 0: Сервис и задача (task vs ad hoc)

1. **П1 (задача):** если в аргументе есть `[T<N>]` — найди задачу в едином корневом `sa_documentation/tasks.md`, возьми сервис из полей **Сервис** / **Шаблон результата**, запомни `[ID]` для статуса (Этап 7) и **путь файла из «Шаблона результата»** — итоговая карта пишется именно по этому пути (Этап 7 п.1), как в `/create-doc`. Сверь **Тип задачи** = `Mindmap`: если тип другой — НЕ продолжай молча (Этап 7 изменит статус чужой задачи) — сообщи пользователю и уточни ID.
2. **Авто-задача:** ID в аргументе нет. Сначала определи сервис — по имени в аргументе, иначе по п.3/п.4 и вернись сюда. Затем посмотри в `tasks.md` задачи типа Mindmap этого сервиса со статусом ≠ ✅: ровно одна — используй её `[ID]` (и трассируй статус на Этапе 7); несколько — спроси одним сообщением, какую брать (ad hoc — только если пользователь откажется выбирать); ни одной — работай ad hoc.
3. **П2 (существующие папки):** папки `sa_documentation/*-docs/` — ровно одна: используй её молча; несколько: выбери по сервису из аргумента, иначе спроси пользователя.
4. **П3 (вывод):** имя папки анализируемого репозитория → kebab-case → подтверди у пользователя одной строкой → при необходимости создай `sa_documentation/<сервис>-docs/`.
5. **Ad hoc** (нет `[ID]` и подходящей задачи): карта создаётся без трассировки статуса в `tasks.md` (Этап 7 п.2 пропускается).

### Этап 1: Ось и рамка

1. Определи ось, режим (As-Is/To-Be), тему и цветовое измерение по каталогу осей и правилам `resources/mindmap_methodology.md` (раздел 1) и `resources/mindmap_colors.md`.
2. Выведи выбранную рамку в отчёт: «Ось: <…>; Режим: <…>; Тема: <…>; Цветовое измерение: <…>».
3. Если цель не различает двух кандидатов-осей — задай ОДИН вопрос пользователю ДО построения.

### Этап 2: Реестр осевых единиц

Составь полный перечень единиц выбранной оси — это эталон полноты для самопроверки (Этап 6) и валидации:

- **UI-экраны:** все экраны раздела — `screens/`, файлы роутинга фронтенда, `api_map.md`, задачи Screen в `tasks.md`.
- **Типы объектов:** `naming_conventions.md`, `erd/`, сущности кода.
- **Интеграции:** `integrations/`, конфиги базовых адресов.
- **Домены/процессы:** `architecture/`, `processes/`, граф (`graph_schema`).

### Этап 3: Сбор фактов (каскад, строго reuse-first)

1. `tasks.md` — какие документы существуют и их статусы (✅ / 🟡 / отсутствует).
2. **Готовые документы** (`screens/`, `api/`, `integrations/`, `data_trace/`, `erd/`, `processes/`, `architecture/`): статус ✅ — факт; 🟡 — факт с пометкой «не валидировано» в мете карты. Извлекай действия (Чтение/ЗАПИСЬ), каналы, атомы.
3. Контекст-артефакты: `api_map.md`, `naming_conventions.md`.
4. `repomix-output.xml` — ТОЛЬКО для единиц оси без готовых документов; долю таких фактов выведи в отчёт.
5. MCP-граф — сверка атомов и структуры (confidence-правила выше).
6. Живой код — последний fallback, с предупреждением в отчёте.

> Запрещено разведывать по коду то, что уже покрыто ✅-документом.

### Этап 4: Цветовое измерение

Выбери ОДНО измерение по `resources/mindmap_colors.md`: риск из цели промта → каноническое «касание критичного хранилища» (если сервис работает с несколькими хранилищами) → карта без цвета. Палитра — из канонической таблицы; legend обязательна при любом цвете.

### Этап 5: Построение карты

1. Строй уровни по контракту L0–L7 (`resources/mindmap_methodology.md`, раздел 2): корень `*[#LightCyan] <Сервис>` → ось L1 → нумерованные элементы L2 → действия `Чтение —`/`ЗАПИСЬ —` L3 → каналы L4 → опциональные под-шаги (только при реальном промежуточном уровне) → атом-лист (терминальный: обычно сразу под каналом на `******`, максимум `*******`). Состав уровней определяет ось (методология §2, правило 5): лестница «действие → канал» — для осей с действиями (UI и т.п.); у объектной оси под элементом L2 сразу атомы `****` без префиксов и каналов (эталон `ideal_mindmap_object_axis.md`).
2. Атомы — только подтверждённые, в канон-форматах (раздел 3 методологии).
3. Переполнение (> ~10–12 элементов L2 в группе, > ~400–500 строк блока) — декомпозиция part-N с серыми заглушками в основном файле (раздел 4).
4. Оформи документ-обёртку по эталону `examples/`: мета-строка, источники фактов со статусами и датой repomix-снапшота, plantuml-блок, «Пруфы и источники» с относительными ссылками.

### Этап 6: Самопроверка

Пройди `resources/mindmap_checklist.md` с явными ✅/❌ по каждому пункту (разделы А–Е). Ключевое: каждая единица реестра (Этап 2) присутствует в карте, вынесена в part-N или помечена `...` — молчаливых пропусков нет; легенда взаимно полна с цветами; синтаксис (`@startmindmap`/`@endmindmap`, `legend`/`end legend`, `[#HEX]` перед текстом узла) корректен. Проваленный пункт исправь до записи; если исправить нечего (факт не подтверждается ни одним источником) — НЕ выдумывай: убери элемент из карты или пометь `...`, сомнение зафиксируй в «Пруфах» как `[NEEDS_INVESTIGATION]` (политика скилла: исправляется ИЛИ фиксируется в отчёте).

### Этап 7: Запись и статус

1. Запиши файл **по пути из «Шаблона результата» задачи** (если работаешь по `[T<N>]`) — иначе `/validate-doc` не найдёт задачу по совпадению пути и не проставит ✅. Для ad hoc сформируй имя по канону: `sa_documentation/<сервис>-docs/mindmaps/mindmap_<ось>_<область>.md` (примеры: `mindmap_ui_gates.md`, `mindmap_objects.md`); карта связи сервисов — `mindmap_link_<svc-x>_<svc-y>.md`; части декомпозиции — `mindmap_<название>_partN.md`.
2. **Актуализируй единый корневой `sa_documentation/tasks.md`**: если работаешь по задаче `[T<N>]` — у задачи установи/обнови строку `> **Статус:** 🟡 Ожидает валидации` (замени существующую `> **Статус:**…` или добавь её под заголовком задачи). Если `tasks.md` нет или работаешь ad hoc — пропусти.
3. Выведи отчёт: рамка (ось/режим/цвет), источники фактов (сколько из ✅-документов, сколько из repomix/кода), самопроверка (✅/❌), дата repomix-снапшота, `[NEEDS_INVESTIGATION]`-список, если есть.
4. Финальное сообщение: «Карта погружения готова: <путь>. Запустите /validate-doc <путь>».
