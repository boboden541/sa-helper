## Использование

```
/impl-bootstrap <система> [FNR_N]
```

**Параметры:**

- `<система>` — имя системы из `workspaces.yaml` (ключ из `systems:`).
- `[FNR_N]` — необязательный номер задачи (например, `FNR_8`). С ним отчёт пишется в `sa_documentation/FNR/FNR_N/harness/`, без него — в `sa_documentation/harness_reports/<система>/`.

## Примеры

```
/impl-bootstrap ticketscloud FNR_8
```

```
/impl-bootstrap buildings-integration
```

## Важно

**Приоритет:** СТРОГОЕ соблюдение протокола v2 (`sa_documentation/harness/harness_by_v2.md`, §6.1). Агент не имеет права писать код в репозиторий, который не может собрать и протестировать. Baseline обязан быть снят **до** любых правок.

**Ожидаемый результат:** `bootstrap_report.md` со статусом `READY` / `READY_WITH_NOTES` / `STOP` и снимком baseline (сборка, тесты, количество).

**Универсальность:** Команда не привязана к конкретному стеку, БД или бизнес-домену. Сборка и тесты — всегда через команды из `workspaces.yaml` (по канону v2 — в Docker); инструменты harness — `python3` (Windows Git Bash: `python`).

## Инструкция для LLM

Ты — исполнитель контура реализации (роль: `.claude/skills/impl-harness/SKILL.md`). Задача шага — доказать, что система собирается и её тесты проходят, **пока в ней ещё ничего не менялось**.

### Графовый контекст (complement-модель)

Граф дополняет работу, а не заменяет её. Для bootstrap граф не нужен; если MCP-инструменты `sa-helper-graph` доступны — можно снять структурный outline системы (`graph_schema`, `graph_arch_summary`) как приложение к отчёту. Если недоступны — пропусти, это не влияет на вердикт.

### Этап 1: Реестр систем

1. Найди `workspaces.yaml` в корне воркспейса (каталог, где живёт `sa_documentation/`). Если файла нет — выполн discovery (Этап 1а) и вернись к шагу 1.
2. Прочитай запись `<система>` из `systems:`. Записи нет → остановись и покажи список доступных систем из файла.

### Этап 1а: Discovery (только если workspaces.yaml отсутствует)

1. Запусти сканер: `python3 harness/workspace_scan.py <корень воркспейса>`.
2. Покажи человеку сводную таблицу: система | стек | тесты | docker | черновик команд. Детект детерминированный, но команды-заглушки `TODO` требуют ручного уточнения — предложи заполнить их вместе (образы docker, скоуп тестов, prerequisites).
3. После явного подтверждения человека запиши файл в корень воркспейса. **Без подтверждения файл не создавать.**

### Этап 2: Предварительные условия

1. Docker доступен? (`docker version`). Недоступен → STOP с инструкцией запуска Docker Desktop.
2. Если при прогоне появится `error getting credentials` — это credential helper вне агентской сессии: повтори команду с `DOCKER_CONFIG` на каталог с пустым `config.json` (`{}`), публичные образы не требуют авторизации.
3. Проверь `prerequisites` из notes системы (если заполнены): VPN-зависимости, соседние репозитории (например, `settings.xml` рядом), учётные данные. Что не выполнено — перечисли в отчёте; если блокирует сборку — вердикт STOP (см. Этап 5).
4. `data_only: true` → пропусти Этапы 3–4, вердикт `READY (data-only)`.

### Этап 3: Сборка (baseline build)

1. Запусти: `python3 harness/runner.py --cwd <путь системы> --mode build --cmd "<build_cmd из workspaces.yaml>" --timeout <defaults.timeout_s> --log <каталог отчёта>/bootstrap_build.log`.
2. `exit_code == 0` → сборка зелёная. Иначе — вычлени причину из JSON (`error`, лог): ошибки зависимостей (`Could not resolve dependencies`, `No matching distribution`) → STOP с перечнем недостающих артефактов и подсказкой из notes; ошибки кода → STOP (репо сломано до нас — чинить вне задач harness нельзя).

### Этап 4: Тесты (baseline test)

1. `test_cmd` == `-` (тестов нет) → пометь в отчёте «no test suite»; правило «характеризационная задача первой» (v2 §7 п. 3) попадёт в план.
2. Иначе запусти `runner.py --mode test --cmd "<test_cmd>"` (плюс `--junit <junit_glob>`, если задан; отчёта нет — runner сам вернётся к stdout-парсингу).
3. Зафиксируй снимок: `summary` (passed/failed/errors/skipped) и список падений (сокращённо, до 20 строк). Красный baseline — не STOP: это честная точка отсчёта; но задачи плана не должны опираться на падающие чужие тесты без оговорки (v2 §6.1).

### Этап 5: Отчёт и вердикт

Сохрани `bootstrap_report.md` (путь по параметру FNR_N, см. Использование):

```markdown
# Bootstrap: <система> (<FNR_N | baseline>)

**Вердикт:** READY | READY_WITH_NOTES | STOP | READY (data-only)
**Дата:** <ISO> · **Ветка:** <текущая> · **Коммит:** <hash>

## Сборка
<команда> → exit 0, <N>s | <причина отказа>

## Тесты (baseline)
<команда> → passed=X failed=Y errors=Z skipped=W (длительность)
<список падений, если есть>

## Замечания и prerequisites
<что нужно человеку: VPN, settings.xml, сервисы, образы>

## Следующий шаг
< READY → «/impl-plan <путь к system_requirements.md>» >
< STOP → что должен сделать человек >
```

Веди `manifest.json` (если контур уже начат): статус системы в `bootstrap`: `ready|ready_with_notes|stop`.

Завершение: выведи вердикт и путь отчёта. При READY — литеральную подсказку: «Система готова. Следующий шаг: /impl-plan <system_requirements.md>». При STOP — перечень действий человека без продвижения контура.
