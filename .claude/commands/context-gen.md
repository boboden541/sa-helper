## Использование

```
/context-gen <context>
```

**Параметры:**

- `<context>` — описание цели того, что хочет сделать аналитик для документирования сервиса

## Примеры

**Пример №1**

```
/context-gen Я, как системный аналитик, должен провести revese-engineering текущего проекта. Мне нужно полностью задокументировать проект:
- Составить C4-диаграмму (до уровня C3), описать основные компоненты сервиса, описать базу данных, 
- Описать имеющиеся API-интерфейсы, которые предоставляет сервис, (один API = одна задача = один документ)
- Описать интеграционные взаимодействия данного сервиса с другими сервисами (одна интеграция = одна задача = один документ). 
- Описать способы взаимодействия данного проекта с базой данных (если есть)
```

**Пример №2**

```
/context-gen Я хочу задокументировать архитектуру проектап и создать C4-диаграмму.
```

## Важно

## Величина контекста

**Целевой лимит:** $800,000$ токенов

**Критический порог:** $1,200,000$ токенов

## Правила фильтрации контекста

Исключать из анализа:

1. **Boilerplate:** Автогенерируемые файлы миграций, логи, временные файлы.
2. **Vendor Bloat:** Папки `node_modules`, `vendor`, `dist`.
3. **Test Data:** Моки и фикстуры, если задача не касается тестирования.
4. **Assets:** Картинки, шрифты, скомпилированный CSS/JS.

## На выходе ожидается

- Созданная папка `sa_documentation`
- Файл `repomix-output.xml` (Контекст проекта)
- Файл `.repomixignore`
- Файл `sa_documentation/tasks.md` (Список декомпозированных задач для документирования)
- Файл `sa_documentation/naming_conventions.md` (Словарь соответствия кода и бизнеса)

**Иные файлы не создавать!**

## Инструкция для LLM

### Этап 0: Подготавливаем директории для работы

1. Создай папку .../sa_documentation.

### Этап 1: Инициализация и первичный замер

1. Запусти ```repomix --no-files```
2. Проанализируй раздел ```Pack Summary``` (Total Tokens) и ```Top 5 Files by Token Count```

### Этап 1.5: Графовая фильтрация (complement-модель)

Если MCP-инструменты доступны (sa-helper-graph подключён):
1. Вызови `graph_select_files` с параметром `task_description="<описание задачи пользователя>"` — инструмент вернёт JSON-массив релевантных путей
2. Из JSON-массива путей сформируй glob-паттерн для repomix: оберни список в фигурные скобки через запятую. Пример: для `["src/controllers/UserController","src/services/OrderService"]` получится `"{{src/controllers/UserController,src/services/OrderService}}"`
3. При запуске repomix на Этапе 2 передай этот glob в флаг `--include`, например: `repomix --style xml --output repomix-output.xml --include "{src/controllers/UserController,src/services/OrderService}"`
4. Если MCP-инструмент недоступен или вернул пустой массив — продолжай без фильтрации (repomix упакует все файлы без флага --include)

### Этап 2: Петля оптимизации (Intelligent Trimming Loop)

**Если** ```Total Tokens``` > $1,000,000$:

1. Изучи список самых тяжелых файлов в Summary.
2. Определи, являются ли они бизнес-логикой. Если это библиотеки, логи, тяжелые стили или сгенерированные файлы — Создай или дополни .repomixignore, добавив их пути в .repomixignore.
3. **ВАЖНО:** Если тяжелым является файл с бизнес-логикой (например, сервисный файл на 200k токенов), не игнорируй его, но ищи другие пути сокращения (например, исключи папки с тестами или документацией внутри проекта).
4. Повтори запуск repomix --summary-only и проверь новый результат.
5. Продолжай цикл до тех пор, пока объем не станет < $1,000,000$ токенов или пока не останутся только критически важные файлы.

### Этап 3: Финальная сборка

1. Только после прохождения проверки лимитов запусти: ```repomix --style xml --output repomix-output.xml```.
2. Если даже после очистки объем $> 1,200,000$ токенов, выведи предупреждение пользователю: "Внимание: проект очень крупный. Планирование может быть менее точным".
3. Файл должен быть перенесен в ранее созданную папку /sa_documentation/repomix-output.xml и удален из корня проекта, где он изначально создавался

#### Этап 3.1: Картирование публичного API

1. Найди файлы конфигурации роутинга.
2. Составь таблицу: `Внешний URL` -> `Внутренний контроллер/метод`.
3. Сравни этот список со списком файлов в `repomix-output.xml`.
4. Если обнаружен "скрытый" эндпоинт (как announcement -> ads), принудительно добавь его в `naming_conventions.md` и выдели под него задачу в `tasks.md`.

> **Эта таблица — источник истины для нарезки задач типа API на Этапе 4.** Каждая строка таблицы (одна атомарная единица API) порождает ровно ОДНУ задачу типа API. Контроль полноты (сверка): после планирования (Этап 4) число задач типа API должно равняться числу строк этой таблицы. При расхождении — найди пропущенные эндпоинты и добавь недостающие задачи.

### Этап 4: Интеллектуальное планирование

1. Прочитай итоговый ```/sa_documentation/repomix-output.xml```
2. Используя универсальные паттерны из `resources/architecture_patterns.md`, определи ключевые слои (Controllers, Services, DAO).
3. Создай файл ```/sa_documentation/tasks.md```, распределим задачи так, чтобы файлы в одной задаче суммарно не превышали $100,000$ токенов.

> **Правило атомарности задач типа API (приоритетнее лимита токенов):**
> Для задач типа **API** действует принцип «один API = одна задача = один документ». Каждая строка таблицы картирования (Этап 3.1) = отдельная атомарная задача типа API. **Лимит токенов (100 000) НЕ может служить причиной объединения нескольких эндпоинтов в одну задачу.** Лимит токенов применяется к API-задачам только как критерий ДРОБЛЕНИЯ контекста: если контекст одного эндпоинта сам по себе превышает лимит — раздроби список файлов контекста, но не объединяй эндпоинты.
>
> **Атомарная единица API** определяется по типу контракта:
> - **REST** — отдельный эндпоинт (HTTP-метод + путь).
> - **GraphQL** — отдельный query или mutation (единый транспортный эндпоинт `/graphql` НЕ является атомарной единицей).
> - **gRPC** — отдельный метод сервиса.
>
> Для задач типа **DataTrace** и **Architecture** правило атомарности НЕ применяется — допустима группировка по смыслу/лимиту токенов.

#### Правило классификации задач по типу документа

Для каждой задачи определи её **тип** и соответствующую подпапку:

| Тип задачи | Признаки | Гранулярность | Подпапка | Префикс файла |
|---|---|---|---|---|
| **Screen** | Описание ОДНОГО экрана (страницы) UI и всех вызываемых на нём API-методов: обзорная карта экрана, маршруты, фронтенд, сквозной флоу | **1 экран = 1 задача = 1 обзорный документ** (зонтичная задача, см. правило ниже) | `screens` | `screen_` |
| **API** | Описание ОДНОГО REST/GraphQL/SOAP эндпоинта (одной атомарной единицы API) | **1 эндпоинт = 1 задача** (атомарно, см. правило атомарности выше) | `api` | `api_` |
| **DataTrace** | Трассировка данных от входа до хранилища, lineage полей, анализ трансформаций | По смыслу / лимиту токенов | `data_trace` | `data_trace_` |
| **Architecture** | C4-диаграммы, описание компонентов, интеграционные взаимодействия между сервисами | По смыслу / лимиту токенов | `architecture` | `architecture_` |

> **Правило для задач типа Screen (экран = зонтичная задача):**
> Когда цель пользователя — «описать экран и все вызываемые на нём API-методы», заведи задачу типа **Screen**. Такая задача:
> 1. **Зонтичная.** Она порождает ОДИН обзорный документ-индекс экрана (папка `screens/`) и набор подзадач типа **API** — по одной на каждый атомарный эндпоинт, вызываемый на экране (правило «1 эндпоинт = 1 задача» сохраняется, см. правило атомарности выше).
> 2. **Обзорный документ НЕ дублирует методы.** В документе `screens/screen_*.md` — только сводная карта методов со ссылками на их документы в `api/`, маршруты экрана, сквозной флоу и общие пруфы. Детальные параметры/маппинг полей живут в API-документах подзадач.
> 3. **Переиспользование (reuse).** Если метод экрана уже документируется на другом экране — не дублируй API-задачу: в карте методов укажи ссылку на документ-владелец (колонка «Владелец»). Это тот же принцип дедупликации, что и для API-задач.
> 4. **Экран без собственных методов.** Если все методы экрана — reuse, задача Screen остаётся (порождает только обзорный документ), новых API-подзадач не создаётся.

**Формат имени файла:**

- Для **Screen**: `screen_<человекочитаемое_название_экрана>.md` — имя по типу/назначению экрана, НЕ по роуту и НЕ с префиксом `api_` (например: `screen_main_page.md`, `screen_search.md`, `screen_shopcart.md`, `screen_building.md`). Имя описывает экран, а не отдельный эндпоинт.
- Для **DataTrace** и **Architecture**: `<префикс>_<человекочитаемое_название>.md` (например: `data_trace_order_status.md`, `architecture_c4_overview.md`).
- Для **API**: `api_<нормализованный_роут>.md`. Имя файла детерминированно выводится из роута эндпоинта по алгоритму нормализации:
  a. Отбрось ведущий `/`.
  b. Замени остальные `/` на `_`; отбрось завершающий `/`.
  c. Параметры пути вида `{id}` заменяй на `by_<param>` (например, `{id}` → `by_id`).
  d. При коллизии путей с разными HTTP-методами — добавь метод суффиксом (`_get`, `_post`).
  e. Добавь префикс `api_` и расширение `.md`.

  **Примеры преобразования роут → имя файла:**
  - `GET /api/shows/search/` → `api_shows_search.md`
  - `POST /search/autocompleteMore/` → `api_search_autocomplete_more.md`
  - `GET /api/shows/{id}` → `api_shows_by_id.md`
  - Коллизия `GET /api/show/filter/` и `POST /api/show/filter/` → `api_show_filter_get.md` и `api_show_filter_post.md`

  **Для не-REST контрактов:** GraphQL — `api_<query_name>.md` (по имени query/mutation); gRPC — `api_<service>_<method>.md`.

Каждая задача должна иметь следующий вид:

```
[ID] Название задачи (например: "Чтение данных по Show")

Бизнес-цель: (Описать понятным языком, что делает этот узел).

Тип задачи: (Screen | API | DataTrace | Architecture)

Необходимый контекст (Файлы):
**Global Context:** Какие архитектурные принципы или общие файлы (конфиги, интерфейсы) должны быть в памяти.

**Local Context:** Список конкретных путей к файлам, которые содержат логику этой задачи.
[ ] path/to/config (Global)
[ ] path/to/service (Local)
[ ] path/to/entity (Data)

**Связи для проверки:** (На что обратить внимание, чтобы не соврать, например: "Проверить маппинг поля status_id в коде vs status_name в БД").

**Шаблон результата:** sa_documentation/<подпапка>/<префикс>_<название>.md
```

#### Навигационная группировка задач типа API

При атомарной нарезке API-задач (1 эндпоинт = 1 задача) их число растёт. Чтобы сохранить обзорность `tasks.md` и не дублировать контекст, применяй навигационную группировку:

1. **Заголовки-секции (функциональные блоки).** Логически связанные атомарные API-задачи (эндпоинты одного экрана, контроллера или домена) объединяй под общим Markdown-заголовком-секцией.
   a. Заголовок-секция НЕ имеет собственного `[ID]` задачи.
   b. Заголовок-секция НЕ порождает документ и НЕ передаётся в `/create-doc` — он служит только для навигации по плану.
2. **Общий Global Context на уровне секции.** Чтобы не дублировать одинаковый Global Context в каждой атомарной задаче:
   a. Опиши Global Context (конфиги роутинга, базовый контроллер, общие интерфейсы) ОДИН раз на уровне секции-блока.
   b. Внутри атомарных задач секции в поле `Global Context` ставь ссылку «см. Global Context секции», а перечисляй только `Local Context` — файлы конкретного эндпоинта.
3. **Группировка не отменяет атомарность.** Каждая атомарная задача внутри секции сохраняет свой `[ID]`, `Тип задачи: API` и `Шаблон результата` → `/create-doc` по-прежнему генерирует ОДИН документ на один эндпоинт.
4. **Секция-экран = задача типа Screen.** Если секция группирует методы одного экрана и пользователь хочет получить обзорный документ экрана, оформи заголовок секции как полноценную зонтичную задачу `[ID]` с `Тип задачи: Screen` и `Шаблон результата` → `sa_documentation/screens/screen_<название>.md`. В этом случае секция-экран И группирует API-подзадачи (навигация + общий Global Context), И сама порождает обзорный документ-индекс экрана. Атомарные API-подзадачи внутри сохраняют свои `[ID]` и `Тип задачи: API`.

**Пример навигационной группировки:**

```
## Блок: Экраны «Поиск» (контроллеры SearchController, ShowsController)

**Global Context секции:**
[ ] path/to/router/search (Global)
[ ] path/to/base/Controller (Global)

### [T7.1] GET /api/shows/search/ — поиск мероприятий
Тип задачи: API
Global Context: см. Global Context секции
**Local Context:**
[ ] path/to/ShowsController (Local)
**Шаблон результата:** sa_documentation/api/api_shows_search.md

### [T7.2] POST /search/autocompleteMore/ — подсказки поиска
Тип задачи: API
Global Context: см. Global Context секции
**Local Context:**
[ ] path/to/SearchController (Local)
**Шаблон результата:** sa_documentation/api/api_search_autocomplete_more.md
```

# Этап 5: Формирование словаря системы (Naming Conventions)

1. На основе анализа кода в XML выдели ключевые бизнес-сущности.
2. «Скан конфигов: Перед формированием таблицы маппинга, сопоставь публичные URL-пути из файлов конфигурации с именами контроллеров. Если название в URL (напр. announcement) отличается от названия в коде (Ads), в словарь должны попасть оба термина с пометкой 'Public Alias'».
3. Создай файл `/sa_documentation/naming_conventions.md`.
4. Заполни его таблицей соответствия. Используй логику:
   - **Понятие:** Как это называть в документах (напр., "Заказ").
   - **Технический термин:** Как это называется в коде (напр., `STOrder`, `UserBasket`).
   - **Описание:** Краткая суть сущности.
5. Добавь раздел "Запрещенные синонимы", чтобы избежать путаницы (например, если в коде "Client", а по бизнесу это "User").
