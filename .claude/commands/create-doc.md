## Использование

```
/create-doc <task_id and description>
```

**Параметры:**

- `<task_id and description>` — ID задачи из файла /sa_documentation/tasks.md и ее описание

## Примеры

```
/create-doc [1.1] Архитектура DAO и низкоуровневый доступ к БД
**Необходимый контекст (Файлы):**
- [ ] `config/database.yml` (Global)
- [ ] `src/db/connection.py` (Global)
- [ ] `src/db/query_builder.py` (Local)
- [ ] `src/repositories/item_repository.py` (Data)
```

## Важно

**Приоритет:** СТРОГОЕ соблюдение структуры из шаблона, **соответствующего типу задачи** (см. «Маршрутизация по типу задачи» ниже), и нотации из `resources/standard_mapping.md`.

**Ожидаемый результат**:  Все документы создаются в `sa_documentation/<подпапка>/` с человекочитаемым именем файла. Подпапка, шаблон и имя файла определяются полем **Тип задачи** и **Шаблон результата** из `tasks.md`.

### Маршрутизация по типу задачи (folder + template)

Перед генерацией определи тип документа по полю **Тип задачи** в `tasks.md` и выбери подпапку и эталонный шаблон:

| Тип задачи | Подпапка | Эталонный шаблон | Что генерируется |
|---|---|---|---|
| **Screen** | `sa_documentation/screens/` | `examples/ideal_screen_document.md` | Обзорный индекс экрана: карта методов (ссылки на API-документы), маршруты, сквозной Sequence, общие пруфы. **Детальные параметры методов НЕ дублируются.** |
| **API** | `sa_documentation/api/` | `examples/ideal_api_document.md` | Полное описание одного эндпоинта: вход/выход, маппинг полей, диаграммы, якоря истины. |
| **DataTrace** | `sa_documentation/data_trace/` | `examples/ideal_api_document.md` (адаптируется под трассировку) | Lineage полей от входа до хранилища. |
| **Architecture** | `sa_documentation/architecture/` | `examples/ideal_c4_l3.puml` + `resources/architecture_standards.md` | C4-описание/диаграмма компонентов. |

> **Источник истины по подпапке/имени — поле «Шаблон результата» задачи.** Если оно задано — используй путь оттуда. Таблица выше определяет, КАКОЙ шаблон открыть. При расхождении типа и пути доверяй явному пути из `tasks.md`, но шаблон бери по типу.

## Инструкция для LLM

### Графовый контекст (complement-модель)

Граф дополняет repomix-output.xml, а не заменяет его. Используй оба источника одновременно:

- **repomix-output.xml** — полный текст кода (реализации, SQL, комментарии)
- **MCP-инструменты** (если sa-helper-graph подключён) — структура и связи

**Графовые запросы для данной команды:**

- `graph_introspect` — реальные метки/свойства/связи графа перед запросами
- `graph_export` — подграф вокруг сущности (точки входа, связи)
- `graph_call_chain` — цепочка вызовов от функции
- `graph_impact` — зависимые компоненты сущности
- `graph_schema` — обзор структуры проекта

Если MCP-инструменты недоступны — пропусти графовые запросы, продолжай с repomix-output.xml.

**Правило достоверности связей (`confidence`):** в выводе `graph_impact`, `graph_db_impact`, `graph_db_lineage` каждая запись зависимости может содержать `confidence` (`low`/`medium`/`high`) и `source`. Рёбра с `source='inventory_resolver'` — **выведенные** (предположительные), а не точные.
- Связи с `confidence='low'` НЕ описывай в документации как установленный факт — либо пропусти, либо явно помечай как предположительные («предположительно использует …») и подтверждай по фактическому SQL в `repomix-output.xml`.
- Точными считай связи без `confidence` или с `confidence='high'`.

### Этап 1: Идентификация задачи и первичный сбор контекста

1. Открой файл `/.../tasks.md`.
2. Найди задачу с указанным `[ID] и описанием`.
3. Учти переданный список файлов для загрузки контекста или сформулируй его, используя разделы задачи **Global Context** и **Local Context**.
4. Прочитай содержимое этих файлов из `/sa_documentation/repomix-output.xml`.

### Этап 2: Полный сбор контекста и поиск "Якорей Истины"

    - **Anchor 1 (Config):** Найди файл конфигурации, содержащий базовый адрес (URL/Host/Topic).
    - **Anchor 2 (Contract):** Найди исходный артифакт, определяющий эндпоинт (Interface, Proto-файл, Swagger-client или аннотации контроллера).
    - **Anchor 3 (Model):** Найди файл определения DTO/Сущности, чтобы увидеть ПОЛНЫЙ список доступных полей, а не только те, что используются в текущем методе.
    - Запрещено приступать к генерации, пока не найдены минимум 2 из 3 анкоров.
    - **Определение топологии:** Прежде чем приступать к маппингу, найди в проекте документ или конфиг, являющийся SSoT (Single Source of Truth) для инфраструктуры. Установи канонические названия для каждой базы данных и внешнего сервиса, чтобы использовать их как префиксы в колонках Origin.

### Этап 3: Загрузка "Прошивки" (Skill & Standards) — ОБЯЗАТЕЛЬНО

1. Загрузи навык `.../technical-documentation/SKILL.md`.
2. Загрузи `.../resources/standard_mapping.md`.
3. **Загрузи и фактически ОТКРОЙ шаблон, СООТВЕТСТВУЮЩИЙ типу задачи** (см. таблицу маршрутизации в разделе «Важно»):
   - **Screen** → `.../examples/ideal_screen_document.md`;
   - **API** → `.../examples/ideal_api_document.md`;
   - **DataTrace** → `.../examples/ideal_api_document.md` (адаптируется под трассировку);
   - **Architecture** → `.../examples/ideal_c4_l3.puml` + `.../resources/architecture_standards.md`.

   Структура генерируемого документа берётся ИЗ ШАБЛОНА, а не из ранее
   созданных документов.
   ⛔ ЗАПРЕЩЕНО использовать другой готовый документ (`api_*.md`, `screen_*.md`) как образец
   структуры. Соседние документы могут содержать незамеченные дефекты;
   единственный источник истины по структуре — соответствующий типу эталонный шаблон.
4. Загрузи `.../resources/validation_checklist.md` — критерии качества
   учитываются ДО генерации, а не только при /validate-doc.

### Этап 4: Аналитическая работа (Reverse Engineering)

> **Для задач типа Screen** аналитика ведётся на уровне ЭКРАНА, а не отдельного поля:
> 1. **Каталог методов экрана.** Найди ВСЕ API-методы, вызываемые на экране (фронтенд: router-модуль, store, `_domain/*.api.ts`, ApiService; бэкенд: контроллеры экрана). Для каждого — `METHOD URL`, контроллер/экшен и имя его API-документа в `api/`.
> 2. **Reuse.** Отметь методы, документируемые на других экранах (владелец) — их выноси в таблицу reuse, отдельные API-задачи не дублируй.
> 3. **Маршруты экрана и фронтенд.** Зафиксируй внешний(ие) URL экрана и точки входа фронтенда.
> 4. **Сквозной флоу.** Восстанови последовательность вызовов по фазам (SSR preFetch → клиентская загрузка → интерактив) для общей Sequence-диаграммы.
> 5. **НЕ дублируй** детальные параметры/маппинг полей методов — они в API-документах подзадач. Шаги 2–6 ниже относятся к задачам типа API/DataTrace.

1. **Omnichannel трассировка роутинга:** Найди в коде ВСЕ точки входа (Web, SPA/REST, Mobile, CLI). Обязательно проверь файлы роутинга (`url_routes`, `routes`), чтобы показать, как внешний URL превращается во внутренний метод контроллера.
2. **Инспекция данных:** Для каждого поля в ответе метода найди путь до БД (`Table.Column`) или формулу вычисления.
3. **Анализ интеграций:** Найди вызовы внешних сервисов и зафиксируй передаваемые параметры. Обязательно укажи физический протокол (REST, SOAP, gRPC, AMQP) и извлеки точный адрес эндпоинта из конфигурационных файлов.
4. **Анализ паттернов ветвления (Branching & Scope):** Обязательно найди Фабрики (Factory), Стратегии (Strategy) или Middleware, которые кардинально меняют выполнение алгоритма в зависимости от контекста (Tenant/Channel/Role/Scope). Зафиксируй все ветки.
5. **Диаграммы:** Сгенерируй Sequence Diagram и Activity Diagram СТРОГО в формате **PlantUML**. Использование Mermaid запрещено для обеспечения единообразия и совместимости.

### Этап 5: Генерация документа

1. Определи путь к файлу из поля **Шаблон результата** в задаче (например: `sa_documentation/api/api_show_listing.md` или `sa_documentation/screens/screen_main_page.md`). Если подпапки нет — создай её.
2. Заполни документ строго по разделам **шаблона, выбранного на Этапе 3 по типу задачи**.

> **Ветка для задач типа Screen (шаблон `ideal_screen_document.md`):**
> - Заполни: заголовок-обзор, «Карту методов экрана» (со ссылками на API-документы в `api/`), таблицу reuse-методов, опциональную доменную карту, сквозную Sequence-диаграмму экрана и «Общие технические пруфы».
> - **Gate вложенных объектов (п. 6 ниже) НЕ применяется** — в обзорном документе экрана нет таблиц «Выходные параметры» с полями. Детальные параметры/маппинг живут в API-документах методов.
> - Ссылки на документы методов — относительные (`[api_x.md](api_x.md)`); если соответствующий API-документ ещё не создан, ссылка всё равно ставится (это план), но методы-reuse ведут на документ владельца.
> - Пути в «Общих технических пруфах» — строго ОТНОСИТЕЛЬНЫЕ от корня проекта.
> Шаги 3–6 ниже относятся к задачам типа API/DataTrace.

3. **Эндпоинты:** Пиши в техническом формате согласно `standard_mapping.md`.
4. **Маппинг:** Используй колонку Origin с указанием полных имен таблиц.
5. **Диаграммы:** Сгенерируй Sequence Diagram (UML) и диаграмму алгоритма (Activity).
6. **Gate вложенных объектов (перед сохранением раздела «Выходные параметры»):**
   Для КАЖДОГО поля ответа проверь его тип в коде (DTO/toArray):
   - скаляр → обычная строка таблицы;
   - объект → тип `Object<{DTO_Name}>`, Origin = `—`, плюс ОБЯЗАТЕЛЬНАЯ
     подтаблица `#### Описание вложенного {DTO_Name}`;
   - массив объектов → `Array<{DTO_Name}>` + подтаблица; массив скаляров → `Array<{scalar}>`.
   Голые `object`/`array`/`list` без параметра ЗАПРЕЩЕНЫ.
   Рекурсивно: вложенный объект внутри вложенного — своя подтаблица.
   ⛔ Не сохраняй документ, пока у каждого поля-контейнера нет парной подтаблицы.
   Если DTO вложенного объекта отсутствует в repomix — создай подтаблицу
   с пометкой [NEEDS_INVESTIGATION], но НЕ сворачивай поля в скобки основной строки.

### Этап 6: Завершение

1. **Актуализируй `sa_documentation/tasks.md`**: у задачи `[<ID>]` установи/обнови строку `> **Статус:** 🟡 Ожидает валидации` — замени существующую строку (начинающуюся с `> **Статус:**`) или добавь её сразу под заголовком задачи `[ID]`. Если `tasks.md` нет или `[ID]` неизвестен — пропусти.
2. Выведи сообщение: "Черновик документации [ID] готов. Теперь запустите команду `/validate-doc` для проверки точности данных."
