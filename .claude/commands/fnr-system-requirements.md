---

## Использование

```
/fnr-system-requirements <path_to_concept>
```

**Параметры:**

- `<path_to_concept>` — путь к файлу `concept.md` с вердиктом дебатов (`/fnr-debate`).

## Примеры

```
/fnr-system-requirements sa_documentation/FNR_1/concept.md
```

## Важно

**Приоритет:** СТРОГОЕ соблюдение структуры из `examples/ideal_system_requirements.md` (шаблон в стиле Confluence).

**Ожидаемый результат:** Документ сохраняется в папку FNR: `sa_documentation/FNR/FNR_<N>/system_requirements.md`. Описание каждой доработки — двухуровневое: «Общее описание доработки» (обзорный уровень) + «Описание доработок» (системно-аналитический уровень).

**Универсальность:** Команда не привязана к конкретному стеку, БД или бизнес-домену.

## Инструкция для LLM

### Графовый контекст (complement-модель)

Граф дополняет repomix-output.xml, а не заменяет его. Используй оба источника одновременно:
- **repomix-output.xml** — полный текст кода (реализации, SQL, комментарии)
- **MCP-инструменты** (если sa-helper-graph подключён) — структура и связи

**Графовые запросы для данной команды:**
- `graph_introspect` — реальные метки/свойства/связи графа перед запросами
- `graph_schema` — обзор структуры для заполнения As-Is (пагинирован: при `truncated=true` листай через `offset`)
- `graph_export` — детали компонента для затрагиваемых компонентов
- `graph_impact` — анализ зависимостей для обоснования задач

Если MCP-инструменты недоступны — пропусти графовые запросы, продолжай с repomix-output.xml.

### Этап 1: Загрузка роли

1. Прочитай `/system-analyst-sysreq/SKILL.md` — твоя персона и принципы работы.
2. Загрузи **контракт уровней изложения** из `.claude/skills/system-analyst-sysreq/resources/abstraction_levels.md` — нормативный источник уровней Л1/Л2/Л3, состава подразделов задачи, канона «Контракт API» и deny-списка.
3. Загрузи **основной шаблон** документа из `examples/ideal_system_requirements.md` — это шаблон в стиле Confluence.
4. Загрузи **канон API-таблиц** из `.claude/skills/technical-documentation/examples/ideal_api_document.md` — источник состава и вида таблиц для блоков «Контракт API».
5. Загрузи чек-лист валидации из `resources/sysreq_validation_checklist.md`.

### Этап 2: Сбор контекста проекта

1. Прочитай `<path_to_concept>` — концепты решений + вердикт дебатов.
2. Прочитай `task.md` из той же папки — постановка проблемы.
3. Извлеки из вердикта: выбранный концепт, модификации из дебатов.

4. Найди `repomix-output.xml`: сначала в `sa_documentation/*-docs/` (несколько сервисов — спроси пользователя, какой относится к задаче; legacy-файл в корне `sa_documentation/` тоже принимается).
   - Если существует — загрузи как первичный источник кода.
   - Если нет — предупредить: "repomix-output.xml не найден. Рекомендуется запустить `/context-gen`. Продолжаю с поиском по живому коду."

5. Прочитай артефакты из `sa_documentation/`:
   - `naming_conventions.md` из `<сервис>-docs/` анализируемого сервиса — терминология.
   - Существующие документы — наследовать стиль, не дублировать.
   - Поиск по живому коду — для точной детализации FR.

### Этап 3: Формирование документа по шаблону Confluence

Заполни документ **СТРОГО** по шаблону `ideal_system_requirements.md`:

#### Структура документа (обязательные разделы):

1. **Введение (раздел 1)** — общая информация (метаданные в таблице) + термины и определения + ссылки + история изменений.
2. **Общее описание (раздел 2)**:
   - **As-Is** — описание текущего поведения с код-доказательствами (ключевые компоненты + ограничения текущего решения).
   - Архитектурное решение (ссылка).
   - Диаграмма компонентов (PlantUML).
   - Схема последовательности (PlantUML).
3. **План миграции (раздел 3)** — этапы внедрения (PlantUML), таблица этапов с откатами, критерии готовности.
4. **Функциональные требования — Backend / БД / API (раздел 4)** — серверные задачи:
   - **Что попадает:** изменения в БД (миграции, таблицы, views), backend-логика (контроллеры, сервисы, роутинг), API-эндпоинты, фоновые процессы (cron, очереди), интеграции между backend-сервисами, поисковые движки.
   - **Состав подразделов каждой задачи и допустимый уровень изложения каждого подраздела** — по контракту `resources/abstraction_levels.md` (разделы 2 и 3). Здесь не дублируется.
5. **Требования к интерфейсам — Frontend / UI (раздел 5)** — клиентские задачи:
   - **Что попадает:** верстка экранов и UI-компонентов, изменения в SSR/CSR, клиентские интеграции с API, микроразметка (schema.org, Open Graph), клиентский роутинг.
   - **Состав подразделов** — тот же контракт: формы 5.1 и 5.2 имеют одинаковый обязательный состав, различаются только блоками специфики.
   - **Если документ не содержит UI-изменений** — раздел 5 опускается с пометкой «Не применимо».
6. **Ревью требований** — таблица согласования (аналитик, разработка Backend, разработка Frontend, тестирование).
7. **Риски и ограничения** — таблица рисков (ID | Риск | Вероятность | Влияние | Митигация) + нумерованный список ограничений.
8. **Приложения** (опционально) — справочные материалы: SQL-скрипты, маппинги, шпаргалки.

#### Правило разделения Backend и Frontend

**Принцип:** каждая задача относится либо к Backend (раздел 4), либо к Frontend (раздел 5).

- **Backend (раздел 4):** затрагивает серверный код, БД, API, Sphinx, фоновые процессы, межсервисные интеграции.
- **Frontend (раздел 5):** затрагивает клиентский код, верстку, UI-логику, микроразметку, клиентский роутинг.
- **Смежные фичи:** если одна фича требует изменений и на backend, и на frontend — создаются **две** задачи:
  1. Backend-задача в разделе 4 (создание API, изменение БД).
  2. Frontend-задача в разделе 5 (интеграция с API, верстка).
  3. Связь через раздел «Зависимости» (frontend-задача зависит от backend-задачи).
- **Только Backend:** если документ не содержит UI-изменений — раздел 5 опускается с пометкой «Не применимо».
- **Только Frontend:** если документ не содержит backend-изменений — раздел 4 опускается с пометкой «Не применимо».

#### Правила заполнения:

- Метаданные каждой задачи — в таблице (Ответственный за тех. реализацию + Задача на разработку).
- Jira-ссылки — с номером и статусом задачи.
- Все нумерованные списки — арабскими цифрами, подпункты — a, b, c.
- Критерии приёмки — конкретные проверяемые условия (как QA проверит).
- NFR — триада «числовое значение + единица измерения + условие проверки». Имена классов, методов и размеры пулов признаком измеримости **не являются** и не требуются (уровень Л3, см. `resources/abstraction_levels.md`).
- Уровень изложения каждого подраздела — по контракту `resources/abstraction_levels.md`: подразделы «Общее описание доработки» (Л1) и «Описание доработок» (Л2) не содержат маркеров deny-списка; код-доказательства идут в «Затрагиваемые компоненты» и в As-Is.
- **Каждый функциональный блок с задачами открывается чек-листом состава доработок** (в простом документе без блоков — один список после заголовка раздела с задачами): чекбокс-пункты «что делаем» широкими мазками, каждый пункт завершается ссылкой на задачу `(N.M)`. Глагольные шаблоны — «Добавляем в <контур> <метод / API / таблицу>», «Расширяем <метод>», «Меняем источник <чего>: <было> → <стало>», «Переводим <экран / список> с <источника> на <источник>», «Убираем <обращение / шаг>»; жаргон («даём API», «прокидываем») запрещён. UI-задачи раздела 5, обслуживающие экран блока, — чекбоксами в списке блока; сквозные задачи нескольких блоков — строкой-примечанием без чекбокса (чекбокс у них один, в их собственном блоке). Чекбокс закрывается при закрытии задачи; открытые вопросы помечай маркером прямо в пункте.
- **«Общее описание доработки» (Л1) — только контекст:** как сейчас / как будет / особенности; без требований, без «должен», без перечисления полей и таблиц.
- **«Описание доработок» (Л2) открывается призывом к действию:** «Нужно <реализовать / добавить / расширить> <объект> — <результат>»; дальше правила от подлежащего («метод должен…», «экран должен…») и явные пункты «Ветвление „…“» для режимов работы, отказов источников, особых случаев. Таксономия без глаголов действия («Сущности:», «Потоки данных:») недопустима.
- **Служебная пометка уровней** — один раз в начале раздела 4 и раздела 5; в теле задач служебные строки не повторяются.
- **Задача создаёт/меняет API-метод → блок «Контракт API»** прямо в задаче по канону `technical-documentation/examples/ideal_api_document.md`: таблицы параметров с одинаковыми колонками (Тип, Обязательность, Описание, Пример, Мапинг на origin), контейнеры `Object<X>`/`Array<X>`, подтаблицы вложенных объектов, алгоритм activity-диаграммой PlantUML, таблица кодов ответов, таблица соответствия ключей. Мапинг — через метод API источника + атрибут; объекты БД за API внешнего сервиса (SP, view) в мапинг не попадают — им место в «Затрагиваемых компонентах».
- **Задача создаёт/меняет объекты БД → блок «Модель данных»:** имя таблицы, DDL с constraints (блок `sql`), фрагмент ERD (PlantUML).
- Неизвестные детали (имена атрибутов легаси-источника, нерешённые вопросы) — маркер `[NEEDS_INVESTIGATION]`; имена не выдумываются.
- JSON-примеры — в блоках кода с разметкой `json`.
- SQL-примеры — в блоках кода с разметкой `sql`, с комментариями.
- Диаграммы — PlantUML (Mermaid запрещён), надписи на русском.

### Этап 4: Визуализация

Сгенерируй диаграммы СТРОГО в формате **PlantUML** (Mermaid запрещён):

1. **Диаграмма компонентов** — компоненты системы и взаимосвязи.
2. **Схема последовательности** — порядок взаимодействия компонентов.
3. **План миграции** — этапы внедрения (activity diagram).

Все надписи на стрелках — на русском языке (бизнес-смысл). Технические имена — в скобках.

### Этап 5: Самопроверка и сохранение

1. Пройдись по чек-листу `resources/sysreq_validation_checklist.md`.
2. Убедись, что документ соответствует шаблону `ideal_system_requirements.md`:
   - Есть разделы: Введение, Общее описание (с As-Is), План миграции, Функциональные блоки, Ревью, Риски и ограничения.
   - Каждая задача имеет состав подразделов по контракту `resources/abstraction_levels.md` (раздел 2) в нормативном порядке.
   - **Каждая задача содержит оба описательных подраздела** — «Общее описание доработки» и «Описание доработок». Отсутствие второго — 🔴.
   - **Каждый блок с задачами открывается чек-листом состава доработок**: пункты-чекбоксы со ссылкой на задачу у каждого; каждой задаче блока (и обслуживающей его экран UI-задаче) соответствует пункт. Отсутствие чек-листа или пункта без ссылки — 🔴.
   - **«Общее описание доработки» — только контекст** (как сейчас / как будет / особенности); требования и призывы в нём — 🔴.
   - **«Описание доработок» открывается призывом к действию** («Нужно реализовать <объект> — <результат>»); таксономия без глаголов — 🔴.
   - **Ни один описательный подраздел не содержит маркеров deny-списка** (`resources/abstraction_levels.md`, раздел 4): ссылок `файл:строка`, идентификаторов кода, имён библиотек, фрагментов кода. Наличие — 🔴.
   - API-задачи содержат блок «Контракт API» с каноническими таблицами (одинаковые колонки, типы, обязательность, мапинг на origin), алгоритмом и кодами ответов; БД-задачи — блок «Модель данных» с DDL и ERD.
   - Диаграммы в PlantUML.
   - Риски с митигацией + ограничения.
3. Убедись, что каждое утверждение подтверждено код-доказательством — в подразделе «Затрагиваемые компоненты» и в As-Is, а не в описательных подразделах.
4. Сохрани документ в `sa_documentation/FNR/FNR_<N>/system_requirements.md` (рядом с task.md и concept.md).
5. Выведи: "Системные требования готовы. Следующий шаг: `/validate-doc <путь_к_файлу>`"
6. Если в документе описаны новые/изменённые API-методы — добавь подсказку: "После реализации API-методов машиночитаемая сверка контракта — `/open-api` (спека OpenAPI из кода сверяется с блоками «Контракт API»)."
