**ХРАНИЛИЩЕ (важно):** состояние Story/задач — в БД витрины. Чтение — только через
`python3 harness/sahelper.py` (state/task/card/flags/comments/docs), запись — через
task-set/ac-set/gates-set/checklist-set/comment-add/card-set/doc-set/task-create.
Файлы harness/ (manifest.json, tasks/, comments/, .flags/) не читать и не писать.
Stream-логи стадий и git-worktree — файлы, как раньше.
---

## Использование

```
/impl-run <путь к каталогу harness> [T<k>]
```

**Параметры:**

- `<путь к каталогу harness>` — например, `sa_documentation/FNR/FNR_1/harness`.
- `[T<k>]` — id задачи из `manifest.json`; если не указан — берётся первая готовая по DAG (`depends_on` закрыты, статус `PLANNED`/`APPROVED`).

## Примеры

```
/impl-run sa_documentation/FNR/FNR_1/harness T2
```

```
/impl-run sa_documentation/FNR/FNR_1/harness
```

## Важно

**Приоритет:** СТРОГОЕ соблюдение TDD-цикла и circuit breaker (v2 §7, `resources/gates_checklist.md`):
тесты прежде кода, RED обязателен, максимум 4 итераций исправлений, правки только в worktree
и только в ветке `harness/*`. Основное рабочее дерево и main/develop не трогаются.

**Ожидаемый результат:** задача доведена до `GATES`→`AGENT_REVIEW` (код + тесты + коммит
`[FNR-<N>/T<k>]` + обновлённый `manifest.json` + логи) либо `ESCALATED_BLOCKED` с отчётом.

**Универсальность:** команды гейтов — из `workspaces.yaml`; роль и правила —
`.claude/skills/impl-harness/SKILL.md`; карточка задачи — единственный рабочий контракт.
`python3` (Windows Git Bash: `python`).

## Инструкция для LLM

Ты — исполнитель задачи контура. Работаешь строго по карточке `tasks/T<k>.md` и досье;
СТ открываешь только чтобы сверить точность пересказа.

### Графовый контекст (complement-модель)

Если MCP `sa-helper-graph` доступен — `graph_call_chain`/`graph_impact` для impact-лестницы
(шаг 5). Недоступен — ripgrep по импортам/вызовам. Не заходить в `.worktrees/` при поисках.

### Этап 0: Предусловия

1. `sahelper flags FNR` → `story_status` ∈ {APPROVED, IN_PROGRESS} **и** флаг
   `APPROVE_PLAN` потреблён (или статус уже APPROVED) — иначе STOP: «план не утверждён».
2. `flags.paused == true` → STOP: «контур на паузе».
3. Задача по параметру или первая готовая по DAG (deps `DONE`/`VERIFIED`). Не готова →
   перечисли, что мешает, STOP. Карточка: `sahelper card FNR T<k>` — прочитай целиком.
4. Система задачи: `gates.build/test` ≠ `skipped`? Для `data_only`-системы TDD сводится к DDL-задаче
   (тесты = проверка скриптов ревью; смотри карточку).
5. Если работа в системе уже идёт (в `state` есть другая задача в IMPLEMENTING/REVIEW) → STOP.
3. Задача по параметру или первая готовая по DAG. Не готова (deps не `DONE`) → перечисли, что
   мешает, STOP. Карточка — прочитай целиком.
4. Система задачи: `gates.build/test` ≠ `skipped`? Для `data_only`-системы TDD сводится к DDL-задаче
   (тесты = проверка скриптов ревью; смотри карточку).
5. Если работа в системе уже идёт (`active_task_id` ≠ null и ≠ эта задача) → STOP.

### Этап 1: Изоляция

1. В репозитории системы: `git worktree add .worktrees/FNR-<N>-t<k> -b harness/FNR-<N>-<slug>-t<k>`
   (если ветка/worktree уже есть от прошлой попытки — продолжи в нём).
2. Скрой артефакты: `.worktrees/` в `.git/info/exclude` (если ещё нет).
3. Включи enforcement, скоупинг по worktree (иначе конфиг протечёт в общие настройки репо и
   заденет основное дерево!):
   ```bash
   git config extensions.worktreeConfig true
   git config --worktree core.hooksPath <абсолютный путь к harness/hooks воркспейса>
   ```
   Каталога `harness/hooks` нет → скопируй из установки sa-helper (универсальные скрипты
   pre-commit/pre-push) в корень воркспейса один раз.
4. Все дальнейшие команды — из каталога worktree.

### Этап 1a: Гранулярный план работ (чек-лист)

Разложи задачу так, как разложил бы её разработчик для контроля своей работы:
4–10 конкретных шагов в порядке исполнения (TDD-порядок: тесты → код → гейты → коммит).
Сохрани в карточку разделом (подготовь текст плана в файле и выполни:
`sahelper checklist-set FNR T<k> --section "План работ (чек-лист)" --file <файл>`,
   синтаксис Checkvist: `# План работ (чек-лист)` заголовок, `+` done, `~` in-progress,
   `-` todo, `[r]/[b]/[f]`, суффикс `!` = обязательный):

```
## План работ (чек-лист)
- [ ]RED-тесты: test_ac_4_1_2_1_* (формат id, уникальности)
- [~]Миграция V2__create_id_mapping.sql
- [x]Изучение Golden Reference MappingRepoImpl
```

Канон значений (как чек-лист в Jira): `[ ]` — Todo, `[~]` — In progress,
`[x]` — Done; расширенные: `[b]` — Blocked (шаг заблокирован — укажите чем),
`[f]` — Failed (попытка сделана, упала), `[r]` — Review (передано на проверку).
`[x]` — Done; расширенные: `[b]` — Blocked (шаг заблокирован, укажите чем),
`[f]` — Failed (попытка сделана, упала), `[r]` — Review (передано на проверку).

Правила ведения:

1. Шаги атомарные: один шаг = проверяемое действие («написать тест X», а не «сделать миграцию»).
2. Начал шаг — пометь `[~]`; закончил — `[x]` (правь карточку сразу, не партиями:
   `checklist-state FNR T<k> <текст-или-id> --state done` после каждого шага
   (или `checklist-add FNR T<k> --section "План работ (чек-лист)" --text "новый шаг"`).
3. Не добавляй шаги постфактум ради галочек; появились новые работы — допиши `- [ ]` и честно
   проведи через `~`→`x`.
4. **Режим доработки**: если в карточке есть раздел «Доработка по ревью (чек-лист)» — это
   первичное задание; веди его чекбоксы по тем же правилам, план работ не переписывай.

### Этап 2: TDD RED

1. Отметь старт задачи: `sahelper comment-add FNR T<k> --author agent --text ...` — по канону
   `.claude/skills/comment-writing/SKILL.md` (шаблон «Старт задачи»: какие AC закрываем,
   план работ числом шагов, worktree/ветка; комментарий — отчёт, понятный junior, а не пометка).
2. По карточке напиши тесты acceptance-критериев: **имена** `test_ac_<номер>_<k>_<действие>`
   (стиль — пресет стека). Тесты не должны требовать кода, которого ещё нет, — только публичного
   контракта из карточки/досье.
3. Запусти гейт test (`runner.py --mode test`, команда из `workspaces.yaml`, `--log` в
   `<harness>/logs/T<k>_red.log`). RED-гейт: **новые тесты обязаны упасть**. Прошли на пустом
   коде → тесты фиктивны: переписывай (п. «RED-гейт» в `resources/gates_checklist.md`).
4. Зафиксируй в manifest: задача `status: "TDD_RED"`; комментарий о результате RED-гейта.

### Этап 3: TDD GREEN (circuit breaker = 4)

1. Минимальная реализация ровно под падающие тесты (пресет стека, Golden Reference из досье).
2. Прогони гейт test. Падает → исправь и повтори. `iteration_count` +1 за каждый цикл
   «исправил → прогнал»; каждый цикл — короткий комментарий (`comment-add`).
3. **Перед каждой итерацией** проверь `sahelper flags FNR` → `paused`: появился — остановись,
   комментарий о паузе, отчёт человеку (снять паузу → продолжить этой же командой).
4. `iteration_count > 4` → **эскалация**: `task-set --status ESCALATED_BLOCKED`, отчёт
   `doc-set --kind failure_report --tid T<k>` + комментарий сутью отказа, STOP.
5. Тесты зелёные → `task-set --status TDD_GREEN`; для каждого AC:
   `sahelper ac-set FNR T<k> AC-<id> --status PASSED --test <имя теста>`;
   комментарий-итог GREEN-этапа.

### Этап 4: Гейты качества

1. `lint_cmd` из реестра (есть, `state` → systems) → `runner.py --mode lint`; нет —
   `sahelper gates-set FNR T<k> --lint skipped`.
2. **Impact-лестница** (`resources/gates_checklist.md`): импортёры изменённых файлов → прогон
   их тестов (суженный скоуп) → при чистом прогоне `gates-set ... --test passed`.
3. Coverage: инструмент есть в репо (pytest-cov/jacoco) → дельта по изменённым файлам ≥ 80%
   (нет инструмента — `--coverage skipped`, не блокирует).
4. Все гейты зелёные/skipped → `task-set --status GATES`.

### Этап 4a: Предложить задачу (если вскрылся пробел вне плана)

Работа выявила недостающую работу (не хватает миграции, реестра, тестового контура) —
НЕ делай её молча в текущей задаче (границы!) и не расширяй объём сам. Предложи задачу:

1. `sahelper task-create FNR '<json: title, description, system, depends_on>' --origin agent`
   (адаптер сам поставит PROPOSED и выдаст T<следующий>), затем карточка: `card-set` —
   что и зачем, предложение границы.
2. Запись в журнал задачи по канону comment-writing: **«Предложена задача T<n>»** — что
   вскрылось, почему это вне текущей задачи, что предложишь сделать.
3. Дальше её увидит человек на витрине (кнопки «Принять в бэклог» / «Отклонить»).
   Принятую задачу конвейер поставит в очередь по DAG — ты продолжаешь СВОЮ задачу.

### Этап 5: Коммит и завершение

1. Коммит в ветке задачи: `[FNR-<N>/T<k>] <type>: <кратко>` (type: feat/test/docs/chore).
2. `sahelper task-set FNR T<k> --status AGENT_REVIEW` (логи перечисли в комментарии).
3. Worktree оставить до ревью (`/impl-review` смотрит дифф; удалит `/impl-review` при APPROVED
   или человек при доработке). Основное дерево системы не тронуто — проверь `git status` там.
4. Если после тебя есть готовые задачи по DAG — предложи продолжить этой же командой.

Завершение: выведи резюме (AC → тесты, гейты, итерации, коммит) и литеральную подсказку:
«Задача T<k> готова к ревью. Следующий шаг: /impl-review <путь к harness> T<k>».
При эскалации — путь к failure_report и формулировку проблемы для человека.
