description: Глубокая многоуровневая проверка документации на предмет ошибок, галлюцинаций и соответствия стандартам
---

## Использование

```
/validate-doc <any_context> <file_path>
```

**Параметры:**

- <any_context> – тезисная задача в произвольной форме
- `<file_path>` — путь к созданному файлу документации (например: /sa_documentation/docs/API-101.md)

## Примеры

```
/validate-doc провалидируй документ /sa_documentation/docs/API-101_OrderInfo.md
/validate-doc проверь системные требования /sa_documentation/FNR/FNR_1/system_requirements.md
```

## Важно

**Метод:** Сплошная проверка (Full Coverage) с учетом специфики документа.
**Токены:** Используй рефлексию в 3 итерации в рамках одного запроса.

## Инструкция для LLM

### Графовый контекст (complement-модель)

Граф дополняет repomix-output.xml, а не заменяет его. Используй оба источника одновременно:

- **repomix-output.xml** — полный текст кода (реализации, SQL, комментарии)
- **MCP-инструменты** (если sa-helper-graph подключён) — структура и связи

**Графовые запросы для валидации:**

- `graph_introspect` — получить точный перечень меток, свойств и связей графа перед сверкой (узнать реальные имена сущностей и их количество)
- `graph_impact` — проверить, действительно ли сущность имеет указанные зависимости (CALLS, QUERIES, EXTENDS)
- `graph_call_chain` — проверить цепочку вызовов, описанную в документе
- `graph_query` — **точечная** проверка существования имени: `MATCH (n) WHERE n.name = $name RETURN labels(n), n.file`

> **Не делай вывод «сущность отсутствует» по `graph_schema`/`graph_arch_summary`.** Эти инструменты пагинированы и по умолчанию возвращают только первую страницу (`pagination.truncated = true` → данные неполны). Для проверки наличия конкретного имени используй точечный `graph_query`, а для полного списка — листай через `offset` до `truncated = false`.

> **Достоверность связей (`confidence`):** в выводе `graph_impact`/`graph_db_lineage`/`graph_db_impact` рёбра с `confidence='low'` или `source='inventory_resolver'` — выведенные (предположительные). Не помечай документ как ошибочный только из-за расхождения с low-confidence связью; сверяйся с фактическим SQL в `repomix-output.xml`.

Если MCP-инструменты недоступны — пропусти графовые запросы, верификация проводится через repomix-output.xml.

### Этап 1: Распознавание типа и сбор контекста

1. Прочитай целевой файл по пути `<file_path>`.
2. **Загрузи общие инструменты:** `repomix-output.xml`, `standard_mapping.md`, `sa_documentation/naming_conventions.md`, `/technical-documentation/resources/validation_checklist.md`
3. **Определи ТИП и догрузи специфику:**
   - **ТИП А (API Doc):** `.agent/skills/technical-documentation/SKILL.md`, `ideal_api_document.md`, `validation_checklist.md`.
   - **ТИП Б (Data Trace):** `.agent/skills/db-archeologist/SKILL.md`, `db_mapping_standards.md`, `ideal_data_trace.md`.
   - **ТИП В (System Requirements):** `/system-analyst-sysreq/SKILL.md`, `ideal_system_requirements.md`, `sysreq_validation_checklist.md`, `abstraction_levels.md` (контракт уровней изложения — нормативный источник состава подразделов задачи и deny-списка).
   - **ТИП Г (Screen Doc):** `.agent/skills/technical-documentation/SKILL.md`, `ideal_screen_document.md`. Признаки: документ лежит в `sa_documentation/screens/`, имя `screen_*.md`, в задаче `tasks.md` — `Тип задачи: Screen`. Это обзорный индекс экрана (карта методов + ссылки на API-документы), а НЕ детальное описание эндпоинта.

> **Ключевое отличие ТИП Г от ТИП А:** документ-экран НЕ содержит таблиц «Входные/Выходные параметры» с полями и Origin-маппингом. Поэтому Hard Gates по покрытию полей (Full Entity Coverage, Nested Object Coverage, типизация контейнеров) к ТИПУ Г **НЕ применяются** — их отсутствие в screen-документе НЕ является ошибкой. Валидация ТИПА Г проверяет полноту карты методов, корректность ссылок, маршруты, сквозную диаграмму и общие пруфы (см. ниже).

### ЭТАП 2: Доказательная база (Evidence Collection)

Прежде чем приступить к валидации, ты ОБЯЗАН найти в коде "Якоря Истины" (Truth Anchors):

**Для ТИПА А (API) и ТИПА Б (Data Trace):**

1. **Точка входа (Protocol Entry):** Найди артефакт, определяющий контракт интерфейса (Routing Table / Intercept Logic). Сверь HTTP-метод и способ парсинга данных.
2. **Слой ограничений (Validation Context):** Проанализируй логику проверки данных. Ищи скрытые зависимости (сквозь If/Else или Switch), влияющие на обязательность атрибутов.
3. **Узлы ветвления (Inference Nodes):** Идентифицируй архитектурные паттерны выбора реализации (Factory/Provider/Strategy).
4. **Инфраструктурный маппинг:** Соотнеси используемые в документе префиксы БД (из колонки Origin) с реальными подключениями в конфигурационных файлах проекта. Если есть расхождение или префикс отсутствует — статус 🔴.

**Для ТИПА Г (Screen Doc):**

1. **Реестр методов экрана:** По коду фронтенда (router-модуль экрана, store, `_domain/*.api.ts`, ApiService) и бэкенд-контроллерам экрана собери ФАКТИЧЕСКИЙ список всех API-методов, вызываемых на экране. Это эталон для сверки «Карты методов экрана».
2. **Маршруты экрана:** Найди в роутинге (`url_routes`/`routes`/router-модуль) реальные внешние URL экрана. Сверь с полем «Маршрут(ы)» документа.
3. **Существование методов:** Для каждой строки карты методов подтверди, что `Controller::action` реально существует в коде. Несуществующий метод — 🔴.
4. **Точки входа фронтенда:** Подтверди наличие файлов из «Общих технических пруфов» (api-сервис, router-модуль, store, `_domain`).

**Для ТИПА В (System Requirements):**

1. **As-Is верификация:** Для каждого утверждения в разделе «Описание текущего поведения» найди подтверждающий код (файл:строка). Если утверждение не подтверждено — статус 🔴 или `[NEEDS_INVESTIGATION]`.
2. **Затрагиваемые компоненты:** Для каждой задачи проверь, что таблица «Затрагиваемые компоненты» содержит реальные файлы и строки из кодовой базы.
3. **Jira-ссылки:** Проверь, что ссылки на задачи в Jira указаны с номером и статусом.
4. **SQL-запросы:** Если в документе есть SQL-запросы (источники данных, приложения), проверь их корректность относительно реальной схемы БД.
5. **Диаграммы:** Проверь, что PlantUML-диаграммы синтаксически корректны и отражают описанную архитектуру.

### Этап 3: Сплошная проверка (4 Итерации рефлексии)

Каждая итерация должна завершаться внутренней проверкой соответствия **Hard Gates**.

#### Итерация 1: Точность Входов и Маршрутизации (The Gateway Gate) 🔴

**Для ТИПА А (API):**

- Проверь эндпоинты. Обязательно: `METHOD /path`. Запрещено: просто имя метода контроллера.
- Произвести верификацию URL, Итоговый URL в документе должен быть результатом явного сложения [Значение из Config] + [Значение из Interface/Annotation].
- Проверь "Источник в коде" для каждого параметра (напр. `$_GET`, `$_POST`).
- Для каждого параметра должен быть указан источник в транспорте (Body, Header, Path, Query). Совпадает ли это с логикой парсинга в коде, если нет, статус 🔴.
- Должны быть отражены зависимости полей, найденные на этапе "Evidence Collection".

**Для ТИПА Б (Data Trace):**

- Проверь, чтобы первая стрелка UML содержала реальный API-путь.

**Для ТИПА Г (Screen Doc):**

- **Полнота карты методов:** Каждый метод из реестра (Evidence) присутствует в «Карте методов экрана». Пропущенный метод экрана — 🔴.
- **Формат строк карты:** Каждая строка содержит `METHOD URL` (не только имя экшена), контроллер `Controller::action` и ссылку на документ. Голое имя метода без `METHOD /path` — 🔴.
- **Reuse и владелец:** Переиспользуемые методы вынесены в таблицу reuse с указанием владельца, без дублирования полного описания. Дублирование детального описания метода в screen-документе — 🟡.
- **Маршруты:** Поле «Маршрут(ы)» соответствует реальным URL экрана из роутинга.

**Для ТИПА В (System Requirements):**

- Проверь структуру документа по шаблону `ideal_system_requirements.md`: наличие обязательных разделов (Введение, Общее описание с As-Is, План миграции, Функциональные блоки, Ревью, Риски и ограничения).
- Проверь метаданные в разделе «Общая информация»: наименование продукта, ответственные, Epic, БФТ, статус.
- Проверь нумерацию разделов — должна быть последовательной (1, 2, 3 / 3.1, 3.2 / 3.1.1, 3.1.2).
- Проверь таблицу «История изменений» — наличие хотя бы одной записи.

#### Итерация 2: Техническая достоверность (The Storage Gate) 🔴

**Для ТИПА А (API) и ТИПА Б (Data Trace):**

- **Объекты Хранения (State Stores):** Существуют ли указанные таблицы, индексы, очереди или ключи в исходном коде?
- **Происхождение (Origin Mapping):** Каждое техническое поле в документе должно иметь четкую привязку `Physical_Entity.Attribute`.
- **[CRITICAL] Full Entity Coverage (уровень 1):** все поля DTO/toArray
  присутствуют в таблице. Отсутствие поля без обоснования — 🔴.
- **[CRITICAL] Nested Object Coverage (рекурсивно):** наличия ключа в таблице
  НЕДОСТАТОЧНО. Для каждого поля-контейнера (`Object<...>`/`Array<...>` ИЛИ поля,
  чей тип в коде — объект/массив объектов) проверь:
  (а) тип записан как `Object<{Name}>` / `Array<{Name}>` (не голый `object`/`array`);
  (б) присутствует парная подтаблица «Описание вложенного {Name}».
  Отсутствие подтаблицы или голый тип — 🔴 (Hard Gate №5 / №6).
  ⚠️ «Покрытие» = рекурсивное раскрытие, а не присутствие ключа верхнего уровня.
- Если в коде класса есть непустые поля, не отраженные в документе (даже если они не используются в бизнес-логике), агент ОБЯЗАН добавить их или обосновать пропуск.
- **Интеграционная Топология:** Указаны ли физические протоколы и конечные точки (URL/IP) внешних систем, извлеченные из конфигурационного контекста?
- **Словарь:** Сверь термины с `naming_conventions.md`. Если наткнулся на что-то новое – дай знать, возможно потребуется расширить naming_conventions.md
- **Якоря истины (Anchors of Truth):** В каждом документе обязателен раздел "Якоря истины" со ссылками на конкретные строки кода. Иначе статус 🔴.

**Для ТИПА Г (Screen Doc):**

> Hard Gates по покрытию полей (Full Entity Coverage, Nested Object Coverage, типизация контейнеров `Object<>`/`Array<>`) к ТИПУ Г **НЕ применяются** — в обзорном документе экрана нет таблиц полей. НЕ выставляй 🔴 за их отсутствие.

- **Валидность ссылок:** Каждая ссылка в «Карте методов» ведёт на документ в `api/` (относительный путь, формат `[имя.md](имя.md)`). Абсолютный путь или битый формат ссылки — 🔴.
- **Контроллеры существуют:** Все `Controller::action` из карты методов реально присутствуют в коде (сверка с Evidence). Галлюцинация контроллера/экшена — 🔴.
- **Относительные пути:** Пути в «Общих технических пруфах» — строго ОТНОСИТЕЛЬНЫЕ от корня проекта. Абсолютный путь (`file:///…`, `/Users/…`) — 🔴.
- **Словарь:** Сверь названия экрана/сущностей с `naming_conventions.md`.
- **Технические пруфы:** Раздел «Общие технические пруфы» обязателен и содержит реальные роутинг/контроллеры/фронтенд-точки входа. Отсутствие раздела — 🔴.

**Для ТИПА В (System Requirements):**

- **As-Is Gate:** Каждое утверждение в разделе «Описание текущего поведения» должно иметь код-доказательство (файл:строка). Утверждения без доказательства — 🔴 или `[NEEDS_INVESTIGATION]`.
- **Task Gate:** Каждая задача в функциональных блоках должна содержать: обоснование, таблицу затрагиваемых компонентов (с файл:строка), критерии приёмки, зависимости. Применяется ко всем формам задач, включая задачи по вёрстке в разделе 5.
- **Improvement Description Gate:** Каждая задача должна содержать оба описательных подраздела — «Общее описание доработки» (уровень Л1) и «Описание доработок» (уровень Л2). Отсутствие второго хотя бы у одной задачи — 🔴.
- **Altitude Gate:** В подразделах «Общее описание доработки» и «Описание доработок» не должно быть маркеров deny-списка (`abstraction_levels.md`, раздел 4): ссылок по шаблону `\S+\.\w+:\d+`, идентификаторов кода (классы, методы, переменные, сигнатуры), имён библиотек и СУБД как средств реализации, фрагментов кода и запросов. Наличие хотя бы одного — 🔴. Оценочные суждения («слишком технично») основанием для 🔴 по этому гейту не являются. Исключение — объект требования: имя API-метода, поля контракта, DDL.
- **Action Gate:** «Описание доработок» открывается призывом к действию («Нужно <реализовать / добавить / расширить> <объект> — <результат>»); первый пункт-таксономия без глаголов действия («Сущности:», «Потоки данных:») — 🔴. Требования и призывы внутри «Общего описания доработки» (Л1 — только контекст) — 🔴.
- **Contract Gate:** Задача создаёт/меняет API-метод → в задаче есть блок «Контракт API» с каноническими таблицами (одинаковые колонки: Параметр | Тип | Обязательность | Описание | Пример | Комментарий | Мапинг; контейнеры `Object<X>`/`Array<X>`; подтаблицы вложенных объектов; алгоритм activity-диаграммой; таблица кодов ответов; таблица соответствия ключей). Мапинг — только метод API источника + атрибут (или `ТАБЛИЦА.ПОЛЕ` собственной БД); объект БД за API внешнего сервиса в мапинге — 🔴. Задача создаёт/меняет объекты БД → есть имя таблицы, DDL с constraints и фрагмент ERD. Нарушение любого пункта — 🔴.
- **Scope Checklist Gate:** Каждый функциональный блок с задачами (в разделах 4 и 5; при задачах без блоков — раздел целиком) открывается чек-листом состава доработок: пункты-чекбоксы «что делаем» широкими мазками, каждый пункт завершается ссылкой на задачу `(N.M)`, глаголы от места изменения («Добавляем в <контур>…», «Расширяем…», «Меняем источник…», «Переводим…», «Убираем…»). Отсутствие чек-листа, пункт без ссылки на задачу, задача блока без пункта или жаргон («даём API», «прокидываем») — 🔴. UI-задачи раздела 5 входят чекбоксами в списки своих экранов; сквозные задачи — строкой-примечанием без чекбокса. Правила — `abstraction_levels.md`, раздел 2.
- **Acceptance Gate:** Критерии приёмки должны быть конкретными и проверяемыми. «Работает корректно» без конкретики — 🔴.
- **NFR Gate:** Каждое нефункциональное требование должно содержать триаду «числовое значение + единица измерения + условие проверки». Оценочные формулировки («быстро», «надёжно») — 🔴. Отсутствие имён классов, методов и размеров пулов основанием для 🔴 **не является** — это уровень реализации, см. `abstraction_levels.md`.
- **Оговорки о неприменимости:** для документов, созданных до введения контракта уровней (ни одна задача не содержит подраздела «Описание доработок», первый описательный подраздел назван «Общее описание функционала», «Общее описание требований» или «Описание») — `Improvement Description Gate`, `Altitude Gate`, `Action Gate`, `Contract Gate` и `Scope Checklist Gate` **НЕ применяются**, 🔴 за них не выставляется. Полный текст оговорок — `sysreq_validation_checklist.md`, раздел «Оговорки о неприменимости».
- **Источники данных:** Если в задачах есть таблицы источников данных (SQL-запросы), проверить корректность имён таблиц и колонок относительно кодовой базы.
- **Маршрутизация:** Если есть таблицы маршрутизации (Сущность | Метод вызова), проверить что методы существуют в коде.

#### Итерация 3: Бизнес-логика и Визуализация (The Human-Readable Gate) 🔴/🟡

**Для всех типов:**

- **UML:** Все стрелки — на РУССКОМ. Описание должно объяснять **бизнес-смысл**, а технический метод писать в скобках.
- **Формат диаграмм:** Проверь, что НЕ используется Mermaid. Используй только PlantUML. Иначе статус СТРОГО 🔴.
- **Синтаксис и Зависимости:**
  1. Проверь все директивы `!include`.
  2. Проверь закрытие всех блоков (`@enduml`, `Boundary`, `Rel`).
  3. Если используется C4-PlantUML, проверь наличие `LAYOUT_WITH_LEGEND()`.
- **Визуализация:** Если диаграмма содержит внешние ссылки, которые могут быть недоступны — статус 🔴.
- **Терминология:** Соответствует ли лексика документа установленному Глоссарию проекта (Domain Glossary)?

**Для ТИПА А (API):**

- **[CRITICAL] Примеры данных:** В отчетах Data Trace ОБЯЗАТЕЛЕН блок `note` с примером структуры данных (JSON/Array). Если примера нет — статус СТРОГО 🔴.
- **Алгоритм:** Количество шагов в тексте должно совпадать с количеством шагов на Sequence-диаграмме.
- **Интеграции:** Вызовы внешних сервисов должны описываться не абстрактно, а с указанием точного физического протокола (SOAP, REST, gRPC) и эндпоинта из конфига.
- **Обработка Исключений:** Совпадает ли логика выброса исключений в коде с описанием ошибок в контракте?

**Для ТИПА В (System Requirements):**

- **Migration Gate:** План миграции должен содержать процедуру отката для каждого этапа. Без отката — 🔴.
- **Risks Gate:** Каждый риск должен иметь конкретную митигацию. Риски без митигации — 🔴.
- **Ограничения:** Раздел «Ограничения» должен перечислять, что решение НЕ покрывает, и компоненты backward compatibility.
- **Диаграммы:** Проверь наличие минимум двух диаграмм (компонентов + последовательности). Проверь корректность PlantUML-синтаксиса.
