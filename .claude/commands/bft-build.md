## Использование

```
/bft-build <контекст: PRD, свободный текст, ссылка/путь или путь к отчёту груминга>
```

**Параметры:**

- `<контекст>` — продуктовые требования: вставленный текст, PRD, ссылка/путь на документ (`.md`, `.html`, Confluence) либо путь к отчёту `/prd-grooming` (`sa_documentation/prd/{...}-grooming.md`).

## Примеры

```
/bft-build <вставленный текст PRD «Интеграция Кино во флоу TL»>
```

```
/bft-build sa_documentation/prd/kino-integration-grooming.md
```

```
/bft-build https://confluence.mts.ru/pages/viewpage.action?pageId=2300579320
```

## Важно

**Приоритет:** СТРОГОЕ соблюдение роли и принципов из `SKILL.md` и структуры эталона из `examples/ideal_bft_document.md`.

**Ожидаемый результат:** Файл `sa_documentation/bft/{bft_name}.md` с построенным БФТ. `{bft_name}` — kebab-case слаг из заголовка инициативы с суффиксом `-bft` (напр. `kino-integration-bft.md`). Если заголовок не извлекается — спроси имя или используй `bft-<N>.md`. Если файл уже есть — не затирай молча: спроси или добавь суффикс версии.

**БФТ ≠ груминг ≠ СТ.** Команда строит бизнес-функциональные требования из входа, а не диагностирует документ (это `/prd-grooming`) и не порождает системные требования с Jira-декомпозицией (это `/fnr-system-requirements`).

**Универсальность:** Команда не привязана к конкретному стеку, БД или бизнес-домену.

## Инструкция для LLM

### Графовый контекст (complement-модель)

БФТ строится по требованиям из входа, но обязан учитывать ограничения реализованной системы. Используй оба источника одновременно:
- **repomix-output.xml** — полный текст кода (реализации, SQL, комментарии);
- **MCP-инструменты** (если sa-helper-graph подключён): `graph_introspect` (реальные метки перед запросами), `graph_schema` (обзор структуры), `graph_impact` (зависимости компонента), `graph_call_chain` (трассировка).

Если система внешняя/сторонняя или источники недоступны — не выдумывай реализуемость: работай в режиме graceful degradation (см. этап 4).

### Этап 1: Загрузка роли

1. Прочитай `/bft-builder/SKILL.md` — твоя персона и принципы.
2. Загрузи эталон структуры из `examples/ideal_bft_document.md`.
3. Загрузи чек-лист из `resources/bft_validation_checklist.md`.

### Этап 2: Получение контекста

1. Если контекст вставлен текстом — работай с ним.
2. Если дан путь/ссылка — прочитай (Read для файла, WebFetch для URL). Если недоступно — попроси вставить текст.
3. Если вход — отчёт груминга (`sa_documentation/prd/{...}-grooming.md`) — используй его находки и открытые вопросы как материал; результат должен быть цельным БФТ, а не списком замечаний.

### Этап 3: Сбор ограничений системы

1. Найди `repomix-output.xml` в `sa_documentation/*-docs/` (несколько сервисов — спроси пользователя; legacy-файл в корне `sa_documentation/` тоже принимается) — если есть, используй как источник кода; если нет — предупреди: «repomix-output.xml не найден. Рекомендуется `/context-gen`. Scope-разметка идёт в режиме предположений.»
2. Если MCP-граф доступен — уточняй структуру и связи (`graph_introspect`, `graph_impact`); иначе пропусти графовые запросы.
3. Прочитай релевантные артефакты `sa_documentation/` (naming_conventions.md из `<сервис>-docs/`, существующие БФТ/СТ в `bft/` и `FNR/`) — не дублируй, ссылайся.

### Этап 4: Построение БФТ

Заполни разделы СТРОГО по эталону `examples/ideal_bft_document.md`:
1. **Описание** и **Общая информация** (метаданные, история изменений, доп. материалы).
2. **Бизнес-требования:** «Вводные» (перенеси открытые вопросы входа с адресатами — не теряй) и **Ценность** (3–7 пунктов БТ — корень трассировки).
3. **Пользовательские требования** — строго User Story «Когда я … Я хочу … Чтобы …», каждое связано с БТ.
4. **Требования к интерфейсам** — рекомендательное ТЗ дизайнеру (параметры среды + видение UX); для продукта без UI — «Не применимо» с обоснованием.
5. **Функциональные требования** — сгруппированы по блокам, проверяемы, с критериями приёмки. Для каждого ФТ проставь **Scope**:
   - 🟢 доработка существующего — с опорой на код/граф (`файл:строка` / узел);
   - 🔵 выход за рамки реализованного;
   - при отсутствии источников — `[ПРЕДПОЛОЖЕНИЕ: доработка/за рамки — подтвердить у <адресат>]`.
6. **Нефункциональные требования** — измеримые, с колонкой «Описание» и категорией.

Правило трассировки: каждое требование разделов 4–7 сводится к пункту ценности (раздел 3.2). «Висячие» требования недопустимы.

### Этап 5: Валидация и запись

1. Прогони документ по `resources/bft_validation_checklist.md`, закрой Hard Gates.
2. Если `sa_documentation/bft/` не существует — создай.
3. Определи `{bft_name}` (kebab-case слаг заголовка + `-bft`). Если файл уже есть — не затирай молча: спроси или добавь суффикс версии.
4. Создай `sa_documentation/bft/{bft_name}.md`.

### Этап 6: Завершение

Выведи: «БФТ построен: `sa_documentation/bft/{bft_name}.md`. Ценностей: <N>, ПТ: <N>, ФТ: <N> (🟢 доработка: <N>, 🔵 за рамки: <N>, ❓ предположения: <N>), НФТ: <N>.» Если работал в режиме graceful degradation — предупреди, что scope-метки требуют подтверждения. При желании предложи следующий шаг — сборку СТ (`/fnr-new-task` → … → `/fnr-system-requirements`).
