# Методология тестирования и сквозной верификации (перенос из /impl-verify)

Проверка завершённой работы в конвейере AI-Harness: полные прогоны, контрактные проверки,
честный вердикт.

## Принцип

Ничего не «дотягиваем» до зелёного: красная проверка — красный вывод. Частичный скоуп —
только если человек явно его утвердил, и он помечается в отчёте.

## Процедура

### 1. Готовность
- Работы, которые должно было закрыть проверяемое изменение, завершены; иначе перечисли
  неготовое и остановись (или явно работай по утверждённому частичному скоупу).
- Система собирается и baseline снят; нет — сначала разработчик, верификация невозможна.

### 2. Полные прогоны
- Сборка и тесты всей системы на итоговом состоянии. Изменения ещё в ветках задач (не
  слиты) — прогон в их worktree и пометка об этом в отчёте.
- Зафиксируй passed/failed/errors/skipped и падения (сокращённо, до 20 строк).

### 2а. E2E и UI-проверки в среде агента (браузер установлен)
Headless Chromium (playwright) установлен в образе демона — UI-сценарии исполняемы, пометка
«в среде нет браузера» больше не основание для NOT_VERIFIED:
- В проекте есть playwright-конфиг — установи зависимости worktree (`npm ci`/`yarn`) и
  гони спеки headless: `npx playwright test --project=chromium` (или `--ui=false`).
- Нужен запущенный сервер — подними его сам в worktree (`dev`/`preview`/`start`, фоном,
  порт из конфига) и останови после прогона.
- Внешний stage-стенд доступен через `http://host.docker.internal:<порт>` (мост к хосту).
  Порт стенда ищи в описании задачи/проекта; если не указан — проверь API-здоровье
  (`/health`, `/healthz`) и зафиксируй использованный адрес в отчёте.
- API-сценарии гоняй без браузера — `curl`/`httpx` по контракту; это исполнимо даже при
  недоступном UI.
- Если и браузер, и стенд недоступны — пометь пункт failed с точной причиной (вывод
  команды), а не общей формулировкой: по причине человек чинит среду, а не гадает.
- Инкрементальный перепрогон: если задача уже проходила тестирование и повтор запущен
  из-за открытых пунктов чеклиста (см. «Прицельный перепрогон» в контексте) —
  верифицируй только открытое + короткий смоук; полный регресс не повторяй.
- Чеклист — это состояние: выполнил пункт — закрой его в checklist_updates того же
  отчёта; невключённый выполненный пункт блокирует гейт и обесценивает прогон.

### 3. Контрактные проверки (связи между системами)
Для каждого контракта постановки:
1. Спецификация существует и валидна.
2. Каждая сторона реально использует контракт — ссылки файл:строка в отчёт.
3. Стороны согласованы: имена полей и коды ответов потребителя = спецификации.

### 4. Data-only и выводимые системы
В диффах задач нет обращений к объектам систем, которые постановка требует не трогать
(и наоборот: для выводимых систем новых обращений появиться не должно). Перечисли в отчёте
проверенные паттерны поиска.

### 5. Отчёт и вердикт
- Сводка: прогоны (числа), контракты (проверено/не проверено), data-only проверки,
  границы верификации (что не проверялось и почему).
- Каждый непройденный пункт — кандидаты в баги: что ожидалось, что вышло, как
  воспроизвести (в конвейере непройденный пункт ПСИ предлагает баг автоматически).
- Вердикт: VERIFIED при полном успехе; иначе NOT_VERIFIED с перечнем, что чинить.
- PR-заготовка приветствуется: заголовок, сводка изменений, перечень веток задач,
  чек-лист проверок с результатами. Push и создание PR делает только человек.

### Docker-среда: глобальные правила (обязательные)

Ты работаешь в контейнере демона с доступом к docker хоста через сокет. Единый
принцип именования: ветка — `task/<код>`, docker-проект задачи — `harness-<КОД>`
(например `harness-VITRINA-37`), порты — из диапазона 21000–29999.

1. **Reuse вместо дублей.** Перед созданием чего-либо проверь существующее:
   `docker ps -a --format '{{.Names}}\t{{.Status}}'` и
   `docker compose -p harness-<КОД> ps`. Живое — используй; остановленное —
   стартуй; создавай только недостающее. Дублирующий контейнер = дефект прогона.
2а. **Павший при старте — не цикли.** Если контейнер после `start` сразу падает —
   НЕ повторяй старт в цикле: одна попытка, затем `docker logs <имя> --tail 50`
   для диагноза; причина падения (повреждённые данные, занятый порт, конфликт
   версий) требует ремонта или человека. Параллельные/частые старты одного
   контейнера создают гонки и маскируют настоящую причину.
2. **Чужое не трогать.** Контейнеры вне твоего проекта `harness-<КОД>` (в том
   числе общий контур `ticketscloud-*`, `fnr8-*`, `ai-harness-*`) не останавливай,
   не пересоздавай, не удаляй. Контурные сервисы подключай через их сеть:
   `docker network connect <сеть_контура> <твой_контейнер>` и ходи по внутренним
   именам (`ticketscloud-core:6543`, `ticketscloud-mongo-1:27017`) — так доступны
   даже порты, не опубликованные на хост. Клиенты внутри контейнеров:
   `docker exec ticketscloud-mongo-1 mongosh`.
3. **Подъём своей среды** — только через compose с проектом задачи:
   `docker compose -p harness-<КОД> up -d ...`; порты публикуй на 127.0.0.1 из
   диапазона 21000–29999 (проверь занятость: `docker ps --format {{.Ports}}`).
4. **Мост путей для `-v`.** docker работает на хосте: пути монтирования указывай
   как на хосте (исходный путь проекта), а не как видит их твой контейнер
   (`/app/host-home/...` — только для файлов внутри твоей среды).
5. **Завершение.** После прогона останови СВОЙ проект (`docker compose -p
   harness-<КОД> stop`); данные и контейнеры оставь — решает человек. Про чужие
   `down`/`rm` запрещены. Использованные порты и имена перечисли в отчёте.

## Артефакт этапа (обязателен)

Отчёт этапа запиши как артефакт в строго JSON-отчёте прогона: поля
`artifact_md` (текст отчёта: шапка с task-code и датой, разделы по
функциональным блокам, пункты с вердиктами) и `artifact_kind`
{reviewer: "review_report", qa: "qa_report"}. Без артефакта гейт перехода
вперёд отклонит задачу («не заполнен артефакт этапа») — попытка сгорит.
