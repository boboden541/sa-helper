# Методология mindmap-карт: оси, уровни, атомы, декомпозиция

> Ресурс скилла `mindmap-cartographer`. Определяет: как выбрать ось группировки, контракт уровней иерархии, форматы атомов, правило декомпозиции part-N. Цветовая семантика — отдельно в `mindmap_colors.md`; чек-лист самопроверки — `mindmap_checklist.md`.

---

## 1. Ось группировки: каталог и правило выбора

Ось — единое измерение, по которому уровень L1 делит сервис. **Одна карта = одна ось.** Смешение разрезов (экраны + объекты в одной карте) запрещено — второй разрез оформляется отдельной картой.

| Ось | Уровень L1 выглядит как | Выбирать, когда цель промта… | Источники реестра единиц |
|---|---|---|---|
| **UI-экраны** | `Шлюзы (10 экранов)` — раздел со счётчиком экранов | «понять, что видит пользователь / что происходит в разделе UI» | `screens/`, файлы роутинга фронтенда, `api_map.md`, задачи Screen в `tasks.md` |
| **Типы объектов** | `Шоу == show` — пара «бизнес-имя == тех.идентификатор» | «понять, какие сущности/данные проходят через сервис и откуда берутся» | `naming_conventions.md`, `erd/`, сущности кода |
| **Интеграции/каналы** | `BI (ядро)`, `Партнёр X` | «понять, с кем и как общается сервис» | `integrations/`, конфиги базовых адресов, граф (`graph_arch_summary`) |
| **Домены/модули** | `Catalog`, `Payment` | «понять, из чего состоит сервис крупными блоками» | `architecture/`, `project_taxonomy`, граф (`graph_schema`) |
| **Процессы** | `Продажа билета`, `Возврат` | «понять, какие сценарии вообще есть» (обзор нескольких процессов одной картой; детальный разбор одного процесса — тип Process, не mindmap) | `processes/`, `tasks.md` |

**Правила выбора:**

1. Явная ось в аргументе («по экранам», «по объектам») — берётся без обсуждения.
2. Явной оси нет → ось выводится из цели промта по таблице выше.
3. Цель не различает двух кандидатов → задай пользователю ОДИН вопрос до построения карты.
4. Дефолты при цели «изучить сервис полностью» (Режим А `/reverse-plan-tasks`, ось не названа): фронтенд-сервис → экраны; бэкенд/репозиторий БД → типы объектов; шлюз/ETL/интеграционный сервис → интеграции.
5. Нужен второй разрез — это отдельная карта (отдельная задача / отдельный файл), а не смешение в одной.

## 2. Контракт уровней иерархии (L0–L7)

| Уровень | Синтаксис | Содержание | Пример |
|---|---|---|---|
| L0 | `*[#LightCyan] <Сервис>` | корень — сервис (или тема связи X↔Y), всегда с заливкой | `*[#LightCyan] ZION` |
| L1 | `**` | **ось**: группы (раздел экранов со счётчиком / тип объекта `Бизнес-имя == tech_id`); сюда же серые заглушки part-N | `** Шлюзы (10 экранов)`, `** Шоу == show`, `**[#E0E0E0] Управление — part2` |
| L2 | `***` | нумерованные элементы группы (экран N / шаг N); цвет элемента = цветовое измерение карты | `***[#FFD5D5] 1. Проблемы сопоставления` |
| L3 | `****` | действия с префиксом `Чтение —` / `ЗАПИСЬ —` (запись КАПСОМ); в осях без действий (объектная) — сразу атомы, см. правило 5 ниже | `**** ЗАПИСЬ — скрытие проблемы`, `**** SELECT FROM bi_db.dbo.mapping` |
| L4 | `*****` | канал: `REST BI (PUT, подпись HMAC) → bi_db.problem`, `REST BI` (узел-канал без цели — цель раскрывается под-шагами ниже), `Напрямую (SOAP ядра)`, `Напрямую (JDBC)`, `Через BI (кэш)`, `Git push из ZION (не uat_db)` | — |
| L5–L6 | `******` и глубже | опциональные под-шаги канала («чтение внутри BI — валидация эталона»); вводятся ТОЛЬКО при реальном промежуточном уровне — прокладки ради глубины запрещены | — |
| L7 | терминальный лист | атом-лист (трассируемый артефакт). По умолчанию ставится сразу под каналом (`******`, без под-шагов — так в эталонах); в ветке с под-шагами — глубже, но не более `*******` | `******[#FFDDDD] uat_db · view BI_Client_View` |
| — | `*** ...` | непокрытый хвост внутри ветки («есть ещё — не вошло») | `*** ...` |
| — | `** ...` | непокрытый хвост самой оси (за последней группой L1 есть ещё неименованные единицы) | `** ...` |

> Номер уровня (L) — логическая роль узла, а не счётчик звёзд: число звёзд отражает фактическую вложенность конкретной ветки. В типовой ветке под-шагов нет, и атом стоит сразу за каналом на `******`; роль L7 означает лишь «терминальный атом», где бы он ни стоял. Жёсткий предел глубины — `*******` (7 звёзд).

Правила:

- Глубже L7 не уходить. Потребность глубже — сигнал: выносить группу в part-N либо дробить элемент L2.
- `title` обязателен: `As-Is: <тема>` / `To-Be: <тема>` (или нейтральная `<Тема>: <суть>`). **To-Be допустим только при источнике требований** (system_requirements / концепт) — иначе запрещён: нет фактов.
- Элементы L2 нумеруются (`1.` … `N.`); у осевых групп UI-осей указывается счётчик (`(10 экранов)`).
- Для объектной оси пары «бизнес-имя == тех.идентификатор» (`Шоу == show`) обязательны: карта читается людьми, идентификатор трассируется в код.
- **Ось определяет состав уровней, а не универсальная лестница.** Осям с действиями и каналами (UI-экраны, интеграции) соответствует цепочка «действие L3 → канал L4 → атом»; осям без них (канон — типы объектов) — «элемент L2 → сразу атомы» (`****`) без префиксов `Чтение —`/`ЗАПИСЬ —` и без уровня каналов (эталон `ideal_mindmap_object_axis.md`). Прокладка неиспользуемых уровней запрещена в обе стороны.

## 3. Атомы (листья)

Каждая ветка заканчивается **атомом** — артефактом, существование которого проверяемо в коде/DDL/графе, — ЛИБО явным хвостом `...`, если единица ещё не покрыта (честная неполнота; хвост фиксируется в отчёте, молчаливый пропуск запрещён). Выдуманный атом = галлюцинация (🔴 на валидации).

Канонические форматы записи:

| Формат | Примеры |
|---|---|
| `<БД> · SP <имя>` / `<БД> · view <имя>` / `<БД> · таблица <имя>` | `uat_db · SP E_Building_getAll`, `uat_db · view BI_Client_View` |
| `<OPERATION> <бд>.<схема>.<объект>` | `SELECT FROM bi_db.dbo.mapping`, `EXEC uat_db.dbo.bi_AddShow`, `INSERT bi_db.dbo.mapping` |
| `REST <сервис> (<METHOD>[, <детали>]) → <цель>` — метод обязателен, когда подтверждён источником (обычно записи) | `REST BI (POST, подпись HMAC) → bi_db.mapping` |
| `REST <сервис> → <цель>` — допустимо для чтений, когда HTTP-метод НЕ подтверждён источником; выдумывать метод запрещено | `REST BI → bi_db.problem` |
| Некритичный контур (кэш, логи, git) | `logs PostgreSQL (не uat_db)`, `Git push из ZION (не uat_db)` |

Допустим и терминальный под-шаг канала, называющий трассируемую цель (`→ <объект>`), — как `запись связки → bi_db.mapping` в UI-эталоне: цель проверяема, даже если лист сформулирован словами.

Откуда берётся атом (в порядке приоритета): готовый документ сервиса → DDL/миграции → `repomix-output.xml` → MCP-граф (с confidence-правилами: ребро `confidence='low'`/`source='inventory_resolver'` — предположение, требует подтверждения SQL в repomix). Неподтверждённый атом в карту не попадает; сомнительный — `[NEEDS_INVESTIGATION]` в «Пруфах» обёртки.

## 4. Декомпозиция part-N

Карта — обзорный документ: она обязана читаться целиком, но не обязана вмещать всё.

- **Порог выноса:** группа оси > ~10–12 элементов L2, либо plantuml-блок ~ > 400–500 строк, либо оценка > ~30–40k токенов на файл → переполненные группы выносятся.
- **Основной файл всегда сохраняет полную ось L1:** вынесенная группа остаётся серой заглушкой `**[#E0E0E0] <Группа> — partN`. Читатель видит состав сервиса целиком, не открывая part-файлы.
- **Part-файл:** `mindmap_<название>_partN.md`, тот же канон: title с суффиксом `— partN`, корень-сервис, полная `legend` (часть не читается без контекста легенды).
- **Непокрытый хвост** внутри ветки — `*** ...`; хвост самой оси (есть ещё неименованные единицы L1) — `** ...`. Это маркеры честной неполноты, а не молчаливый пропуск.
- В `tasks.md` части part-N — та же задача (карта = один результат); отдельные задачи на части не заводятся.

## 5. Обёртка .md

Файл `mindmap_*.md` = минимальная обёртка + plantuml-блок (канон screen/process): заголовок с сервисом и осью, мета-строка (сервис · ось · режим · цветовое измерение), источники фактов со статусами и датой repomix-снапшота, сама карта, раздел «Пруфы и источники» с ОТНОСИТЕЛЬНЫМИ ссылками на использованные документы. Точный вид — эталоны `examples/ideal_mindmap_ui_axis.md` и `examples/ideal_mindmap_object_axis.md`.
