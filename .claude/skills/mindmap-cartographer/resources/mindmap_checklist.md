# Чек-лист mindmap-карты (самопроверка и валидация)

> Ресурс скилла `mindmap-cartographer`. Используется дважды: генератором на Этапе 6 команды `/mindmap` (и `/create-doc` с типом Mindmap) — с явными ✅/❌ по каждому пункту; валидатором `/validate-doc` (ТИП З) — как Hard Gate-замена полевых гейтов (Full Entity / Nested Object Coverage к mindmap НЕ применяются).

---

## А. Скелет карты

- [ ] `title` присутствует и отражает тему и режим (`As-Is:` / `To-Be:` / нейтральная). To-Be — только при источнике требований.
- [ ] Корень L0: `*[#LightCyan] <Сервис>` — один, с заливкой.
- [ ] Уровень L1 кодирует РОВНО одну ось; смешение разрезов (экраны + объекты) отсутствует.
- [ ] У осевых групп UI-осей есть счётчики (`(10 экранов)`); у объектной оси — пары `Бизнес-имя == tech_id`.
- [ ] Элементы L2 пронумерованы последовательно (`1.` … `N.`).
- [ ] Действия L3 несут префикс `Чтение —` / `ЗАПИСЬ —` (запись капсом) — там, где ось предполагает действия.

## Б. Полнота (Coverage оси)

- [ ] У каждой единицы реестра оси (Этап 2 команды) есть исход: присутствует в карте, вынесена в part-N (серая заглушка `**[#E0E0E0] … — partN`) или помечена хвостом `...` (внутри ветки — `*** ...`, у самой оси — `** ...`). **Молчаливо пропущенной единицы быть не может — 🔴.**
- [ ] Каждая серая заглушка part-N имеет существующий part-файл; каждый part-файл имеет заглушку в основном файле (взаимно).
- [ ] Part-файл несёт: title с `— partN`, корень-сервис, полную legend.

## В. Трассируемость атомов

- [ ] Каждая ветка заканчивается атомом в одном из канон-форматов (`<БД> · SP <имя>`, `<OPERATION> <бд>.<схема>.<объект>`, `REST <svc> (<METHOD>) → <цель>` либо `REST <svc> → <цель>` — без неподтверждённого метода, выдуманный метод — та же галлюцинация; «некритичный контур» — `logs PostgreSQL (не uat_db)`, `Git push из ZION (не uat_db)`; терминальный под-шаг канала с трассируемой целью `→ <объект>` — как в UI-эталоне) ЛИБО хвостом `...` (непокрытая единица — допустимо, фиксируется в отчёте).
- [ ] Каждый атом подтверждён: готовым документом, DDL/миграциями, repomix или графом (ребро не `confidence='low'`/не `inventory_resolver`). Галлюцинация атома — 🔴.
- [ ] Неподтверждённые, но важные сущности — в «Пруфах» обёртки как `[NEEDS_INVESTIGATION]`, не в карте как факт.

## Г. Цвет и legend

- [ ] В карте ровно ОДНО цветовое измерение; оно названо в мете обёртки.
- [ ] `legend … end legend` присутствует, если использован хотя бы один цвет (кроме `#LightCyan` корня и `#E0E0E0` заглушек).
- [ ] Взаимная полнота: каждый HEX расшифрован строкой; каждая строка легенды = реально используемый HEX; бесцветность описана.
- [ ] Палитра соответствует `mindmap_colors.md` (для канонического измерения — HEX оттуда).

## Д. Синтаксис PlantUML

- [ ] Пара `@startmindmap` / `@endmindmap`; блок `legend` закрыт `end legend`.
- [ ] Уровни — корректные `*`-префиксы, `[#HEX]` стоит перед текстом узла.
- [ ] Глубина ≤ L7 (`*******`).
- [ ] ТОЛЬКО PlantUML; Mermaid или иной формат — 🔴.
- [ ] Подписи на русском; технические идентификаторы (SP, таблицы, tech_id) — как в коде.

## Е. Обёртка .md

- [ ] Мета-строка заполнена: сервис · ось · режим · цветовое измерение.
- [ ] «Источники фактов» перечисляют использованные документы со статусами ✅/🟡 (🟡 — с пометкой «не валидировано») и дату repomix-снапшота.
- [ ] «Пруфы и источники» — относительные ссылки (`../screens/…`, `../api_map.md`); абсолютные пути — 🔴.
- [ ] В карте нет детального разбора: маппингов полей, Sequence, таблиц параметров — это работа api_/screen_-документов; вместо этого — ссылки на них.
