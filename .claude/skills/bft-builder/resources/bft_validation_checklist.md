# Чек-лист валидации БФТ

## 1. Структура документа (шаблон)

- [ ] Документ начинается с заголовка `[БФТ] <PROJECT>-<NNN> <Название>`
- [ ] Присутствуют все обязательные разделы: 1 Описание, 2 Общая информация (2.1 История изменений, 2.2 Доп. материалы), 3 Бизнес-требования (3.1 Вводные, 3.2 Ценность), 4 Пользовательские требования, 6 Функциональные требования, 7 Нефункциональные требования
- [ ] Раздел 5 (Требования к интерфейсам) заполнен либо помечен «Не применимо» с обоснованием
- [ ] Колонки таблиц соответствуют эталону `examples/ideal_bft_document.md` (ни одна колонка шаблона не опущена)

## 2. Ценность (раздел 3.2)

- [ ] Есть 3–7 пунктов ценности с идентификаторами (БТ-…)
- [ ] Каждый пункт имеет приоритет и наименование
- [ ] Ценность сформулирована как польза для бизнеса/пользователя, а не как техническая задача

## 3. Пользовательские требования (раздел 4)

- [ ] Каждое ПТ — в формате User Story: **Когда я** … **Я хочу** … **Чтобы** …
- [ ] Одно ПТ — одна атомарная возможность (не смешано несколько)
- [ ] Каждое ПТ связано минимум с одним БТ (колонка «Связанные требования»)
- [ ] Нет технических деталей реализации в тексте Story

## 4. Интерфейсные требования (раздел 5)

- [ ] Заданы параметры среды (тип продукта, браузеры, разрешение, вёрстка) — если есть UI
- [ ] Видение UX сформулировано как рекомендация дизайнеру, а не как жёсткая вёрстка
- [ ] Для продукта без UI — раздел «Не применимо» с обоснованием

## 5. Функциональные требования (раздел 6)

- [ ] Каждое ФТ проверяемо (можно написать критерий приёмки)
- [ ] Каждое ФТ связано с БТ/ПТ (колонка «Связанные требования»)
- [ ] Приведены критерии приёмки (примеры) под таблицей
- [ ] ФТ сгруппированы по функциональным блокам (строки-подзаголовки)

## 6. Scope-разметка (доработка vs выход за рамки)

- [ ] Каждое ФТ имеет метку Scope: 🟢 доработка / 🔵 за рамки / ❓ предположение
- [ ] Метка 🟢 «доработка» подкреплена опорой на код/граф (`файл:строка` или узел графа)
- [ ] При отсутствии repomix/графа спорные метки оформлены как `[ПРЕДПОЛОЖЕНИЕ …]` с вопросом к адресату
- [ ] В документе есть предупреждение о режиме работы, если источники ограничений недоступны

## 7. Нефункциональные требования (раздел 7)

- [ ] Каждое НФТ измеримо (конкретные числа/условия), есть колонка «Описание»
- [ ] Указана категория (производительность / доступность / безопасность / совместимость)
- [ ] Нет «резиновых» формулировок («быстро», «удобно», «надёжно») без раскрытия

## 8. Трассировка и вопросы

- [ ] Каждое требование разделов 4–7 сводится к пункту ценности (нет «висячих» требований)
- [ ] Открытые вопросы входа перенесены в 3.1 «Вводные» с адресатами (не потеряны)

## 9. Ссылки и пути

- [ ] Все ссылки на код/артефакты — относительные от корня проекта
- [ ] Нет остаточной HTML/Confluence-разметки

## Hard Gates (🔴)

1. **Template Gate:** Опущен обязательный раздел или колонка таблицы, предусмотренная эталоном — 🔴.
2. **Value Trace Gate:** Требование (ПТ/ФТ/НФТ) не сводится ни к одному пункту ценности — 🔴.
3. **User Story Gate:** ПТ не в формате «Когда я … Я хочу … Чтобы …» — 🔴.
4. **Scope Gate:** ФТ без метки scope, либо 🟢 «доработка» без опоры на код/граф и без пометки предположения — 🔴.
5. **NFR Gate:** НФТ без измеримого критерия или с оценочной формулировкой — 🔴.
6. **Owner Gate:** Открытый вопрос без адресата — 🔴.
7. **Path Gate:** Абсолютные пути в ссылках на код — 🔴.
