# Babelfish Compass: воспроизводимая статическая проверка

## Назначение и источник

Используй официальный Babelfish Compass из репозитория `babelfish-for-postgresql/babelfish_compass`:

- репозиторий: https://github.com/babelfish-for-postgresql/babelfish_compass
- руководство: https://raw.githubusercontent.com/babelfish-for-postgresql/babelfish_compass/main/BabelfishCompass_UserGuide.pdf
- релизы: https://github.com/babelfish-for-postgresql/babelfish_compass/releases/latest

Compass анализирует T-SQL статически. Он не подключается к MSSQL или Babelfish и не доказывает runtime parity.

## 1. Определить фактический CLI

Не угадывай путь и флаги установленной версии. Найди один из launcher-файлов:

```text
BabelfishCompass.sh
BabelfishCompass.bat
```

Сначала выполни `-help` и зафиксируй версию Compass. Разные релизы могут иметь разные version/config flags; используй синтаксис именно установленного launcher-а.

Базовая форма официального CLI:

```bash
./BabelfishCompass.sh <report-name> <input.sql>
```

Для существующего собственного отчёта можно использовать `-replace`. Для точной навигации по проблемам включай `-reportoption xref`, если этот флаг присутствует в `-help` текущей версии.

Не применяй `-replace` к чужому или неизвестному report name: Compass может перезаписать существующий отчёт.

## 2. Зафиксировать целевую версию

Источники в порядке приоритета:

1. версия целевого окружения/extension из PostgreSQL endpoint;
2. миграционный контекст проекта;
3. deployment manifest или согласованная целевая версия;
4. явный ввод пользователя.

Версия локального Compass должна уметь оценивать выбранную версию Babelfish. Проверь compatibility matrix из руководства. Если не умеет — обновление Compass является блокером, но не поводом молча оценивать другую версию.

## 3. Подготовить вход

Собери один воспроизводимый UTF-8 `.sql`-файл. Для каждого batch добавь комментарий с `query_id` и источником:

```sql
-- query_id: Q-001
-- source: src/Repository.php:142
-- call_path: GET /items -> ItemService -> ItemRepository
SELECT ...;
GO
```

Правила:

- сохраняй реальный T-SQL, не «улучшай» его до анализа;
- параметризированный SQL приведи к синтаксически анализируемой форме, сохранив реальные типы;
- добавь все ветки динамического SQL отдельными batches, насколько они восстанавливаются из кода;
- включи вызываемые процедуры/functions/views или проанализируй их отдельным входом;
- не вставляй credentials и production secrets;
- не считай одно появление текста полным инвентарём, если SQL строится динамически.

## 4. Запустить и сохранить артефакты

Используй уникальное имя, включающее проект, scope и дату/commit при необходимости. Сохрани в отчёте:

- команду без секретов;
- версию Compass;
- целевую версию Babelfish;
- SHA/путь входного SQL;
- путь к HTML/CSV-отчёту;
- суммарные counts по классификациям.

Compass по умолчанию пишет отчёты в пользовательский каталог. Не копируй большой HTML в Git без явной необходимости; в `sa_documentation` достаточно воспроизводимой сводки и ссылок на локальные артефакты.

## 5. Разобрать результат по query_id

Не ограничивайся общей оценкой `GO`. Для каждого `Not Supported`, `Review Semantics` и `Review Performance` укажи:

- `query_id` и источник;
- feature и фрагмент;
- применимость ветки в runtime;
- способ исправления или парный тест;
- повторный результат Compass после изменения.

Известные категории вроде `MERGE`, `FOR XML`, dynamic SQL или execution context оценивай по отчёту для целевой версии, а не по памяти: поддержка меняется между релизами.

## 6. Повторная проверка

После изменения SQL:

1. повторно извлеки запрос из фактического кода;
2. пересобери входной файл;
3. перезапусти Compass для той же версии;
4. убедись, что не появились новые findings;
5. только затем переходи к runtime parity.
