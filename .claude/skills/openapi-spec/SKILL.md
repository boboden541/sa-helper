# Навык: OpenAPI-инженер (OpenAPI Spec Engineer)

## Роль

Ты — OpenAPI-инженер. Твоя задача — по одному HTTP-методу проекта построить **машиночитаемую OpenAPI 3.1 спецификацию** в формате YAML, схемы запроса и ответа которой полны и взяты строго из кодовой базы, без фантазий. Результат обязан без ошибок проходить внешний линтер и рендериться в IDE-плагине «OpenAPI (Swagger) Editor».

Ты НЕ пишешь прозаическую документацию (это задача `/create-doc` и навыка `technical-documentation`). Ты производишь формальный контракт API.

---

## Графовый контекст (complement-модель)

Neo4j-граф дополняет repomix-output.xml, а не заменяет его. Модель:

- **repomix-output.xml** — полный текст кода (чтение DTO, контроллеров, валидаторов, конфигов роутинга)
- **MCP-инструменты** (если sa-helper-graph подключён) — структура и связи (CALLS, QUERIES, DEPENDS_ON)
- Оба источника используются одновременно; если MCP недоступен — только repomix / живой код

# Принципы

## 1. Код — единственный первоисточник истины

Тот же принцип, что в навыке `technical-documentation` (см. `.claude/skills/technical-documentation/SKILL.md:5`): рыночные REST-стандарты игнорируются, если противоречат реальной реализации в коде. Каждое поле схемы, каждое ограничение (`pattern`, `minLength`, `enum` …) обязано иметь происхождение в коде.

## 2. Запрет на фантазии (No Hallucination Gate)

Запрещено выдумывать ограничения, которых нет в коде.

- Если в коде/валидаторе нет `pattern` — не пиши `pattern`.
- Если длина поля нигде не ограничена — не пиши `maxLength`.
- Если значение поля в коде неизвестно или не удалось проследить — пометь его в `description` строкой `[NEEDS_INVESTIGATION]: <что проверить>` и не придумывай ни `example`, ни ограничений.

Лучше неполная, но честная схема, чем полная и выдуманная.

## 3. Целевая версия — OpenAPI 3.0.3 (по умолчанию)

По умолчанию генерируется `openapi: 3.0.3`. Причина — **рендеримость в целевом IDE-плагине «OpenAPI (Swagger) Editor»** (главное требование заказчика). Эмпирически установлено: плагин валидирует `type` как одиночную строку из набора `{array, boolean, integer, number, object, string}` и **отвергает union-типы OpenAPI 3.1** (`type: [string, "null"]`) со структурной ошибкой. Поэтому 3.1 для этого плагина непригоден.

**Кодирование `nullable` (КРИТИЧНО):**

- В **3.0** обнуляемость кодируется отдельным булевым ключом рядом с одиночным `type`:

  ```yaml
  type: string
  nullable: true
  ```

- Union-тип `type: [string, "null"]` (синтаксис 3.1) — **запрещён**: плагин выдаёт `Structural error ... type should be string`.
- Нуллабельный `$ref` в 3.0 нельзя пометить `nullable` напрямую — оборачивай: `allOf: [ {$ref: ...} ]` + `nullable: true` на родителе, либо оставляй без nullable, если код этого не требует.

**Если** проект/заказчик явно требует 3.1 И его тулинг это поддерживает — переключись на `openapi: 3.1.0` и кодируй nullable union-типом. Версия — параметр; дефолт 3.0.3 как наиболее совместимый.

> Требования к полям (`pattern`, `minLength`/`maxLength`, `enum`, `format`, `minimum`/`maximum`, `example`) одинаково доступны в 3.0.3 и 3.1 — выбор версии влияет только на способ кодирования `nullable`.

## 4. Полнота атрибутивного состава поля

Для каждого поля запроса и ответа заявляй максимум того, что подтверждено кодом:

| Аспект | Ключ OpenAPI | Источник в коде |
|--------|-------------|-----------------|
| Тип | `type` (+ `format`) | тип поля DTO / аннотация |
| Обязательность | имя поля в массиве `required` родительского объекта | not-null констрейнт, `@NotNull`, `required=True`, отсутствие default |
| Обнуляемость | `nullable: true` (3.0) рядом с одиночным `type` | nullable-колонка, `Optional[...]`, `?`-тип |
| Регэксп | `pattern` | валидатор `@Pattern`, regex в коде |
| Длина строки | `minLength` / `maxLength` | `@Size`, `max_length`, DDL-длина |
| Диапазон числа | `minimum` / `maximum` | `@Min`/`@Max`, проверки границ |
| Перечисление | `enum` | enum-тип, список допустимых значений |
| Пример | `example` (или `examples`) | дефолт, фикстура, тест, комментарий |

Детальная таблица соответствия — `resources/openapi_field_model.md`.

## 5. Структурность: `$ref`, а не дублирование

- Каждый именованный DTO выноси в `components/schemas/<DtoName>` и ссылайся через `$ref`.
- Вложенный объект → `type: object` + `properties` (или `$ref` на отдельную схему).
- Массив объектов → `type: array` + `items: { $ref: ... }`; массив скаляров → `type: array` + `items: { type: ... }`.
- Имя схемы = имя класса/DTO из кода (сохраняет трассируемость).

## 5а. Идентичность DTO = идентичность кода (КРИТИЧНО)

Схема в `components/schemas` соответствует ровно одному **классу DTO в коде**, а не «форме данных».

- **Переиспользуй** схему (один `$ref` на всех методах домена), только если методы используют **тот же класс кода** (тот же FQCN/файл). Тогда DTO объявляется один раз и шарится.
- **Не объединяй** два разных класса, даже если их поля идентичны. Разные классы в коде → **разные схемы** в документации. Пример: `modules/shows/models/Building.php` (главная) и `BuildingSphinxModel`/`BuildingItem` (поиск) — это РАЗНЫЕ схемы, несмотря на общий смысл «площадка».
- **Идентичность определяется по `x-source`** (FQCN/путь к файлу класса), а не по совпадению полей. Перед добавлением схемы ищи в `components/schemas` схему с тем же `x-source`: нашёл → переиспользуй; не нашёл → новая схема.
- **Имя схемы** = короткое имя класса. При коллизии имён РАЗНЫХ классов дизамбигуируй префиксом модуля/неймспейса: `Shows_Building` vs `Search_Building`. Совпадение имён разных классов без префикса запрещено.

## 6. Трассируемость к коду

В `description` ключевых схем/полей или через расширение `x-source` указывай происхождение (файл/класс), когда это не раздувает документ. Раздел «Технические пруфы» не является частью спеки, но факты о происхождении не должны теряться.

## 7. Объективная валидация — обязательный финал

Спека не считается готовой, пока внешний валидатор не вернул **0 ошибок**. Это не «на глаз», а воспроизводимый прогон (см. методологию, Этап 5). Цикл «правка → перепроверка» обязателен.

## 8. Относительные пути

Все ссылки на артефакты кода — относительные от корня проекта. Абсолютные пути запрещены.

## 9. Один файл на домен (накопительная модель)

Спецификации НЕ разбиваются по файлу-на-метод (это плодит дубли DTO). Вместо этого:

- Все методы одного API/домена живут в **одном файле** `sa_documentation/<сервис>-docs/api/openapi/<domain>.yaml` (например `ticketland.yaml`).
- При каждом вызове команды новый метод **дописывается** в этот файл: добавляется операция в `paths`, а его DTO мёржатся в общий `components/schemas` по правилу идентичности (принцип 5а).
- `<domain>` определяется детерминированно из хоста API (`servers[0].url`): `ticketland.ru` → `ticketland`. Если в аргументе команды явно передан домен/имя API — используется он (слугификация: lower-case, не-буквенно-цифровые → `_`).
- Общий `components/schemas` — главный выигрыш: DTO, реально переиспользуемые в коде между методами, объявляются один раз и шарятся через `$ref`.

# Методология (6 этапов)

Команда `/open-api` оркеструет эти этапы; навык задаёт их содержание.

## Этап 1: Разбор аргумента

Вход: `<API + METHOD + PATH>` (например, `Catalog GET /api/shows/{id}`).

- Выдели: имя API/сервиса/домена, HTTP-метод (`GET/POST/PUT/PATCH/DELETE`), path (`/api/shows/{id}`).
- Зафиксируй параметры пути (`{id}`), которые станут `parameters` с `in: path`.

## Этап 2: Целевой файл домена и идентификатор операции

**Файл — на домен, а не на метод** (принцип 9): `sa_documentation/<сервис>-docs/api/openapi/<domain>.yaml`.

1. Определи `<domain>` из хоста API (`servers[0].url`): `ticketland.ru` → `ticketland`. Если домен явно задан в аргументе — слугифицируй его (lower-case; не-буквенно-цифровые → `_`).
2. Если файл `sa_documentation/<сервис>-docs/api/openapi/<domain>.yaml` отсутствует — он будет создан; если есть — метод **дописывается** в него (Этап 4).

**`operationId`** (уникален в пределах файла) выводится из метода+path по алгоритму нормализации (согласован с `context-gen.md:144-157`):

1. Отбрось ведущий `/`; остальные `/` → camelCase или `_`; `{id}` → `ById`/`by_id`.
2. Добавь HTTP-метод префиксом (`get`/`post`/...): `GET /api/shows/{id}` → `getApiShowsById`.
3. Ключ path в `paths` — сам путь (`/api/shows/{id}`); при совпадении path с разными методами они сосуществуют как разные ключи-методы под одним path.

## Этап 3: Сбор контекста (якоря истины)

Переиспользуй правила добычи из `technical-documentation` (не копируй — следуй). Найди три якоря:

- **Anchor 1 (Routing):** конфиг роутинга / аннотация контроллера — как внешний path маппится на метод.
- **Anchor 2 (Contract):** интерфейс/контроллер/прото/аннотации — сигнатура метода, входные параметры, тип ответа.
- **Anchor 3 (Model):** DTO/Entity/сериализатор — ПОЛНЫЙ список полей и их ограничений (а не только используемые в текущем методе).

Запрещено приступать к генерации, пока не найдены минимум 2 из 3 якорей. Недостающее помечается `[NEEDS_INVESTIGATION]`.

**Ветка harvest:** если проект построен на фреймворке, который САМ генерирует OpenAPI (FastAPI `/openapi.json`, Springdoc/SpringFox, NestJS `@nestjs/swagger`, ASP.NET `/swagger.json`, drf-spectacular и т.п.) — найди этот источник и **извлеки** готовую спеку нужного метода, а не синтезируй. Синтез из кода — только когда авто-генерации нет.

## Этап 4: Reverse-engineering схем и merge в доменный файл

1. **Загрузи-или-создай** `sa_documentation/<сервис>-docs/api/openapi/<domain>.yaml`:
   - нет файла → создай скелет (`openapi: 3.0.3`, `info`, `servers`, пустые `paths`, `components.schemas`);
   - есть файл → распарси текущие `paths` и `components.schemas` для мёржа.
2. Собери схемы метода:
   - Вход: path/query/header-параметры, `requestBody` (для методов с телом) — полный атрибутивный состав (принцип 4).
   - Выход: успешный ответ (`2xx`) + известные из кода ошибки (`4xx`/`5xx`).
3. **Добавь операцию** в `paths.<path>.<method>`. Если такая операция уже есть — обнови её и предупреди (не плоди дубль).
4. **Мёрж схем по идентичности (принцип 5а):** для каждого нужного DTO найди в `components/schemas` схему с тем же `x-source` (FQCN/файл класса):
   - совпало → переиспользуй существующую (`$ref`), НЕ дублируй;
   - не совпало → добавь новую схему с именем класса; при коллизии имён разных классов — префикс модуля (`Shows_Building`).
   - У каждой схемы указывай `x-source` (FQCN/относительный путь) — это ключ идентичности для будущих мёржей.
5. Кодируй по эталону `examples/ideal_openapi_spec.yaml` и `resources/openapi_field_model.md`. `nullable` — ключом `nullable: true` рядом с одиночным `type` (принцип 3). Нуллабельный `$ref` — обёртка `nullable: true` + `allOf: [$ref]`.

## Этап 5: Объективная валидация и самокоррекция

Прогон внешнего валидатора через Bash (порядок предпочтения):

1. **Основной:** `npx @redocly/cli@latest lint --extends minimal <file>.yaml`
   > Флаг `--extends minimal` оставляет **структурную конформность** (ловит union-типы 3.1, битые `$ref`, `array` без `items`, неверные `type`) и отключает governance-правила набора `recommended` (`security-defined`, `info-license`, `no-server-example.com`). Это совпадает с поведением плагина «OpenAPI (Swagger) Editor» и не вынуждает выдумывать `security`/`license` (принцип 2).
2. **Фолбэк (нет Node/`npx`):** `python -m openapi_spec_validator <file>.yaml`
3. **Деградация (нет обоих):** синтаксис YAML `python -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))"` + **явное предупреждение**, что семантическая валидация пропущена.

Цикл: пока ошибки ≠ 0 — правь спеку и перезапускай линтер. Предел — 5 итераций; при превышении не удаляй файл, выдай отчёт с остаточными ошибками. Соответствуй чек-листу `resources/openapi_validation_checklist.md`.

## Этап 6: Завершение

Выведи путь к `.yaml`, итог валидации (валидатор, число ошибок/предупреждений) и список полей, помеченных `[NEEDS_INVESTIGATION]`, если такие есть.

# Анти-паттерны (частые ошибки)

- Union-тип `type: [string, "null"]` (3.1) в документе для плагина «OpenAPI (Swagger) Editor» → структурная ошибка `type should be string`. Используй `type: string` + `nullable: true` (3.0.3).
- Голый `type: object` без `properties`/`additionalProperties` для известного DTO — теряется состав полей.
- `type: array` без `items` — невалидно.
- Висячий `$ref` на несуществующую схему — ошибка линтера (типовой дефект; проверяется на Этапе 5).
- Выдуманные `example`/`pattern`, которых нет в коде — нарушение принципа 2.
- Абсолютные пути в `x-source`/комментариях — нарушение принципа 8.
