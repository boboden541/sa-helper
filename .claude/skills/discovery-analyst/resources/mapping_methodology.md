# Ресурс: Методология MAP (зоны изменений и разрывы)

Этап MAP превращает «что есть» (CONTEXT) в материал для развилок (DECIDE). Два инструмента.

## 1. Blast-radius — кто пострадает от изменения

Цель: понять, **что ещё сломается**, если мы тронем компонент/таблицу/интеграцию. Это источник «Что сломается» в карточках и блокеров.

- `graph_impact(entity_name)` — зависимые компоненты в коде.
- `graph_db_impact(object_name)` — транзитивные зависимости таблицы/view/процедуры (до 3 хопов).
- Для каждого значимого изменения из CONTEXT спроси: «а кто ещё это читает/пишет?» — и зафиксируй потребителей.

Типичные находки → карточки:
- «у старой базы есть другие читатели» → режим миграции как развилка.
- «поле используется отчётностью/DWH» → нельзя просто убрать.

## 2. Gap-finder — нестыковки и отсутствующие пути

Цель: найти **разрывы**, которые требуют доработок или решений. Источник «белых пятен» и развилок.

- `graph_call_chain(function_name)` — трассировка вызовов; ищи обрывы (нет ожидаемого следующего шага).
- `graph_db_lineage(object_name, direction)` — upstream/downstream данных; ищи отсутствующие или односторонние потоки.
- `graph_db_unresolved()` — имена таблиц/процедур в коде без DDL (битые ссылки, опечатки).
- `graph_db_orphans()` — объекты БД без связей (кандидаты на удаление/миграцию).

Паттерны разрывов → карточки:
- **Отсутствующий канал:** данные идут в систему A, но должны идти в B (нет OUT-канала).
- **Несовпадение моделей:** сущность в системе A имеет двойную роль, в B — разделена.
- **Осиротевшие данные:** таблица/поле без читателей или без писателя.
- **Захардкоженное поведение:** магические константы, зашитые id — без решения их не перенести.
- **Односторонний поток:** есть чтение, нет записи (или наоборот).

## Выход MAP
- Раздел «Зоны изменений» и «Разрывы» в `00_context.md`.
- Каждый значимый разрыв → кандидат в карточку `D-N` (если закрывается решением человека) ИЛИ в `04_action_points.md` как гипотеза (если закрывается расследованием).
