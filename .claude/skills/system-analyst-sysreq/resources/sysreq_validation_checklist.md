# Чек-лист валидации документа системных требований

## 1. Структура документа (шаблон Confluence)

- [ ] Документ начинается с заголовка `[СТ] <PROJECT>-<NNN> <Название>`
- [ ] **Раздел 1 — Введение:**
  - [ ] Таблица метаданных (наименование продукта, ответственные, Epic, БФТ, статус)
  - [ ] Термины и определения (таблица)
  - [ ] Ссылки (таблица)
  - [ ] История изменений (таблица: Дата | Автор | Суть изменений)
- [ ] **Раздел 2 — Общее описание:**
  - [ ] As-Is: описание текущего поведения с код-доказательствами
  - [ ] Ключевые компоненты (таблица: Компонент | Роль | Файл:строка)
  - [ ] Ограничения текущего решения (нумерованный список с доказательствами)
  - [ ] Ссылка на архитектурное решение
  - [ ] Диаграмма компонентов (PlantUML)
  - [ ] Схема последовательности (PlantUML)
- [ ] **Раздел 3 — План миграции:**
  - [ ] Диаграмма этапов (PlantUML activity diagram)
  - [ ] Таблица этапов (Этап | Действие | Затрагиваемые объекты | Откат)
  - [ ] Критерии готовности для каждого этапа
- [ ] **Раздел 4 — Функциональные требования (Backend / БД / API):**
  - [ ] Содержит только серверные задачи: БД, backend-логика, API, фоновые процессы, межсервисные интеграции
  - [ ] Каждый блок = логическая группа задач
  - [ ] Каждая задача содержит все обязательные подсекции (см. п.2)
- [ ] **Раздел 5 — Требования к интерфейсам (Frontend / UI):**
  - [ ] Содержит только клиентские задачи: верстка, UI-компоненты, клиентские API-интеграции, микроразметка, роутинг
  - [ ] Если UI-изменений нет — раздел опущен с пометкой «Не применимо»
  - [ ] Если есть — каждая задача содержит обязательные подсекции (см. п.2), включая задачи по вёрстке: для них состав подразделов тот же, что и для серверных задач
  - [ ] Для задач по вёрстке в таблице затрагиваемых компонентов перечислены экраны, UI-компоненты и макеты; `файл:строка` указан только для уже существующих компонентов
- [ ] **Разделение Backend / Frontend:**
  - [ ] Задачи корректно распределены между разделами 4 и 5 (нет серверных задач в разделе 5 и наоборот)
  - [ ] Смежные фичи (требуют и BE, и FE) представлены двумя задачами в разных разделах, связанными через «Зависимости»
  - [ ] [CRITICAL] Серверная задача помещена в раздел 5 или клиентская — в раздел 4 — 🔴
- [ ] **Ревью требований** — таблица согласования (аналитик, разработка, тестирование)
- [ ] **Риски и ограничения:**
  - [ ] Таблица рисков (ID | Риск | Вероятность | Влияние | Митигация)
  - [ ] Нумерованный список ограничений
- [ ] [CRITICAL] Пропущен любой из обязательных разделов — 🔴

## 2. Качество каждой задачи

Нормативный состав подразделов и допустимый уровень изложения каждого — `abstraction_levels.md` (разделы 2 и 3).

- [ ] Таблица метаданных (Ответственный за тех. реализацию + Задача на разработку со статусом)
- [ ] **Общее описание доработки** (уровень Л1) — только контекст: как сейчас / как будет / особенности; без требований и призывов к действию, без перечисления полей и таблиц
- [ ] **Описание доработок** (уровень Л2) — первое предложение призыв к действию («Нужно реализовать / добавить / расширить <объект> — <результат>»); дальше правила от подлежащего («метод должен…», «экран должен…»); ветвления логики — отдельными пунктами «Ветвление „…“»
- [ ] Обоснование — почему выбран этот подход
- [ ] Блоки специфики формы — если применимы к типу задачи (`abstraction_levels.md`, раздел 3)
- [ ] Затрагиваемые компоненты — таблица (Компонент | Тип изменения | Файл:строка)
- [ ] Критерии приёмки — нумерованный список проверяемых условий
- [ ] Зависимости — явно указаны (нет / после задачи N.M)
- [ ] Порядок подразделов совпадает с нормативным составом из контракта
- [ ] Служебная пометка уровней — один раз в начале раздела с задачами, не в каждой задаче
- [ ] Ссылка «правила — как в задаче N.M» сопровождается пересказом сути своими словами
- [ ] [CRITICAL] Отсутствует подраздел «Описание доработок» хотя бы у одной задачи — 🔴
- [ ] [CRITICAL] «Описание доработок» не открывается призывом к действию (таксономия без глаголов: «Сущности:», «Потоки данных:» в первом пункте) — 🔴
- [ ] [CRITICAL] В подразделах «Общее описание доработки» или «Описание доработок» присутствует маркер deny-списка (`abstraction_levels.md`, раздел 4): ссылка `файл:строка`, идентификатор кода, имя библиотеки/СУБД, фрагмент кода или запроса — 🔴
- [ ] [CRITICAL] В подразделе «Общее описание доработки» есть требования или призывы к действию («нужно реализовать», «метод должен») — 🔴
- [ ] [CRITICAL] Описание без обоснования и таблицы затрагиваемых компонентов — 🔴

## 2а. Согласованность артефактов навыка

- [ ] Состав подразделов задачи в теле форм эталона совпадает с нормативным составом в `abstraction_levels.md` (раздел 2)
- [ ] Оглавление эталона перечисляет для каждой формы тот же состав подразделов, что и тело формы
- [ ] Перечень подразделов задачи задан дословно ровно в одном нормативном месте — в контракте; в эталоне, навыке и инструкции команды на него стоит ссылка

## 3. Контракт API (если задача создаёт или меняет API-метод)

Канон таблиц и полный состав блока — `abstraction_levels.md`, раздел 3.1; шаблон — `technical-documentation/examples/ideal_api_document.md`.

- [ ] Блок «Контракт API» находится прямо в задаче (разработчик не ходит за контрактом в другие документы)
- [ ] Входные и выходные параметры — таблицами с каноническими колонками: `Параметр | Тип | Обязательность | Описание | Пример | Комментарий | Мапинг (БД/Метод/Сервис/API)`
- [ ] Обязательность — по легенде Да / Да (nullable) / Условно
- [ ] Контейнеры типизированы `Object<X>` / `Array<X>` / `Array<скаляр>`; вложенные объекты раскрыты подтаблицами «Описание вложенного `X`»
- [ ] Мапинг каждого поля на origin: метод API источника + атрибут ответа (или `ТАБЛИЦА.ПОЛЕ` — только для собственной БД задачи); объекты БД за API внешнего сервиса (SP, view) в мапинг не попадают
- [ ] Есть таблица соответствия ключей: ключ нашего метода → метод API источника → ключ, куда подставляется наш ключ
- [ ] Алгоритм метода — activity-диаграмма PlantUML (порядок шагов и ветвления); sequence-диаграмма при более чем двух участниках
- [ ] Коды ответов — таблицей (код | когда возвращается)
- [ ] Неизвестные атрибуты источника помечены `[NEEDS_INVESTIGATION]`, имена не выдуманы
- [ ] [CRITICAL] Таблицы параметров с разными наборами колонок (без «Типа», «Описания» или «Мапинга») — 🔴
- [ ] [CRITICAL] Мапинг поля на объект БД, скрытый за API внешнего сервиса (хранимая процедура, view) — 🔴

## 4. Модель данных и обработка данных (если применимо)

- [ ] **Модель данных** (задача создаёт/меняет объекты БД): указано имя таблицы, приведён DDL с constraints (блок `sql`), фрагмент ERD (PlantUML) с местом таблицы среди соседей
- [ ] [CRITICAL] Задача меняет БД, но без DDL или без ERD — 🔴
- [ ] Таблица маршрутизации (Сущность | Метод вызова | Отправляемые события)
- [ ] Таблица источников данных (Сущность | DataSource | SQL-запрос)
- [ ] SQL-запросы в блоках кода `sql` с комментариями

## 5. Нефункциональные требования

- [ ] Каждое NFR содержит триаду: числовое значение + единица измерения + условие проверки
- [ ] Нумерованный список
- [ ] Измеримость выражена характеристикой поведения системы, а не элементом реализации: имена классов, методов и размеры пулов признаком измеримости **не являются** и не требуются
- [ ] [CRITICAL] Нет оценочных формулировок («быстро», «надёжно», «удобно»)

## 6. План миграции

- [ ] Этапы упорядочены логически (зависимости учтены)
- [ ] Каждый этап содержит критерий готовности (как проверить)
- [ ] Каждый этап содержит процедуру отката
- [ ] Диаграмма миграции (PlantUML) соответствует текстовому плану

## 7. Риски и ограничения

- [ ] Каждый риск содержит оценку вероятности и влияния
- [ ] Каждый риск содержит конкретную митигацию
- [ ] Ограничения явно перечислены (что решение НЕ покрывает)
- [ ] Зафиксированы компоненты, которые НЕ должны быть затронуты (backward compatibility)

## 8. Визуализация

- [ ] Все диаграммы используют PlantUML (Mermaid запрещён)
- [ ] Диаграмма компонентов корректно отражает архитектуру
- [ ] Схема последовательности отражает порядок взаимодействия
- [ ] Все надписи на стрелках — на русском языке
- [ ] Технические имена указаны в скобках
- [ ] Все блоки PlantUML корректно закрыты (`@startuml` / `@enduml`)

## 9. Форматирование

- [ ] Нумерация разделов последовательная (1, 2, 3... / 3.1, 3.2... / 3.1.1, 3.1.2...)
- [ ] Таблицы используются для структурированных данных
- [ ] JSON/SQL — в блоках кода с соответствующей разметкой
- [ ] [CRITICAL] Нет абсолютных путей (`file:///`, `/Users/...`) — только относительные

## 10. Фактологическая точность

- [ ] Все утверждения в As-Is подтверждены код-доказательствами (файл:строка)
- [ ] Совпадают названия таблиц, полей, методов, классов с реальными в коде
- [ ] [CRITICAL] Утверждения, которые нельзя подтвердить кодом, помечены `[NEEDS_INVESTIGATION]`

## Hard Gates (Условия СТРОГОГО 🔴)

1. **Template Gate:** Отсутствует обязательный раздел (Введение, Общее описание с As-Is, План миграции, Функциональные блоки, Ревью, Риски и ограничения) — 🔴.
2. **As-Is Gate:** Раздел «Описание текущего поведения» без код-доказательств — 🔴.
3. **Task Gate:** Задачи без обоснования, таблицы затрагиваемых компонентов или критериев приёмки — 🔴. Применяется ко всем формам задач, включая задачи по вёрстке.
4. **Improvement Description Gate:** Хотя бы у одной задачи отсутствует подраздел «Описание доработок» — 🔴.
5. **Altitude Gate:** В подразделе «Общее описание доработки» или «Описание доработок» присутствует хотя бы один маркер deny-списка — 🔴. Проверяемые признаки (полный перечень — `abstraction_levels.md`, раздел 4):
   - ссылка на позицию в файле по шаблону `\S+\.\w+:\d+` (например `install.sh:51`);
   - идентификатор кода: имя класса, метода, функции, переменной, сигнатура вызова;
   - имя библиотеки, фреймворка или СУБД как средства реализации;
   - фрагмент кода или запроса к хранилищу.
   Оценочные суждения («слишком технично», «избыточно подробно») основанием для 🔴 по этому гейту **не являются**.
6. **Acceptance Gate:** Критерии приёмки непроверяемые («работает корректно» без конкретики) — 🔴.
7. **NFR Gate:** NFR без триады «числовое значение + единица измерения + условие проверки» или с оценочными формулировками — 🔴. Отсутствие имён классов, методов и размеров пулов основанием для 🔴 **не является**.
8. **Migration Gate:** План миграции без процедур отката — 🔴.
9. **Risks Gate:** Риски без митигации — 🔴.
10. **PlantUML Gate:** Диаграммы в формате Mermaid или с незакрытыми блоками — 🔴.
11. **Path Gate:** Абсолютные пути в ссылках — 🔴.
12. **Hallucination Gate:** Утверждение о поведении системы, не подтверждённое кодом и не помеченное `[NEEDS_INVESTIGATION]` — 🔴. Код-доказательство размещается в подразделе «Затрагиваемые компоненты» и в разделе As-Is; его отсутствие в описательных подразделах нарушением **не является**.
13. **Action Gate:** Подраздел «Описание доработок» не открывается призывом к действию («Нужно <реализовать / добавить / расширить> <объект> — <результат>») — первый пункт представляет собой таксономию без глаголов действия («Сущности:», «Потоки данных:») — 🔴. Также 🔴: требования или призывы к действию внутри «Общего описания доработки» (Л1).
14. **Contract Gate:** Задача создаёт или меняет API-метод, а блока «Контракт API» с каноническими таблицами нет, либо таблицы контракта имеют разные наборы колонок (без «Типа», «Описания» или «Мапинга»), либо мапинг поля указывает на объект БД, скрытый за API внешнего сервиса, — 🔴. Задача создаёт или меняет объекты БД, а DDL или ERD отсутствуют, — 🔴. Применяется к документам, созданным после введения блока (см. оговорки ниже).

---

## Оговорки о неприменимости

Гейты `Improvement Description Gate` (№4), `Altitude Gate` (№5), `Action Gate` (№13) и `Contract Gate` (№14), а также пункты 2, 2а, 3 и 4 чек-листа, опирающиеся на контракт уровней, **не применяются** к документам, созданным до введения контракта `abstraction_levels.md` — то есть к документам, у которых ни одна задача не содержит подраздела «Описание доработок» и первый описательный подраздел назван «Общее описание функционала», «Общее описание требований» или «Описание».

Для таких документов:

- **НЕ выставляй 🔴** за отсутствие подраздела «Описание доработок».
- **НЕ выставляй 🔴** за маркеры deny-списка в описательных подразделах.
- **НЕ выставляй 🔴** за то, что «Описание доработок» не открывается призывом к действию.
- **НЕ выставляй 🔴** за отсутствие канонических таблиц контракта API или DDL/ERD.
- **НЕ выставляй 🔴** за расхождение состава подразделов с нормативным.
- Отметь в отчёте: «документ создан по предыдущей версии эталона; гейты уровней изложения неприменимы».

Ретрофит ранее созданных документов к новой структуре не выполняется.
