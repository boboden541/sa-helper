# Методология разработки (перенос из команд /impl-run + /impl-bootstrap)

Методология автономной работы агента-разработчика над задачей конвейера AI-Harness:
baseline до правок, изоляция в worktree, TDD с RED-гейтом и circuit breaker, гейты качества.

## Принципы

1. Карточка задачи — единственный рабочий контракт. Постановку и досье открываешь, чтобы
   сверить точность понимания, а не расширять скоуп.
2. Ничего вне границ задачи: вскрылся пробел — не делай молча, предложи отдельную задачу.
3. Тесты прежде кода; красная проверка — красный вердикт; ничего не «дотягиваем».
4. Основное дерево репозитория не трогаешь: вся работа в worktree задачи на ветке задачи.

## Этап 0. Baseline (до любых правок)

Агент не имеет права писать код в репозиторий, который не может собрать и протестировать.
1. Собери систему и прогони её тесты ДО изменений; зафиксируй снимок (passed/failed/
   errors/skipped + падения сокращённо) в комментарии к задаче.
2. Сборка ломается на зависимостях или чужом коде → blocked с отчётом: репозиторий сломан
   до нас, чинить вне своей задачи нельзя.
3. Красный baseline — не блокер: это честная точка отсчёта; но твоя работа не должна
   опираться на падающие чужие тесты без оговорки в отчёте.
4. Тестов в репозитории нет → пометь «no test suite»: первой фазой идут характеризационные
   тесты, а не фичи.

## Этап 1. План работ (чек-лист)

Разложи задачу, как разработчик, контролирующий себя: 4–10 атомарных шагов в TDD-порядке
(тесты → код → гейты → коммит). Обновляй чек-лист задачи через контракт отчёта
(checklist_updates): начал шаг — in_progress, закончил — closed сразу, не партиями.
Появились новые работы — добавь пункт и честно проведи его через весь цикл; шаги
постфактум ради галочек не добавляй.

**Режим доработки после ревью:** прочитай вердикт и находки (файл:строка + суть + как
чинить). Дополни СВОЙ план переосмысленными шагами доработки (не копия находок), веди их
по общим правилам — так видно, что скоуп задачи изменился.

## Этап 2. TDD RED

1. По карточке напиши тесты acceptance-критериев: имена test_ac_<номер>_<действие>.
   Тесты опираются только на публичный контракт из карточки, не на несуществующий код.
2. RED-гейт: новые тесты обязаны упасть. Прошли на пустом коде — тесты фиктивны, переписывай.
3. Результат RED зафиксируй комментарием к задаче.

## Этап 3. TDD GREEN (circuit breaker = 4)

1. Минимальная реализация ровно под падающие тесты, по конвенциям репозитория и
   Golden Reference из досье.
2. Каждый цикл «исправил → прогнал» — короткий комментарий: что пробовал, что вышло.
3. Больше 4 итераций → заблокируй задачу с отчётом: что не сходится и что нужно человеку.

## Этап 4. Гейты качества

1. Линт (если настроен в репозитории) — прогони.
2. Impact-лестница: найди импортёров изменённых файлов и прогони их тесты (суженный скоуп).
3. Coverage: инструмент есть → дельта по изменённым файлам ≥ 80%; нет — честно «skipped».
4. Data-only задачи (DDL/скрипты): TDD сводится к проверке скриптов на ревью — скажи об
   этом в отчёте.

## Этап 5. Вне скоупа и завершение

1. Вскрылась недостающая работа (миграция, реестр, контур тестов) — НЕ делай её в текущей
   задаче: предложи новую задачу через вопросы/комментарий отчёта и продолжай свою.
2. Коммит в ветке задачи осмысленным сообщением; merge и переключение веток — не твоё,
   слияние выполняет конвейер.
3. Отчёт по контракту раннера: status, summary_md (поймёт junior: что сделано и как
   проверялось), checklist_updates, proposed_transition. Комментарии — от первого лица.
