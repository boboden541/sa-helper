# Навык: Искусство написания комментариев (Task Journal Writing)

> Канон ведения журнала задачи `harness/comments/T<k>.md`. Навык подключают
> все авторы журнала: исполнитель (`/impl-run`), ревьюер (`/impl-review`),
> демон конвейера. Читатель комментария — человек, который **не видел твою
> сессию**: junior-специалист, аналитик, будущий ты через неделю.

## Миссия

Комментарий — это отчёт, а не пометка. Читатель должен за 15 секунд понять:
**что произошло, почему это важно, что будет дальше** — без открытия карточки,
манифеста или кода. Если для понимания нужны знания из твоей головы —
комментарий плохой.

## Формат записи

Одна запись журнала:

```
- [YYYY-MM-DD HH:MM | author] **Заголовок события** — суть в одной строке.
  Тело записи (markdown): контекст, детали, ссылки.
  · подпункты — только через «·», не через «-»
  (строка с «-» выглядит как новая запись журнала)
```

- Первая строка: `- [время | author] **Что произошло** — коротко`.
- Тело — при необходимости; markdown: **жирные** вводные, `код`, списки «·»,
  таблицы допустимы.
- author ∈ `agent | reviewer | daemon | human`.
- Одна запись = одно событие. Не склеивай RED-гейт и коммит в один абзац.

## Три вопроса, на которые отвечает хорошая запись

1. **Что произошло?** Факт, конкретно: не «тесты починил», а
   «GREEN: 24/24 теста зелёные, включая новые `test_ac_4_1_2_1_*`».
2. **Почему это важно / что из этого следует?** Связь с критерием, находкой,
   планом: «закрывает AC-4.1.2.1; finding b1 устранён».
3. **Что дальше?** Следующий шаг или ожидание: «передаю на ревью», «жду
   решения по X».

## Правила ясности (для junior-читателя)

1. **Расшифровывай при первом употреблении**: не «IMP упал», а
   «impact-прогон (все тесты сервиса) упал».
2. **Числа вместо оценок**: «8 тестов падают, все — новые» лучше, чем
   «местами красное».
3. **Ссылки-якоря**: `AC-4.1.2.1`, `файл:строка`, имя теста, ветка — читатель
   должен уметь проверить тебя за один клик.
4. **Причины, не только действия**: не «откатил миграцию», а «откатил
   миграцию: последовательность стартовала с 1 вместо 1000000 (СТ 4.1.1.5)».
5. **Без снисходительности и без жаргона-ради-жаргона**: пиши так, как
   объяснял бы вчерашнему студенту, который умён, но контекста не имеет.
6. **Плохие новости — такими же ровным тоном**: эскалация — не признание
   вины, а данные для решения. Факт → причина → варианты.

## До / после

Плохо (непонятно ни что, ни зачем):

```
- [10:42 | agent] Починил тесты, всё ок, передаю на ревью.
```

Хорошо (junior понимает без контекста):

```
- [10:42 | agent] **GREEN со 2-й итерации** — 24/24 теста зелёные.
  Причина 1-й итерации: последовательность `draft_event_id` стартовала с 1,
  а СТ 4.1.1.5 требует старт с 1000000 — поправил `V1__initial_draft_schema.sql:12`.
  Закрыты AC-4.1.1.1, AC-4.1.1.2. Гейты: build ✅ · test ✅ · impact ✅ (685 passed, 0 failed).
  Дальше: коммит `[FNR-8/T2]` и передача на ревью.
```

## Шаблоны типовых событий

| Событие | Заголовок | Обязательно в теле |
|---|---|---|
| Старт задачи | `**Старт: <суть>**` | какие AC закрываем, план работ (чел. шагов), worktree/ветка |
| RED-гейт | `**RED: N/M тестов падают**` | какие новые тесты, почему падение честное, лог |
| GREEN | `**GREEN с k-й итерации**` | причина итераций, что закрыто (AC), гейты |
| Гейты/impact | `**Impact: N passed / M failed**` | что прогоняли, регрессы или их отсутствие |
| Эскалация / Blocked | `⏸ **Требуется решение**` | факт → причина → варианты решения → что нажать |
| Ответ человеку | `**Ответ на ваш комментарий**` | цитата вопроса кратко, ответ, что сделал по нему |
| Вердикт ревью | `**Ревью: CHANGES_REQUESTED**` | число находок по существенности, ссылка на отчёт, что в чек-листе |
| Завершение | `**Задача завершена**` | коммит, ветка, что передано дальше |

## Демон и автоматические записи

Демон пишет переходы статусов кратко (однострочно) — это «сердцебиение»
конвейера, а не отчёт. При эскалациях демон и агент обязаны писать полный
отчёт по шаблону «Эскалация» выше.
