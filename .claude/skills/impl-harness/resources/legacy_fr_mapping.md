# Ресурс: идентификация требований и легаси-маппинг

Канон СТ (harness-ready): каждая задача `#### <номер> <название>` имеет строку метаданных
`| FR-ID | FR-<номер задачи> |`, критерии приёмки пронумерованы `AC-<номер задачи>.<k>`,
мульти-системные документы содержат раздел «Затронутые системы и контракты».

## Маппинг для документов старого образца (без FR-ID)

Если в задаче нет строки `| FR-ID |` — отображение **механическое**, без изобретения имён:

- `#### 4.2` → `FR-4.2`; `#### 4.2.1` → `FR-4.2.1`; `#### 5.1.2` → `FR-5.1.2`;
- критерии приёмки (`Критерии приёмки`) задачи получают `AC-<номер задачи>.1`, `.2`, …
  по порядку следования.

Карта соответствия фиксируется в `dossier.md` (раздел **ID map**): номер задачи → FR-ID →
заголовок → система. ID map — единственное место, где живёт соответствие; карточки задач и
манифест ссылаются только на FR-/AC-ID.

## Шлюз пробелов (что считается недостаточным входом)

`/impl-plan` останавливается с gap-report (артефакты не создаются), если:

1. В документе нет ни одной распознаваемой задачи (`#### <номер> <название>`) или задач нет вовсе.
2. У какой-либо задачи нет секции «Критерии приёмки» — задача неприемлема для реализации.
3. Критерии не проверяемы (нет конкретики: «работает корректно» без условий).
4. Документ мульти-системный (2+ систем), а раздел о затронутых системах/контрактах отсутствует —
   непонятно, в каких репозиториях работать и где точки интеграции.
5. Указанных в документе систем нет в `workspaces.yaml` (или их bootstrap = `stop`).

Формат gap-report: перечень пробелов с указанием раздела/задачи СТ и что именно дописать человеку.
После исправления человеком — повторный запуск строит план.
