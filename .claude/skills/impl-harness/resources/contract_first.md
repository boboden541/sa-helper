# Ресурс: Contract-First для мульти-системных задач

Когда доработка затрагивает 2+ систем и меняет **контракт взаимодействия** (API, схема сообщений,
формат выгрузки, схема данных, доступная другой стороне), реализация начинается с фиксации
контракта — прежде чем кто-либо из участников начнёт писать логику (v2 §8).

## Фазы плана

| Фаза | Что делает | Статус гейтов |
|---|---|---|
| `contract` | создаёт/меняет спецификацию взаимодействия: OpenAPI/protobuf/JSON Schema/DDL общей таблицы/формат файла выгрузки. Никакой бизнес-логики. | обычные (валидация схемы — если инструмент есть; иначе `skipped`) |
| `producer` | сторона, порождающая данные/события. Реализуется **против замороженного контракта**. | build/test |
| `consumer` | сторона-потребитель. Реализуется против контракта (мок поставщика — если есть инструмент мокирования; иначе фейковые фикстуры из схемы). | build/test |
| `regular` | одно-системная задача или не связанная с контрактом | обычные |
| `characterization` | первая задача по репо без тестов: snapshot-тесты As-Is (v2 §7 п. 3) | тесты = фиксация текущего поведения |

Правила DAG: `contract` → (`producer`, `consumer`); `characterization` — всегда первая задача
своего репозитория.

## Что считается контрактом

- HTTP/gRPC API между системами;
- сообщения брокера, события, очереди;
- форматы выгрузки/файлов, разделяемые таблицы и вьюхи;
- **общая схема БД**, читаемая другой системой (владелец схемы — producer).

Не контракт: внутренние рефакторинги, UI одного сервиса, конфигурация одного сервиса —
такие задачи остаются `regular`.

## Валидация контракта

- OpenAPI/AsyncAPI: валидатор (`spectral`, `openapi-spec-validator`), если доступен; иначе —
  структурная самопроверка агентом + пометка `skipped` в гейте.
- protobuf: `buf lint` при наличии.
- Схема БД/файла: сверка с требованиями (раздел «Затронутые системы и контракты» СТ) + ревью.
- Доступность инструмента проверяется `shutil.which`-паттерном; отсутствие — деградация, не STOP.
