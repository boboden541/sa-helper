# Методология составления ПСИ

Составление документа ПСИ (процедура приёмо-сдаточных испытаний) по истории: инструкция,
по которой человек без «техники» воспроизведёт проверку функционала руками. Методология
переносит дух канона `/fnr-system-requirements`: идеальный документ — эталон, самопроверка —
по чек-листу, результат — файл в папке FNR.

## Источники скилла (читать до начала)

1. `examples/ideal_psi.md` — эталон-шаблон документа ПСИ: канон структуры и языка,
   абстрагированный от конкретных проектов (скелет повторяет признанный документ
   FNR_8). Заполняешь вместо <заполнителей>, инструкции «>» в документ не пишешь:
   шапка, «Что реализовано (простыми словами)», словарик, правила, группы пунктов,
   замечания.
2. `resources/psi_checklist.md` — чек-лист самопроверки перед сдачей документа.
3. `scripts/validate_psi.py` — структурный валидатор; прогони его по готовому документу
   (python3 scripts/validate_psi.py <psi.md>), блокеры — исправь до сдачи.

## Принципы

1. Пункт ПСИ — элементарное действие: одна проверка, один наблюдаемый результат.
2. Ожидаемый результат берётся из постановки и отчётов задач, не «улучшается».
3. Документ самодостаточен: пункты выполняются человеком без помощи инженера.
4. Непокрытое — честно в замечания, не спрятано.

## Процедура

### Этап 1. Сбор источников

1. Прочитай постановку истории целиком и связанные задачи/отчёты (разработка, ревью,
   тестирование) — они показывают, что реально реализовано и как проверялось.
2. Определи «папку FNR» документа: путь сохранения задаёт поле истории «Путь сохранения
   ПСИ» (psi_path) — например …/sa_documentation/FNR/FNR_8/psi.md. Путь пуст → конвейер
   сам сохранит в <путь проекта>/.harness/psi/<код истории>/psi.md.

### Этап 2. Составление документа

Соблюдай канон структуры идеального ПСИ (все разделы — в `examples/ideal_psi.md`):

1. **Заголовок** — «Процедура приёмо-сдаточных испытаний (ПСИ): <функционал> (<код>)».
2. **Назначение** — для кого документ и как им пользоваться; документ самодостаточен.
3. **Дата и версия** документа.
4. **Что реализовано (простыми словами)** — как было → как стало; можно схемой.
5. **Словарик терминов** — таблица «Термин | Что это (для читателя вне IT)».
6. **Правила проведения ПСИ** — пара «Действие → Ожидаемый результат», порядок групп,
   поведение при расхождении, как копировать команды.
7. **Группы пунктов** (Г1…Гn): каждый пункт — «Действие» (команда/ссылка/шаг целиком,
   копируется как есть) + «Ожидаемый результат» (наблюдаемый) + «Если расхождение» (где
   искать причину и когда ставить ✗). Негативные проверки обязательны.
8. **Замечания по итогам прогона** (первая версия — «Пилотный прогон не проводился»).

**Версия v2+ (изменение требований).** Если это не первая версия (или у истории стоит отметка
«ПСИ устарел» — увидишь её в контексте/флаге psi_stale), шапка начинается с раздела
**«Что изменилось против vN-1»**: какие пункты добавлены, у каких изменилось действие/ожидание,
какие удалены и почему (со ссылкой на событие изменения требований из хроники). Документ читается
сверху вниз: человек сначала видит диф, потом полный документ. ПРИМЕЧАНИЕ о дополнениях:
дополнения (новые требования) вплетаются в группы пунктов по месту, НЕ складываются хронологией
в шапку; история изменений живёт в разделе «Что изменилось» и в хрониках истории, не в теле
документа. Противоположный пример — «старый» FNR_8/psi.md с девятью «Дополнениями» в шапке:
так не делать. Замечания по итогам прогона — только актуальные; история вердиктов — в протоколах
прогонов (psi_run) и хрониках, не в шапке.

Разделы 1–6 и 8 собери в **шапку документа** (единый markdown-блок) — она уходит в поле
«preambleMd» при создании версии; раздел 7 (группы пунктов) — в `sections`:

```
sections: [
  {"heading": "Г1. <группа проверок>",
   "items": [{"action": "<элементарное действие, воспроизводимое руками>",
              "expected": "<наблюдаемый ожидаемый результат>"}]},
  …
]
```

### Этап 3. Самопроверка

1. Прогони `scripts/validate_psi.py` по собранному документу — блокеры исправь.
2. Пройди `resources/psi_checklist.md` пункт за пунктом.

### Этап 4. Сохранение

Версия ПСИ сохраняется через интерфейс/API истории (sections + preambleMd). **Файл пишет
конвейер автоматически** при сохранении каждой версии: документ ложится по «Пути сохранения
ПСИ» истории (например …/sa_documentation/FNR/FNR_8/psi.md — рядом с task.md и
concept.md); путь не задан — <путь проекта>/.harness/psi/<код истории>/psi.md. Факт записи
и путь видны в хронике истории. Новая версия — новый файл поверх (версии хранятся и в БД).


## Регистрация документа (обязательна)

Документ ПСИ живёт в системе, а не в разговоре и не во временных папках:
1. Файл — строго по `psiPath` задачи (например `FNR/FNR_8/psi.md` в чекауте
   проекта). Папки `tmp/` и случайные места запрещены: задача уйдёт в done —
   worktree и tmp вычищаются, документ пропадёт.
2. Документ версии — через карточку истории / `POST /stories/{код}/psi`
   (создаёт `psi_document` версии). Без записи в `psi_document` документ
   не существует для конвейера: зачёт M6 невозможен. Из среды прогона
   (контейнер) бэкенд доступен как `http://host.docker.internal:8000` —
   `localhost:8000` внутри контейнера это НЕ конвейер («пустой стаб»,
   v23–v25, 03.11.2026). Формат sections — те же группы пунктов, что в
   файле; регистрация переписывает psi-чеклист истории.
   Недоступно — напиши в отчёте «требуется регистрация vN человеком».
3. Psi-чеклист задачи (`kind=psi`) — источник истины для гейта M6: пункты
   с `failed` блокируют переход в done. После прогона — `psi_run` с
   вердиктами (passed/failed) как снапшот сверки.


## Вердикты: без факта вердикта нет

- «ПРОЙДЕН» ставится ТОЛЬКО с фактическим результатом в `actual`: вывод команды,
  строка SQL-результата, значение счётчика — то, что человек может перепроверить.
  «Прошло, потому что должно» — запрещено: вердикт без факта невалиден
  (инцидент 02.11: агент отчитал «всё ✓» против действительности владельца).
- Не смог выполнить пункт из-за среды (нет docker/сервиса/доступа) → вердикт
  «не прогонялся» + отдельное замечание с точной причиной; НЕ ставь «пройден»
  по косвенным признакам. Среда должна быть поднята тобой по правилам
  методологии разработки — на это и дан docker.
- Пункт ПСИ НЕ ПРОЙДЕН → заводишь БАГ: `POST /api/v1/tasks` (type=bug,
  storyCode=код истории, title=«ПСИ П.x: <суть>»), привязываешь
  `POST /stories/{код}/psi/link-bug`, пункт чеклиста → failed. Без заведённого
  бага пункт failed не оставлять.
- ВСЕ пункты ПРОЙДЕНЫ (ни одного failed/todo) → САМ предлагаешь переход
  в done (`proposed_transition: {"to": "done"}`): ребро разрешено агенту,
  и это ОБЯЗАННОСТЬ, не опция. Объявлять blocked при зелёном psi-чеклисте
  ЗАПРЕЩЕНО: blocked — только когда работа не сходится. Иначе человек
  вынужден вручную возвращать задачу по кругу (VITRINA-1, 03.11: история
  трижды уходила в blocked при готовом, верифицированном документе).
  ПСИ, проваленный владельцем ранее, не повод молчать: актуализировал →
  верифицировал → предлагай done; финальное подтверждение всё равно
  делает человек (Готово → Завершено).
  гейт M6 пройдёт (psi-чеклист без failed). Ждать человека не нужно.
- Человек afterward вручную переносит историю из «Готово» в «Завершено» —
  это вне твоей работы.
