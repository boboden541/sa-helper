## Что реализовано (простыми словами)

**Как было.** Сервис интеграций (BI) получал каталог мероприятий из внешних билетных систем («шлюзов») и записывал его напрямую в старую базу «Базис» (uat_db) через её хранимые процедуры. Новые системы платформы не могли эти данные принять: у «Базиса» одни идентификаторы (целые числа), у платформы TicketsCloud — другие (длинные строковые коды ObjectId), а сырые данные шлюзов часто неполные и без ручной проверки в «бою» им делать нечего.

**Как стало.** Между шлюзами и платформой вставлен «конвейер с черновиками»:

```
 Шлюз ──> BI ──> база черновиков draft_db ──> модерация в админке TicketsCloud ──> кнопка «Опубликовать»
                (свои целые номера,                (контент-менеджер правит название,            │
                 Базис не используется)             ценз, привязывает площадку)                  ▼
                                                        чистовое ядро TicketsCloud ◄── BI отправляет данные
                                                        (событие + партнёры + сделка,               │
                                                         строковые ObjectId)                        │
                                                              ▲                                     │
                                                              └────── связка «номер черновика ↔ ObjectId» ──┘
                                                        дальше BI синхронизирует цены и статусы мест по ObjectId
```

1. Шлюз прислал каталог → BI сохранил его как **черновики** в собственную базу draft_db, присвоив каждому объекту свой целочисленный номер; в старую учётную таблицу `dbo.mapping` записалась связка «внешний номер ↔ наш номер». Базис (uat_db) больше не нужен.
2. Контент-менеджер видит черновики в привычной админке TicketsCloud, проверяет название и возрастной ценз, привязывает зал шлюза к «мастер-площадке» платформы.
3. По кнопке «Опубликовать» BI собирает чистовой пакет и отправляет его в ядро TicketsCloud по доверенному API.
4. Ядро само заводит нужных участников (системного бота, Поставщика — шлюз и Правообладателя), создаёт событие (в витринном статусе stand_by) и сделку «Поставщик ↔ МДТЗК», и возвращает строковый код — ObjectId.
5. BI сохраняет связку «номер черновика ↔ ObjectId» в реестр `gateway_id_mapping`, черновик получает статус PUBLISHED.
6. Все последующие изменения цен и статусов билетов BI доставляет в ядро напрямую по ObjectId (синхронизация К3).

## Словарик терминов

| Термин | Что это (для читателя вне IT) |
|---|---|
| Шлюз | Внешняя билетная система, откуда приходят мероприятия, сеансы, залы, места |
| BI (buildings-integration) | Наш сервис интеграций: принимает данные шлюзов и «заводит» их в платформу |
| draft_db | Новая база черновиков при BI (PostgreSQL): сюда попадает всё до проверки человеком |
| Черновик | Мероприятие/зал/сеанс в draft_db, ещё не попавшие в «бой»; имеет целочисленный номер (1000000 и далее) |
| dbo.mapping | Старая учётная таблица bi_db: связка «внешний номер шлюза ↔ наш номер черновика» |
| Модерация | Ручная проверка черновика контент-менеджером в админке TicketsCloud |
| master_venue_id | Привязка зала шлюза к настоящей площадке платформы; без неё публикация запрещена |
| Публикация | Перенос проверенного черновика в чистовое ядро по кнопке / доверенному API |
| Ядро TicketsCloud | Боевая система платформы: события, партнёры, сделки |
| ObjectId | Строковый код созданной в ядре сущности (24 символа), например `670c5e7b23f1a20001bc4901` |
| gateway_id_mapping | Реестр связок «номер черновика ↔ ObjectId» в draft_db; по нему BI находит чистовые сущности |
| stand_by | Витринный статус созданного события: видно в системе, но ещё не активно для продажи |
| Поставщик | Участник-шлюз: тот, чей каталог импортируем (роль agent) |
| МДТЗК | Наш дистрибьютор-партнёр, с которым автоматически заключается сделка по каждому событию |
| К1 / К3 | Контракты: К1 — публикация каталога в ядро; К3 — прямая синхронизация мест/цен по ObjectId |
| uat_db (Базис) | Старая база, из контура импорта выведена: обращений к ней больше нет |
| Админка | Веб-интерфейс TicketsCloud (Flask-Admin) по адресу `http://localhost:5000` |

## Правила проведения ПСИ

1. Каждый пункт — пара «Действие → Ожидаемый результат». Ведущий выполняет действие, сверяет факт с ожиданием и ставит вердикт: **✓ пройден** или **✗ не пройден** (к не пройденному — формулирует замечание; замечание фиксируется в конце документа и оформляется как дефект, после доработки — повторное ПСИ затронутых пунктов).
2. **Пункты выполнять по порядку Г1 → Г7** (единственное исключение: **П.2.5 выполняется до П.2.4** — блокировку кнопки публикации проверяют на ещё не привязанном черновике): java-прогоны сбрасывают базу черновиков, поэтому SQL-проверки выполняются сразу после прогона своей группы; данные в ядре (MongoDB) при этом накапливаются — везде используется ObjectId последней публикации.
3. Один и тот же java-прогон может закрывать несколько пунктов — в «Факте» тогда указывается общий прогон.
4. NFR-пункты (производительность) — advisory: на демонстрационном dev-стенде они показывают порядок величин, а не приёмку точных порогов.
5. **Если результат не совпал с ожидаемым:** прочитайте строку «Если расхождение» в пункте — там указано, где искать причину (лог, повторное действие, проверка контура) и когда ставить ✗. Общий порядок: проверьте контур (`docker ps` — 13 контейнеров в статусе Up), повторите действие один раз, не сошлось снова — ставьте ✗ и записывайте наблюдение в раздел «Замечания по итогам пилотного прогона».
6. **Как копировать команды.** Все команды в пунктах приведены целиком — копируйте от первой до последней строки (многострочные команды со знаком `\` копируются блоком: Bash исполнит их как одну). Слова вида `$ADMIN`, `$BIPASS`, `$BIWT` — переменные из «Подготовки стенда»: они живут до закрытия окна Терминала, в новом окне повторите шаги 1–2 (и шаг «Вход», если слетела сессия браузера).

Стенд входит по персональной подписанной ссылке (JWT-токен), а не через Google-аккаунт. Выполните в Терминале:

```bash
SECRET=$(sed -n 's/^gatekeeper_secret *= *//p' $VITRINA_MOUNT/ticketscloud/.worktrees/t17-tcbase/settings/local.ini | head -1)
TOKEN=$(python3 -c "
import hmac,hashlib,base64,json,sys
b=lambda d: base64.urlsafe_b64encode(d).rstrip(b'=')
h=b(json.dumps({'alg':'HS256','typ':'JWT'}).encode())
p=b(json.dumps({'email':'moderator@ticketscloud.ru','is_manager':True}).encode())
print((h+b'.'+p+b'.'+b(hmac.new(sys.argv[1].encode(),h+b'.'+p,hashlib.sha256).digest())).decode())" "$SECRET")
echo "Откройте в браузере: http://localhost:5000/login?token=$TOKEN"
curl -s -c /tmp/psi.cookies -o /dev/null -w '%{http_code}\n' "http://localhost:5000/login?token=$TOKEN"
```

- Терминал напечатает готовую ссылку — **откройте её в браузере**: страница сама выполнит вход и перенаправит в админку.

Это **нормальное поведение** dev-стенда (стоит боевой гейткипер), а не поломка. Всегда заходите по ссылке с токеном из этого шага.
- Если `302` не напечаталось: проверьте, что `SECRET` не пустой (шаг 1 выполнен, путь `settings/local.ini` доступен), и выполните блок заново — ссылка станет новой.

## Г1. Импорт: от шлюза до черновиков, Базис не участвует

**Факт:** COUNT = 0 — ни одного jtds-соединения к специально поднятой uat_db.
