# Чек-лист BPMN-документа (самопроверка и валидация)

> Ресурс скилла `business-process-analyst`. Используется дважды: генератором `/create-doc` (тип BPMN) перед сохранением — с явными ✅/❌ по каждому пункту; валидатором `/validate-doc` (ТИП К) — как Hard Gate-замена полевых гейтов (покрытие DTO-полей и Origin-маппинг к BPMN НЕ применяются).

## А. Рамка и источники

- [ ] Шапка: процесс, владелец процесса, режим, участники, триггер, вход → выход; для To-Be — источник требований.
- [ ] To-Be — только при источнике требований; ссылка есть в шапке и разделе 10. To-Be без источника — 🔴.
- [ ] Разделы 1–10 присутствуют по эталону; удалённый раздел — 🔴.
- [ ] Каждый факт бизнес-слоя имеет источник (документ, бизнес-артефакт, постановка задачи) или пометку `[УТОЧНИТЬ]`.
- [ ] Раздел 10 перечисляет использованные документы со статусами ✅/🟡 («не валидировано»), файлы кода и дату repomix-снапшота.

## Б. Слой языка

- [ ] В разделах 1–8 НЕТ технических идентификаторов: эндпоинтов, таблиц, колонок, хранимок, классов, методов, полей, очередей, конфиг-ключей, путей, кода, SQL. Хотя бы один — 🔴.
- [ ] Системы названы бизнес-именами (сверены с `naming_conventions.md`) и описаны как чёрные ящики.
- [ ] Технические подробности — только в разделе 9, и там они даны ссылками на документы-владельцы, а не пересказом.
- [ ] Аудитория и границы слоёв языка объявлены в шапке.

## В. Диаграмма (BPMN-профиль)

- [ ] В каждом блоке есть пара `@startuml` / `@enduml`, `title` с режимом (`As-Is:` / `To-Be:`) и `skinparam shadowing false`; `monochrome true` отсутствует.
- [ ] Дорожки — участники с бизнес-именами; внутренние — `<Пул> — <Роль>`; ≤ 7 дорожек и ≤ ~25–30 задач в блоке.
- [ ] Задачи — `:№. Действие;` с последовательной нумерацией; шлюзы `if / elseif / else`, параллельность `fork`, циклы `while` / `repeat` — по профилю.
- [ ] Основной сценарий ведёт к единственному `stop`; альтернативные завершения — `end` в первой ветке шлюза.
- [ ] Запрещённые конструкции отсутствуют: `#HEX:Текст;`, `kill`, `detach`, `split`, `newpage`, `stop` до `else`.
- [ ] Ветки `fork` заканчиваются в дорожке слияния.
- [ ] ТОЛЬКО PlantUML; Mermaid — 🔴. Подписи на русском, на бизнес-языке.
- [ ] Цвет: одно измерение, объявленное в мета-строке; `legend` с взаимной полнотой в каждом блоке, где есть цвет; цвет без легенды — 🔴.

## Г. Синхронность текста и диаграммы

- [ ] Число пронумерованных задач основной диаграммы = числу строк раздела 6; номера совпадают. Расхождение — 🔴.
- [ ] Каждая развилка, цикл, ожидание и параллельность диаграммы описаны в разделе 7; каждая ветка раздела 7 есть на диаграмме.
- [ ] Каждый свёрнутый подпроцесс `◁ ▷` раскрыт отдельным блоком (шаги `№.k` описаны в «П.<Название>» раздела 7) или отдельным документом со ссылкой в разделе 9.
- [ ] `bpmn_<название>.puml` существует и совпадает с plantuml-блоками раздела 5. Отсутствие или расхождение — 🔴.

## Д. Полнота и честность

- [ ] Известные, но не раскрытые ветки и правила помечены `[УТОЧНИТЬ]` (в тексте и `note` на диаграмме); молчаливый пропуск — 🔴.
- [ ] Нет выдуманных участников, шагов, правил и объектов: каждый подтверждён источником. Галлюцинация — 🔴.

## Е. Техническая привязка (раздел 9)

- [ ] Таблицы заполнены: участник → сервис; триггер → точка входа; объект → данные; шаг → документ-владелец.
- [ ] Каждая строка подтверждена готовым документом или кодом; пробелы помечены `[NEEDS_INVESTIGATION]`; неподтверждённая строка без пометки — 🔴.
- [ ] Ссылки относительные (`../processes/…`, `../api/…`, `../screens/…`, `../integrations/…`, `../erd/…`, `../data_trace_*.md`); битая или абсолютная — 🔴.
